# 赛事管理—赛事编排现状与理论、实操、仿真开发需求

> 版本：V1.0  
> 日期：2026-08-06  
> 适用范围：管理端赛事管理中的“赛段编排”及其理论考试、实操考评、仿真内容配置。  
> 需求口径：以当前代码、Flyway 迁移和既有成绩规则合同为基线；本文将“已实现”“后端已具备但前端未形成闭环”“待开发”分开描述。

## 1. 结论摘要

当前赛事编排不是单一的赛段名称维护，而是由以下四层组成：

1. 赛事上下文：赛事、赛事工种、赛事工种等级。
2. 赛段结构：资格赛、初赛、复赛、半决赛、决赛的阶段顺序、时间、说明和锁定。
3. 赛段内容：理论考试、实操考评、仿真操作及分项权重。
4. 赛前执行：按工种/等级生成理论或实操执行方案、名册、考场/场次、裁判组、选手分配、评分和晋级结算。

目前的完成状态如下：

| 范围 | 当前状态 | 说明 |
|---|---|---|
| 赛段画布编排 | 已实现 | 管理端可选择赛事和工种，配置预设赛段、时间、说明、内容权重、晋级比例，保存草稿并确认锁定。 |
| 理论试卷与考试执行 | 已实现一条独立管理链 | 已有组卷要求、A/B 卷快照、考场、排考版本、场次、随机分配、发布/撤回、名册导出、监考和结果摘要。 |
| 实操竞赛后端能力 | 已具备基础合同 | 已有实操规则、规则明细、场次、裁判组、裁判成员、选手分配、评分单及锁定/解锁接口。 |
| 实操编排前端闭环 | 待完善 | 尚未形成类似认定模块“考评员配置 + 实操配置”的竞赛页面和完整接口编排。 |
| 仿真 | 待定 | 当前仅允许在赛段内容中占位并设置权重；Provider 未接入时，执行方案发布和结算应被后端阻断。 |

赛事编排主入口为管理端 `/competition/stages`；理论考试独立入口为 `/competition/theory-exams`。`CompetitionStageExecutionWorkbenchPage` 已存在内容配置组件，但目前没有在赛事编排路由中形成完整的执行工作台入口。

## 2. 当前已实现功能

### 2.1 赛事和赛事工种上下文

- 赛事支持平台赛事和企业内部赛两种范围。
- 支持赛事草稿、发布、关闭、归档状态展示。
- 支持赛事开始时间、结束时间和赛事说明。
- 企业内部赛要求绑定所属企业。
- 赛事可关联多个赛事工种；赛段编排页面只允许选择状态为 active 的赛事工种。
- 赛事工种可继续拆分为赛事工种等级，等级有编码、名称、来源等级和对账状态。
- 赛事赛段编排支持赛事级兼容数据；管理端正式按“赛事工种 + 工种等级”独立保存赛段画布和晋级配置，工种级确认状态优先于赛事级状态。

### 2.2 赛段画布

当前节点库固定提供以下五种预设赛段，每种赛事最多添加一次：

| stageType | 展示名称 | 默认顺序 |
|---|---|---:|
| `qualification` | 资格赛 | 10 |
| `preliminary` | 初赛 | 20 |
| `quarterfinal` | 复赛 | 30 |
| `semifinal` | 半决赛 | 40 |
| `final` | 决赛 | 50 |

已实现操作：

- 从节点库拖入赛段或通过画布添加赛段。
- 删除赛段、自动排列、适配视口。
- 通过拖拽连线表达赛段顺序；业务顺序仍由 `stageType`/`sortOrder` 派生，连线上的说明仅作为编排备注。
- 选择赛段后编辑时间范围和赛段说明。
- 赛段编排草稿保存、放弃修改、离开页面未保存提醒。
- 校验结果以阻断项和警告项展示，并支持定位到节点或连线。
- 保存成功后可确认并锁定；锁定后不可继续编辑结构和关键属性。

当前校验规则：

- 至少配置一个业务赛段。
- 同一赛事不允许重复配置同一预设赛段。
- 开始时间和结束时间必须成对填写；结束时间必须晚于开始时间。
- 赛段时间不得超出赛事时间范围。
- 相邻赛段时间必须按预设顺序递增且不能重叠。
- 业务连线不能反向、分支、汇聚、成环、重复或断链；只能连接排序后的相邻赛段。
- 时间未填写、赛段说明为空属于警告；其余结构和时间错误属于阻断。

### 2.3 赛段内容与权重

每个赛段支持以下三种内容：

| contentType | 展示名称 | 当前状态 |
|---|---|---|
| `theory` | 理论考试 | 已有理论考试配置及执行链。 |
| `practical` | 实操考评 | 赛段内容可配置，竞赛实操执行链待前端闭环。 |
| `simulation` | 仿真操作 | 仅占位，Provider 未接入。 |

内容配置规则：

- 可多选内容类型；至少启用一项。
- 启用项权重必须大于 0，未启用项权重为 0。
- 理论、仿真、实操权重总和必须等于 100%。
- 权重范围为 0～100，前端支持两位小数；数据库使用 `DECIMAL(5,2)`。
- 仿真内容当前自动写入 `providerCode=simulation-placeholder`，后端就绪检查会将其视为未接入。
- 赛段内容与权重可以在选中的赛段上编辑，并随赛段编排草稿统一保存。

### 2.4 按工种的晋级配置和结算确认

按赛事工种配置的属性包括：

- 启用状态：`enabled`。
- 工种内赛段顺序：`sortOrder`。
- 晋级规则类型：当前支持 `PERCENTAGE`、`FINAL_PODIUM`、`LEGACY`，后端还兼容 `FIXED_COUNT`。
- 晋级百分比：1～100 的整数；前端对非决赛赛段提供编辑。
- 晋级人数：`promotionQuota`，作为固定人数规则兼容字段。
- 历史规则标记：`legacyRule`。

当前页面行为：

- 非决赛赛段可填写晋级百分比；系统按有效选手基数计算目标人数，并在参考名单生成时向上取整。
- 决赛不配置晋级百分比，结算后人工确认第一、第二、第三名。
- 可按工种选择执行方案和结算快照。
- 可生成晋级参考名单，查看基数、目标人数、来源排名、选择状态和计算说明。
- 可确认并锁定参考名单。
- 决赛前三名支持录入第一名、第二名、第三名及特殊说明，并确认锁定。

### 2.5 已具备但尚未完全挂入赛段编排页的执行能力

后端已有通用执行方案合同，覆盖：

- 执行方案版本的创建、查询、发布、撤回和发布前检查。
- 执行方案资源的整体替换和资源占用时间校验。
- 资格/晋级/人工三类选手名册快照的生成、发布和调整。
- 理论、仿真、实操三类执行分配类型。
- 实操规则、实操场次、裁判组、裁判成员、选手—裁判分配和评分单。

这些接口属于“后端已具备”，不等同于“管理端已形成可操作闭环”。本次 B 需求需要把其中的实操能力挂入赛事工种、赛段和等级上下文，并补齐认定模块式的前端配置体验。

## 4. A. 理论试卷配置开发需求

### 4.1 目标和范围

形成“赛事—赛段—工种—等级—评分规则—组卷要求—A/B 快照—排考—考试执行”的完整链路。理论试卷必须使用竞赛域不可变快照，不能直接把可变的旧 `exam_paper` 作为开考数据源。

### 4.2 管理端页面和操作

页面上下文必须选择：

- 赛事。
- 赛段。
- 赛事工种。
- 可选赛事工种等级。
- 已发布成绩规则版本。

页面至少包含四个工作区：

1. **组卷要求**：查看和编辑模板、时长、题量、单题分值、总分和及格线。
2. **A/B 卷快照**：选择题库课程和来源试卷，导入并固化 A/B 两套竞赛快照，显示版本、题量、分值、时长、状态和固化时间。
3. **排考与名册**：创建排考版本，配置考场、场次和卷别，随机分配或手动调整，发布/撤回，导出 Excel/PDF 名册。
4. **监考与结果**：查看选手号、姓名、单位、场次、考场、座位、答题状态、在线状态和最后保存时间；支持强制下线、强制交卷、恢复暂定缺考；查看未发布结果摘要。

### 4.3 固定业务规则

- `THEORY_90`：90 分钟，单选 60×1 分、多选 20×1 分、判断 40×0.5 分，总分 100。
- `THEORY_120`：120 分钟，单选 120×0.5 分、多选 20×1 分、判断 40×0.5 分，总分 100。
- `CUSTOM` 只能在题量×分值之和等于总分、题型受支持且分值合法时保存。
- 同一工种的 A/B 卷必须使用同一模板、同一时长、同一满分，并通过等值性检查后才允许进入同一排名范围。
- A/B 必须为不同来源试卷；重复导入生成新版本，不覆盖历史快照。
- 试卷快照发布后，题干、选项、答案、分值、判分规则和来源审计字段不可变。
- 多选题必须与标准答案集合完全一致才得分，漏选、错选、多选均为 0 分，不设部分分和倒扣分。
- 场次发布后，已分配选手的场次和试卷版本不能直接修改；更正必须保留原分配、原因和操作者。
- 所有考试时间以服务端时间为准；交卷、自动交卷、监考操作和成绩来源写入审计记录。

### 4.4 现有实现需先修正的口径冲突

当前前端在无组卷要求时使用了 `templateCode=A_B` 的默认值，但数据库约束和后端合同只允许 `THEORY_90`、`THEORY_120`、`CUSTOM`。A 需求开发前必须统一为上述三个编码，不能继续提交 `A_B`。

### 4.5 接口交付

现有接口可作为 A 的实现基线：

- 组卷要求：`GET/PUT /competition/score-rules/{ruleId}/theory-requirement`。
- 来源课程和试卷：`GET /competition/events/{eventId}/theory-exam/courses`、`source-papers`。
- A/B 快照：`GET/POST /competition/events/{eventId}/theory-exam/paper-snapshots`。
- 排考版本：创建、列表、详情、发布前检查、发布、撤回。
- 考场：新增、编辑、删除、列表。
- 场次：新增、编辑、删除、随机分配、手动调整。
- 名册：Excel/PDF 导出。
- 监考：列表、强制下线、强制交卷、恢复暂定缺考；结果摘要查询。

新增或调整接口时必须补充等级作用域、权限、审计和雪花 ID 字符串化约束。

### 4.6 A 验收标准

- 两个固定模板和自定义模板的合法/非法边界均有后端测试。
- A/B 卷来源不同、模板一致、题量和总分一致时可以固化；否则阻断。
- 快照生成后修改题库原题不会改变快照。
- 场次重叠、容量不足、跨工种试卷、未发布快照绑定均被拒绝。
- 发布后的排考不能直接改卷或换人，撤回必须填写原因并保留历史。
- 选手端/监考端投影不包含标准答案、解析、来源组织和出题人信息。
- 交卷幂等，同一答卷最多生成一个当前有效理论成绩来源。

## 5. B. 实操配置开发需求

### 5.1 参考认定模块的复用边界

参考认定模块的两个配置入口：

- **考评员配置**：考评组名称、组长、负责工种/等级、考评员成员、证号、工种范围、等级范围、有效期、工作状态、成员角色。
- **实操配置**：按工种/等级筛选考生，绑定实操试卷和考评组，生成三名考评员评分任务，查看三人评分进度、分差异常、缺考、退回、修分和导出。

竞赛 B 应复用其交互方式、三人评分和评分模板理念，但不能直接写入 `certification_*` 表，也不能把认定任务 ID 当作竞赛主键。竞赛数据必须落在 `competition` 领域，并以赛事、赛段、赛事工种、赛事工种等级、选手成员和执行方案为作用域。

### 5.2 B 页面结构

在赛事编排的选定赛段/工种/等级下新增“实操配置”工作台，至少包含：

1. **考评员配置**。
2. **实操规则/评分表配置**。
3. **场次和工位配置**。
4. **选手分配与开考**。
5. **评分进度、异常处理和导出**。

### 5.3 B-1 考评员配置字段

#### 考评员来源和资格

考评员候选人从当前赛事中 `roleType=referee` 且状态有效的赛事成员中选择，展示：

| 字段 | 含义 | 规则 |
|---|---|---|
| `refereeMemberId` | 赛事裁判成员 | 必须属于当前赛事且具有 referee 角色。 |
| `professionalField` | 专业领域 | 来源裁判档案快照。 |
| `refereeLevel` | 裁判等级 | 用于资格匹配。 |
| `certificateNo` | 裁判/证书编号 | 作为展示和审计快照。 |
| `refereeGroupCode` | 来源裁判组编码 | 可选。 |
| `status` | 成员状态 | active/suspended/withdrawn 等。 |

候选列表必须过滤：已退出成员、当前赛段无授权成员、有效期不满足规则的成员，以及命中回避关系的成员。

#### 裁判组

| 字段 | 展示名称 | 规则 |
|---|---|---|
| `stageId`、`eventWorkTypeId`、`eventWorkTypeLevelId` | 配置范围 | 必须绑定当前赛段、工种和可选等级。 |
| `sessionId` | 实操场次 | 裁判组属于具体场次。 |
| `groupNo` | 组号 | 同一场次内唯一且大于 0。 |
| `groupName` | 裁判组名称 | 必填。 |
| `officialCount` | 正式裁判数 | 固定为 3，不允许前端改成其他数量。 |
| `standbyCount` | 备用裁判数 | 可配置为 0 或多个。 |
| `status` | 裁判组状态 | draft/published/closed。 |
| `remark` | 备注 | 可选。 |

#### 裁判成员

| 字段 | 展示名称 | 规则 |
|---|---|---|
| `refereeMemberId` | 裁判 | 来源当前赛事裁判成员。 |
| `memberRole` | 成员角色 | official/standby。 |
| `taskRole` | 任务角色 | member/leader 等展示角色。 |
| `workTypeScope`、`levelScope` | 工种/等级范围 | 必须覆盖当前配置范围。 |
| `certificateNo`、`validUntil` | 证号、有效期 | 建立任务时保存快照。 |
| `status` | 分配状态 | active/replaced/withdrawn。 |
| `replacedMemberId` | 被替换成员 | 备用裁判补位时必填。 |
| `replacementReason` | 补位原因 | 补位、退出或回避必须填写。 |

#### 回避配置

系统必须支持裁判—选手回避：

- 关系类型：`mentor`、`relative`、`same_org`、`other`。
- 回避原因、配置人、配置时间、状态、结束时间。
- 生成选手分配和保存评分前再次校验回避，不允许仅依赖前端过滤。

### 5.4 B-2 实操规则和评分表字段

#### 规则主表

| 字段 | 含义 | 规则 |
|---|---|---|
| `eventId`、`stageId`、`eventWorkTypeId`、`eventWorkTypeLevelId` | 实操规则作用域 | 规则必须属于当前编排上下文。 |
| `ruleVersion` | 规则版本 | 新规则生成新版本，已发布版本不可覆盖。 |
| `ruleName` | 评分规则名称 | 必填。 |
| `totalScore` | 实操总分 | 默认 100，范围 0～100。 |
| `status` | 状态 | draft/published/withdrawn。 |
| `publishedAt`、`publishedBy` | 发布信息 | 审计字段。 |
| `sourceFileId`、`sourceVersion` | 技术文件/评分细则来源 | 必须能追溯到已确认版本。 |

#### 评分项

认定模块中的评分模板字段要迁移到竞赛规则明细中，不能只保存一个不可解释的总分：

| 字段 | 含义 | 规则 |
|---|---|---|
| `itemCode` | 评分项编码 | 同一规则内唯一。 |
| `itemName` | 评分项名称 | 必填。 |
| `sortOrder` / `itemNo` | 评分项序号 | 大于 0 且连续展示。 |
| `criterion` | 评分标准 | 评分员可见；作为规则快照。 |
| `maxScore` | 满分 | 大于 0。 |
| `maxDeduction` | 最大扣分 | 不得超过该项满分。 |
| `deductionStep` | 扣分步长 | 大于 0；默认 1。 |
| `deductionAllowed` | 是否允许扣分 | 0/1。 |
| `criteriaPayload` | 结构化评分要点 | JSON；记录安全、质量、工艺等要点。 |
| `status` | 明细状态 | enabled/disabled。 |

当前 `competition_practical_rule_item` 已有 `itemCode`、`itemName`、`sortOrder`、`maxScore`、`deductionAllowed`、`criteriaPayload`，但尚未完整具备认定模块的 `criterion`、`maxDeduction`、`deductionStep` 字段。B 开发必须补齐，或在 `criteriaPayload` 中形成稳定版本化 schema 并明确字段映射；推荐补充为独立列，便于校验、查询和导出。

规则发布前检查：启用评分项至少一项；各项分值合计等于总分；扣分上限、步长、评分标准完整；当前作用域没有未处理的裁判资格或回避冲突。

### 5.5 B-3 场次、工位和选手配置

#### 实操场次

| 字段 | 含义 | 规则 |
|---|---|---|
| `planId` | 执行方案 | 必须是当前上下文的 draft 方案。 |
| `sessionCode` | 场次编码 | 同一执行方案内唯一。 |
| `sessionName` | 场次名称 | 必填。 |
| `startAt`、`endAt` | 开始/结束时间 | 结束晚于开始，同资源不能冲突。 |
| `capacity` | 场次容量 | 可空时由资源容量计算；填写时必须大于 0。 |
| `resourceId` | 场地/设备资源 | 关联执行方案资源。 |
| `status` | 场次状态 | draft/published/in_progress/closed/cancelled。 |

#### 选手—裁判分配

| 字段 | 含义 | 规则 |
|---|---|---|
| `rosterItemId` | 名册行 | 必须来自当前已发布名册快照。 |
| `contestantMemberId` | 选手成员 | 必须属于当前赛事工种/等级。 |
| `sessionId`、`judgeGroupId` | 场次和裁判组 | 必须属于同一执行方案。 |
| `refereeMemberIds` | 裁判成员 | 正式裁判固定 3 人；回避成员不能分配。 |
| `workstationCode` | 工位编号 | 同一场次内唯一，可选。 |
| `status` | 分配状态 | assigned/in_progress/completed/withdrawn。 |
| `assignedAt`、`endedAt` | 分配和结束时间 | 服务端记录。 |

配置体验应参考认定模块：先按工种/等级筛选候选选手，再批量选择执行方案、实操规则/试卷和裁判组；已配置或已生成评分任务的选手不能重复配置，除非先撤销并保留原因。

### 5.6 B-4 开考、评分、异常和结果

- 每名选手固定 3 名有效正式裁判；正式裁判缺评、回避、退出或无法重评时，只能由已配置的备用裁判补位。
- 未达到 3 个有效锁定评分时，选手实操成绩为“待确认”，不得进入总分和排名。
- 实操评分单必须关联选手、裁判、执行方案、规则版本和评分明细版本。
- 每个评分项保存扣分、得分、说明；总分由服务端计算，不接受前端直接提交总分。
- 三名有效裁判成绩取算术平均，按既有合同保留 2 位小数。
- 评分单状态至少支持 draft、submitted_locked、unlocked_for_rescore、voided；锁定后只有具备解锁权限且填写原因才能重评。
- 三名评分分差超过 10 分时，标记为 `review_required`，不能直接完成该选手实操成绩。
- 支持标记缺考；缺考成绩如何进入最终排名必须引用赛事成绩规则，不在实操页面自行决定。
- 实操管理页展示考生、工种、等级、裁判组、三名裁判提交进度、单题/评分项进度、总分、分差异常、缺考和状态。
- 支持退回评分任务、异常修分、填写修改原因、保留历史版本和导出实操评分表。

### 5.7 B 接口和权限基线

当前后端接口可复用：

- 实操规则：`GET/POST /competition/stages/{stageId}/practical-rules`、`POST /competition/practical-rules/{ruleId}/publish`。
- 实操场次：`GET/POST /competition/execution-plans/{planId}/practical-sessions`、发布场次。
- 裁判组：查询/创建裁判组，启用备用裁判。
- 分配：创建实操分配，查询场次分配。
- 评分单：打开、保存、锁定、解锁。

需要补齐的竞赛前端闭环接口：

- 当前赛事/赛段/工种/等级可用裁判列表及资格校验结果。
- 裁判组编辑、删除、成员列表、添加/移除成员、正式/备用角色调整。
- 裁判—选手回避配置和冲突查询。
- 实操规则明细编辑、导入评分表、规则版本复制和发布前检查。
- 按名册快照批量生成选手—裁判—工位分配。
- 实操开考会话、评分进度、分差异常、缺考、退回、重评和汇总导出。

权限沿用后端最终裁决：

`competition:practical-rule:view/manage/publish`、`competition:practical-session:view/manage`、`competition:judge-group:view/manage`、`competition:practical-assignment:view/manage`、`competition:practical-score:manage/unlock`。所有写操作必须有审计日志。

### 5.8 B 验收标准

- 只能从当前赛事的有效 referee 成员中配置裁判；不满足工种/等级范围、已退出或命中回避的成员被拒绝。
- 每个裁判组正式成员必须恰好 3 人，备用成员可以为 0 个或多个；重复成员、重复组号被拒绝。
- 场次时间、容量、资源冲突、跨执行方案分配均有后端校验。
- 选手批量配置后生成唯一评分任务；重复配置不重复生成任务。
- 三名裁判全部锁分后才产生正式实操成绩；平均值和精度正确。
- 分差超过 10 分自动进入异常状态；异常未处理不能结算。
- 评分单锁定后直接保存被拒绝；解锁必须有权限、原因和历史版本。
- 备用裁判补位保留被替换成员、替换原因、原评分和新评分。
- 竞赛实操页面不读写认定任务表，但交互和字段能覆盖认定模块的“考评员配置/实操配置”核心能力。

## 6. C. 仿真配置（待定）

### 6.1 当前处理口径

仿真暂不开发外部系统接入、仿真过程、设备状态、成绩回传、耗时回传、验签和对账。当前仅保留：

- 赛段内容类型 `simulation`。
- 仿真权重。
- `providerCode` 和未来成绩来源 `sourceType=simulation` 的扩展位。

### 6.2 必须保持的占位行为

- 允许在赛段内容中勾选仿真并设置权重，但权重合计仍必须为 100%。
- Provider 为 `simulation-placeholder` 或未配置时，执行方案发布前检查返回阻断项。
- 仿真未接入时不得生成正式仿真执行分配、仿真成绩来源、总分快照或排名快照。
- 赛事成绩页面可以展示“仿真待接入/未就绪”，不能展示伪造的 0 分或成功状态。
- 不创建仿真回调、验签、重试、对账和外部系统映射表，直到业务确认外部平台、字段和时序。

### 6.3 后续启动条件

C 需要业务确认以下内容后另立开发任务：仿真平台/Provider、选手身份映射、考试开始和结束信号、成绩与耗时字段、签名验签、失败重试、人工修订、对账规则、是否参与赛制 A/B 总分和排名二级排序。

## 7. 版本、权限、审计和数据约束

- 赛事、赛段、执行方案、试卷、评分规则、名册、成绩、晋级和排名都必须保留版本或快照，发布后不可静默覆盖。
- 理论快照、实操评分规则和裁判分配必须带赛事、赛段、工种、等级作用域。
- 后端是权限最终裁决点；前端权限只用于展示和交互控制。
- 所有创建、修改、发布、撤回、锁定、解锁、缺考、补位、回避、异常修分和名单调整必须写审计日志。
- 竞赛实操不得绕过 `competition` Application/Domain 层直接访问认定 Mapper；如复用认定评分算法，应通过明确的适配层复用纯规则，不复用认定数据表。
- 所有新增或修改实体必须和 DDL 完整映射 BaseEntity 六列；分数、权重使用 `DECIMAL`/`BigDecimal`，禁止使用浮点计算。
- 雪花 ID 下发前转字符串，避免前端 `Number` 精度丢失。
- 异步生成名册、评分任务、导出或回调时，HTTP 线程提前捕获 `tenantId/userId/requestId`，Worker 调用链不得读取 `SecurityContext`；每个 Worker 独立设置并清理租户上下文。

## 8. 推荐开发顺序

1. 先修正理论模板编码冲突，补齐 A 的等级作用域和发布前校验。
2. 将实操规则明细补齐评分模板字段，先完成竞赛实操后端合同和测试。
3. 在赛事编排页增加实操配置入口，先交付考评员配置，再交付评分规则/实操配置。
4. 接入实操场次、名册、裁判组、选手分配和评分进度，完成三人评分及异常处理闭环。
5. 将实操结果接入成绩来源、总分计算和晋级结算，并补齐真实权限/审计验收。
6. 仿真保持占位，待业务确认后另立 C 任务，不与 A/B 同批假设性开发。
