## 3. 目标口径

### 3.1 scope 定义

```
scope = (tenant_id, work_type_id, level)     // level 用库内 0~4
scopesOf(plan) = train_exam_work_type_list 中该计划的有效绑定，
                 过滤 deleted=0、work_type_id/level 非空、work_type 存在且未删除，
                 按 (work_type_id, level) 去重
```

- `course_id` **不属于** scope；它只用于同步学/题库取题。
- 一个计划可以有 N 个 scope；真题可见性取这些 scope 的**并集**。
- 不采用“多等级取最高等级”。

### 3.2 等级口径

库内 `train_exam_work_type_list.level` 是 `tinyint`，0~4：

| level | 标准名 | 标题常见写法 |
|---|---|---|
| 0 | 五级 / 初级工 | 五级、初级、初级工 |
| 1 | 四级 / 中级工 | 四级、中级、中级工 |
| 2 | 三级 / 高级工 | 三级、高级、高级工 |
| 3 | 二级 / 技师 | 二级、技师 |
| 4 | 一级 / 高级技师 | 一级、高级技师 |

**v2 推荐直接沿用 0~4 作为存储与比较口径**，展示时由 `ZhentiLevel` 输出中文标签。若产品/接口必须使用 1~5（1=一级），只在边缘转换：`displayCode = 5 - level`，且转换只能有一处实现。

> 实体里 `level` 是 `String`、库是 `tinyint`，解析必须容错；复用 `ReviewQuestionQueryService.parseLevel` 的写法。

### 3.3 降级规则

以下情况该计划**不参与共享**，退回 `exam_id` 私有口径：

- 没有任何有效绑定；
- 绑定存在但 `work_type_id` 或 `level` 为空；
- 绑定的 `work_type_id` 在 `exam_work_type` 中不存在或已删除；
- `platform.zhenti.scope-enabled=false`。

当前生产有 **9 条活跃绑定**命中第 3 条（工种 68/104 已消失），对应计划在修复前走降级，不能因为“算不出 scope”而看不到真题。

### 3.4 可见性与上传语义

**查询可见性**（计划有有效 scope 时）：

```sql
WHERE tenant_id = ?
  AND status = 1
  AND deleted = 0
  AND (
        (work_type_id, level_code) IN (scopes...)
     OR (work_type_id IS NULL AND level_code IS NULL AND exam_id = ?)  -- 迁移期未归类旧数据
  )
```

第二项保证：已有但尚未回填 scope 的真题，仍然只在自己的计划可见，不会在迁移期“消失”。

**上传语义**：

- 0 个 scope → 按 `exam_id` 私有；
- 1 个 scope → 默认使用该 scope；
- N 个 scope → 请求必须显式指定一个 scope，不默认取最高；同一文件如需共享到多个 scope，v1 要求分别上传（或后续增加“应用到全部 scope”）。

## 4. 数据模型改造

### 4.1 不改 `train_exam_list`

关联表已经是事实来源；给主表加 `work_type_id/level_code` 会制造第二份实现，而且表达不了一对多。v2 取消 v1 的 `V20261020_001__exam_list_add_scope.sql`。

### 4.2 `exam_zhenti` 新增 scope 字段

```sql
ALTER TABLE exam_zhenti
  ADD COLUMN work_type_id BIGINT NULL COMMENT '共享组：工种（exam_work_type 叶子节点）' AFTER exam_id,
  ADD COLUMN level_code   TINYINT NULL COMMENT '共享组：等级 0五级 1四级 2三级 3二级 4一级' AFTER work_type_id,
  ADD COLUMN scope_key    VARCHAR(64) NOT NULL DEFAULT '' COMMENT '去重键：work:{workTypeId}:{level} 或 exam:{examId}' AFTER level_code,
  ADD KEY idx_zhenti_scope (tenant_id, work_type_id, level_code, status, deleted);
```

- `exam_id` 保留，语义 = 首次上传来源计划，仅用于溯源与降级查询；
- `file_key` / `file_size` / `file_md5` 不变，同一文件仍只存一份对象；
- `scope_key` 由应用统一生成，禁止各 Service 自行拼接。

### 4.3 唯一键与 NULL 陷阱

现有 `idx_zhenti_md5(exam_id, file_md5)` **不是唯一索引**，去重靠应用查询。若直接升级为：

```sql
UNIQUE (tenant_id, work_type_id, level_code, file_md5)
```

在 `work_type_id/level_code` 为 NULL 时，MySQL 认为 NULL 互不相等，同一文件可以插入多行，去重失效。因此 v2 使用 `scope_key`：

- 有 scope：`work:{work_type_id}:{level_code}`
- 无 scope：`exam:{exam_id}`

```sql
ALTER TABLE exam_zhenti
  ADD UNIQUE KEY uk_zhenti_scope_md5 (tenant_id, scope_key, file_md5);
```

> **实施修正（v2.2）**：唯一键实际实现为 `(tenant_id, scope_key, file_md5, deleted)`——
> 不含 deleted 时软删行会永久挡住同键重传（D5 隐性回归）；含 deleted 则“删除→重传→再删”
> 撞键，由 `ZhentiAdminService.delete` 捕获 DuplicateKeyException 后归档 scope_key
> （追加 `:del:{id}`）再删兜底。两种语义都已用 IT 固化（ZhentiDedupeServiceTest）。

- 加唯一键前先查重：当前生产仅 1 行真题，安全；
- 若历史环境存在重复 `(tenant_id, scope_key, file_md5)`，先清理再加；
- `scope_key` 用普通列（应用维护）还是生成列，见 §12 Q4；v1 建议普通列 + 单一工具类，便于 `ON DUPLICATE KEY UPDATE` 与索引稳定。

### 4.4 迁移清单

取号前必须重新查两库 `SELECT MAX(version) FROM flyway_schema_history`（2026-10-20 实测均为 `20261018.004`，别人可能已插号）。

| 脚本 | 内容 |
|---|---|
| `V20261020_001__exam_zhenti_add_scope.sql` | §4.2 加列 + `scope_key` + `idx_zhenti_scope`（**先不加唯一键**） |
| `V20261020_002__exam_zhenti_backfill_scope.sql` | 回填全部现有真题（当前仅 1 条）：按各 `exam_id` 的活跃绑定写 `work_type_id/level_code/scope_key`（441 → `work:35:0`）；无有效 scope 的行写 `exam:{exam_id}`；幂等、带存在性守卫 |
| `V20261020_003__exam_zhenti_scope_unique.sql` | 先查 `(tenant_id, scope_key, file_md5)` 重复，确认无冲突后加 `uk_zhenti_scope_md5`；有冲突则先清理，不硬加 |
| `V20261020_004__zhenti_scope_menu_seed.sql` | 仅保留“真题共享范围”页时新增菜单，复用 `exam:zhenti:manage`，`tenant_id=10159` |
| 可选 | `train_exam_work_type_list` 增加 `KEY idx_exam_work_type_exam (exam_id, deleted)`（当前只有 PRIMARY，508 行全表扫无压力，量大再加） |

> 顺序不能颠倒：先加列 → 回填 → 再加唯一键。否则所有旧行的 `scope_key` 都是空串，唯一键可能在建键阶段直接冲突。

### 4.5 绑定表数据约束

`train_exam_work_type_list` 没有 `(exam_id, work_type_id, level)` 唯一约束；历史上 `saveWorkTypeList` 采用“逻辑删旧 + 插新”，所以同一计划会有多条历史行。v2 不强行加唯一约束（`deleted` 维度会让历史行冲突），由 resolver 过滤 `deleted=0` 后按 `(work_type_id, level)` 去重。

## 6. 服务端改造

| 位置 | 现状 | 改造 |
|---|---|---|
| **新增** `ZhentiScopeResolver` | — | 输入 `examId` → 查 `train_exam_work_type_list`（`exam_id=? AND deleted=0`）→ 过滤 `work_type_id/level` 空值、`work_type_id` 在 `exam_work_type` 不存在或已删除 → 按 `(work_type_id, level)` 去重 → 返回 `List<Scope>`，无有效 scope 返回空；“共享计划数/范围页”统计才 join 活跃 `train_exam_list`（排除孤儿） |
| **新增** `ZhentiLevel` / `ZhentiScopeKey` | — | 等级标签、0~4 解析、`scope_key` 生成（`work:{id}:{level}` / `exam:{id}`），单一实现 |
| `ZhentiAppService.list()`（A1） | `.eq(examId)` | 有 scope → 按 §3.4 的并集查询（含未归类旧数据）；无 scope → 保持 `.eq(examId)` |
| `ZhentiAdminService.page()`（D1） | `.eq(examId)` | 同上 |
| `ZhentiAdminService.years()` | 按 `exam_id` 去重 | 按 scope 集合 + 未归类旧数据去重 |
| `ZhentiAdminService.upload()`（D2） | 传 `examId` | 先解析 scopes；0/1/N 按 §3.4 处理；N 时必须显式 scope |
| `ZhentiIngestService.ingest()` | 写 `examId`；`findActiveByMd5(examId, md5)` | 额外写 `work_type_id/level_code/scope_key`；去重改为 `(tenant, scope_key, md5)`；无 scope 用 `exam:{examId}` |
| `ZhentiImportService` / `ZhentiImportWorker` | 传 `examId` | 异步链路显式传 `List<Scope>` + tenantId，不依赖 SecurityContext |
| `ZhentiAdminService.delete()/update()` | 单条 | 逻辑不变；确认文案改为“影响整个共享组” |
| `ExamZhentiEntity` | — | 加 `workTypeId/levelCode/scopeKey` |
| `ZhentiVO` | `examId` | 加 `scopeLabels`（复数，形如“铝及铝合金熔铸工 · 四级/中级工”） |
| 配置 | — | `platform.zhenti.scope-enabled`（默认 `true`），一键回退 |

**实现要点**：

- 查询条件用 `and(...)` 包住 scope OR 分支，避免与 title/year 等过滤串联成错误 SQL；MyBatis-Plus 不支持 row constructor 时改为逐 scope `OR`；
- scopes 为空时**禁止**生成 `IN ()`；
- 有有效 scope 的计划上传**必须**选一个 scope，v1 不提供“有 scope 但按 exam_id 私有”；
- 管理端列表保留“来源计划（exam_id）”列，共享不掩盖归属；
- `scope-enabled=false` 同时作用于读路径与去重键（去重回退 `exam:{examId}`）；
- resolver 只按参数使用 tenantId，整条调用链不调 `SecurityContext`（异步红线）；Worker 线程自行 `TenantContextHolder.set/clear`。

**缓存**：v1 不加缓存。261 个计划、500 余条绑定，按 `exam_id` 查询（建议补索引）足够快；缓存会引入“计划改绑定后真题范围不更新”的一致性问题。若后续压测需要，再加按 `examId` 的短 TTL 缓存，并在计划绑定变更时发事件失效。

**关键约束**：`scope_key`、等级解析、scope 过滤只能有一份实现；禁止在 A1/D1/上传/导入里各写一套。

## 附录 A：盘点 SQL

```sql
-- 1. 计划与绑定覆盖（活跃口径）
SELECT COUNT(*) AS plans FROM train_exam_list WHERE deleted = 0;

SELECT COUNT(*) AS bindings, COUNT(DISTINCT w.exam_id) AS plans_with_binding
FROM train_exam_work_type_list w
JOIN train_exam_list e ON e.id = w.exam_id AND e.deleted = 0
WHERE w.deleted = 0;

-- 2. 缺绑定计划
SELECT COUNT(*) AS no_binding
FROM train_exam_list e
LEFT JOIN (
  SELECT DISTINCT w.exam_id
  FROM train_exam_work_type_list w
  JOIN train_exam_list e2 ON e2.id = w.exam_id AND e2.deleted = 0
  WHERE w.deleted = 0
) w ON w.exam_id = e.id
WHERE e.deleted = 0 AND w.exam_id IS NULL;

-- 3. 每计划绑定数分布
SELECT cnt, COUNT(*) AS plans
FROM (
  SELECT w.exam_id, COUNT(*) AS cnt
  FROM train_exam_work_type_list w
  JOIN train_exam_list e ON e.id = w.exam_id AND e.deleted = 0
  WHERE w.deleted = 0
  GROUP BY w.exam_id
) t
GROUP BY cnt ORDER BY cnt;

-- 4. 空值与失效工种
SELECT SUM(work_type_id IS NULL) AS null_wt,
       SUM(level IS NULL) AS null_level,
       SUM(course_id IS NULL) AS null_course
FROM train_exam_work_type_list w
JOIN train_exam_list e ON e.id = w.exam_id AND e.deleted = 0
WHERE w.deleted = 0;

SELECT w.exam_id, w.work_type_id, w.level
FROM train_exam_work_type_list w
JOIN train_exam_list e ON e.id = w.exam_id AND e.deleted = 0
LEFT JOIN exam_work_type t ON t.id = w.work_type_id
WHERE w.deleted = 0 AND t.id IS NULL;
```
