## 一、背景

### 1.1 为什么要写本方案

现网 `TrainingOperatorScopeService` 把用户所属组织的 `org_type` 映射为 `loginRole`：

- `company` / `master` → `company`（企业视角）  
- 其它 → `org`（机构视角）  

产品侧实际口径是：**机构下面可以有多家企业；企业也可独立开账号；企业可自运营（几乎与机构同能力，限本企业数据）；机构可配置企业功能。**  
旧「组织层改造方案」中 D1（企业默认仅读 + 审核）与本次访谈不一致，需用本方案重锁目标。

### 1.2 名词

| 名词 | 含义 |
|------|------|
| 机构 | 培训承办方组织；组织树上级；下一层可挂多家企业 |
| 企业 | **单个公司**；可挂在机构下，也可做成树上独立节点 |
| 下属企业 | 组织树上 `parent` 挂在某机构下的企业 |
| 独立企业 | 树上无上级机构；可由超管创建 |
| 业务关联 | 机构在「培训需求」中选中该企业后建立；**永久有效**；不改变组织树挂载 |
| 超管 | 当前即系统平台管理员 `admin`（`PLATFORM_ADMIN`，role_id≈2000） |
| 细角色 | 机构管理员/跟班员、企业审核员等；**本期不做，以后再拆** |

## 二、已锁定产品决策

| # | 决策 | 口径 |
|---|---|---|
| P1 | 层级关系 | 机构 ⊃ 企业（树上可挂多企业）；企业=单个公司 |
| P2 | 企业节点形态 | **可独立节点，也可挂机构下** |
| P3 | 下属企业可见性 | 机构账号默认可看本机构下全部下属企业的数据（挂树 = 有合作） |
| P4 | 独立企业可见性 | 默认仅本企业账号 + 超管；机构须经业务关联后才可看 |
| P5 | 关联起点 | **机构创建培训需求时选中该企业** |
| P6 | 关联效力 | 关联后机构可查看该企业**全部信息**；关联**一直有效**（不随单笔需求结束而取消） |
| P7 | 多机构 | 同一企业可被多家机构需求选中；多家均可看全部信息 |
| P8 | 关联不改树 | 独立企业被需求选中后，**组织树仍保持独立**，只建业务「可查看/可关联」 |
| P9 | 下属企业跨机构 | 挂在机构 A 下的企业，机构 B 仍可用需求选中；B 也可看全部信息 |
| P10 | 企业能力 | 企业可**自运营**，能力**几乎与机构一样**，数据范围限本企业；要能看本企业使用数据 |
| P11 | 功能配置 | **菜单/模块开关 + 权限角色包两者都有** |
| P12 | 谁可配置 | 机构可配置（下属/关联）企业功能；超管可配置机构与企业功能；企业管理员可在**超管给定能力上限**内配本企业子账号权限 |
| P13 | 多机构配功能冲突 | **系统暂不消解**，靠人工协调 |
| P14 | 账号谁建 | 超管可建机构账号与企业账号；机构可建下属企业账号并代管；企业只建本企业子账号 |
| P15 | 机构建企业 | 机构建企业时，企业组织**自动挂到该机构下**成为下属企业 |
| P16 | 细角色 | **以后再拆**；本期机构/企业各按一类账号理解 |
| P17 | 大师工作室 | **完全排除**出本模型 |

> 相对「组织层改造方案」旧 D1：企业默认不再限制为「仅审核」；默认能力上限由超管配置，企业可在上限内自运营。

## 三、目标与非目标

### 3.1 目标

1. 用统一 Scope 表达：超管 / 机构 / 企业三类身份的数据范围（含下属树 + 业务关联）。  
2. 支持企业自运营（本企业全流程）与机构代运营并存。  
3. 支持「机构配置企业功能」「超管配置机构与企业功能」「企业在上限内配子账号」。  
4. 用明确关联表（或等价）表达「培训需求选中 → 永久可查看」，且不强迫改组织树。  
5. 与现有 `sys_role` / 菜单 / 权限码兼容；本期不拆细角色种子包。

### 3.2 非目标

- 本期不做机构内/企业内细角色（管理员、跟班、审核员等）标准种子。  
- 不做多机构功能配置的自动冲突裁决。  
- 不纳入技能大师工作室。  
- 不重做班级五角色、不改 App 学员端身份模型。  
- 不在本方案展开具体菜单清单逐项勾选（另附配置清单迭代）。

## 四、目标模型

### 4.1 身份判定

```text
登录用户
  ├─ 是否 PLATFORM_ADMIN（超管） → 租户内全量数据 + 可配机构/企业功能
  └─ 所属组织 org
        ├─ 组织类型 = 企业（company） → 企业身份
        │     数据范围 = 本企业 orgId
        │     功能 = 超管（及关联机构）配置的上限 ∩ 本企业子账号权限
        └─ 其它（培训机构） → 机构身份
              数据范围 = 本机构 orgId
                ∪ 组织树下属全部企业
                ∪ 业务关联表中的企业（含独立企业、他机构下属企业）
              功能 = 超管配置的机构上限 ∩ 本机构账号权限
              可配置 = 下属企业 + 业务关联企业 的功能/角色包
```

说明：

- 本期「机构账号 / 企业账号」各一类；细角色以后映射为不同 `sys_role` 即可，**数据范围仍按组织身份**，不按细角色名。  
- `org_type=master` 不参与上表。

### 4.2 组织树 vs 业务关联（两套关系）

| 关系 | 载体 | 建立方式 | 效果 |
|------|------|----------|------|
| 树上下属 | `sys_org.parent_id`（或等价） | 机构创建企业账号时自动挂接；或超管手工挂树 | 机构默认可看该企业全部数据；机构默认可配其功能 |
| 业务关联 | 新建关联表（建议，见 §5） | 机构培训需求选中企业 | 永久：机构可看该企业全部数据；机构可配其功能；**不改 parent** |

同一企业可同时：挂在 A 下 + 被 B/C 业务关联。

### 4.3 功能配置分层

```text
超管给定「机构能力上限」「企业能力上限」（菜单/模块开关 + 可授角色包）
        ↓
机构在上限内：使用自身功能；为下属/关联企业裁剪功能与角色包
        ↓
企业管理员在「超管上限 ∩ 各机构已配结果」内：为本企业子账号分配权限
```

冲突策略（P13）：若 A、B 都对企业配了开关，**系统不自动合并裁决**；产品上先允许后写覆盖或并存展示「多方配置」，运维人工协调。实现阶段需在评审中二选一默认写策略（建议：**后写覆盖 + 审计日志**，避免运行时不确定），但**不做智能并集/交集**。

## 五、数据与接口（实现要点）

### 5.1 建议新增：机构–企业业务关联表

示例名：`train_org_enterprise_link`（最终以迁移为准）

| 字段 | 说明 |
|------|------|
| `id` / `tenant_id` / BaseEntity | 常规 |
| `org_id` | 机构组织 ID |
| `enterprise_id` | 企业组织 ID（`org_type=company`） |
| `source` | 来源：`demand`（培训需求）等 |
| `source_id` | 来源单据 ID（可空，历史兼容） |
| `status` | `active`（本期无自动失效；预留解除） |

约束：`(tenant_id, org_id, enterprise_id, deleted)` 唯一；幂等：需求再次选中不重复插。

**写入时机**：机构保存/提交培训需求且选中企业时 upsert。  
**不删除**：需求结束不删关联（P6）；若未来要「解除合作」，另做显式解除，不在本期。

### 5.2 主数据字段（延续组织层改造方案）

- 班级 / 培训信息等继续用 `company_id` 表达企业归属。  
- 机构隔离仍建议补 `training_org_id`（承办机构）；与本方案树上下属、业务关联一起参与 Scope。  
- 独立企业无上级时：`training_org_id` 可空；机构侧可见性靠关联表，不靠改挂 `parent_id`。

### 5.3 Scope 伪代码

```text
if 超管: return ALL

if 企业身份:
  return filter enterprise_id = user.orgId

if 机构身份:
  enterprises = 树下属企业(user.orgId)
             ∪ 关联表.active 中 enterprise_id where org_id = user.orgId
  return filter company_id/enterprise_id ∈ enterprises
         OR training_org_id = user.orgId
         （具体资源表字段按模块对齐）
```

写操作闸门：

- `requireTrainingOperator()`：超管 / 机构 / 企业（P10 自运营写）  
- `requireOrgOperator()`：仅机构 / 超管（如代建系统企业、改他企功能上限）  
- 数据边界仍配合 `assertClassAccessible` / `assertCompanyAccessible`

### 5.4 账号与组织 API 行为

| 操作 | 规则 |
|------|------|
| 超管建机构用户 | 用户 `org_id` → 机构组织 |
| 超管建企业用户 | 用户 `org_id` → 企业组织；企业可为独立节点 |
| 机构建企业用户 | 若企业组织不存在则创建，**parent=本机构**；用户挂该企业 |
| 企业建子账号 | 仅允许 `org_id=本企业`；不可改挂其它组织 |

### 5.5 功能配置存储（方向）

可选实现路径（评审定一条）：

1. **配置快照表**：`org_id`（被配置方）+ `configurer_org_id`（配置方，超管可用 0）+ 菜单码/权限码白名单 JSON；或  
2. **复用 sys_role**：为每个企业生成「企业运营包」角色，由机构/超管维护角色权限，再绑到企业用户。

本期细角色不做，优先 **路径 2 的一个默认企业角色 + 路径 1 的模块开关** 即可。

### 5.6 管理端入口（企业管理 + 开设账号）

**结论：放在现有「培训管理 → 支持保障 → 企业管理」扩展，不新开顶层菜单。**

| 项 | 口径 |
|----|------|
| 现网菜单位置 | 菜单码 `train_company`，页面 `EnterpriseManagePage` |
| 机构日常路径 | `支持保障 → 企业管理 → 选企业 → 开设账号 / 账号列表` |
| 创建企业 | 支持「创建企业时可同时开设首个账号」；机构操作时企业组织 **自动挂到本机构下**（P15） |
| 开设账号 | 强制 `org_id = 该企业`；机构仅能操作下属企业 + 业务关联企业 |
| 功能配置入口（M3） | 同页「功能配置 / 角色包」 |
| 超管 | 同一页可看全部企业 |
| 企业侧自管子账号 | 企业管理员在本企业视角开子账号；不可改挂其它组织；不可改本企功能上限 |

**明确不放：** 仅「系统管理 → 用户管理」；新建顶层「企业账号管理」；「企业审核 / 需求管理」混入口。

**前端落点：** `EnterpriseManagePage.tsx`；权限 `train:company:*` / `train:company:account`。

## 八、测试要点（抽样）

1. 下属企业：机构 A 可见；未关联的机构 B 不可见，直到 B 在需求中选中。  
2. 独立企业：仅本企 + 超管可见；A 需求选中后 A 可见且树仍独立；需求结束后 A 仍可见。  
3. 同一企业被 A、B 都选中：A、B 均可见全部。  
4. **企业自运营**：本企业可读写本企班级角色/花名册/开班准备；不可见其它企业。  
5. 企业建子账号：不能指定其它 `org_id`；不能改功能上限。  
6. 机构建企业：新企业 `parent` 为本机构。  
7. 大师工作室账号不走本 Scope 企业分支。  
8. 超管可见全部并可配企业功能。  
9. 企业管理页开户：`org_id` 必为该企业。  
10. （待做）创建企业并同时开户一步流。
