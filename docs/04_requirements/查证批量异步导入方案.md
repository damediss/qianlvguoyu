# 查证批量异步导入方案

> 目标：导入用户后自动触发批量查证，多线程并行执行，支持大数据量后台静默处理。

## 一、需求分析

### 1.1 当前痛点

| 痛点 | 说明 |
|---|---|
| 手动逐个查证 | Excel 导入 500 人后，前端需循环调 500 次 `/users/{id}/cert`，体验差 |
| 串行执行慢 | 单线程逐个查证，每轮约 2-5s（网络 IO），500 人需 1000-2500s（15-40 分钟） |
| 无进度反馈 | 用户不知道查证进行到哪了，是否失败 |
| 前后端强绑定 | 查证期间前端必须保持连接，断网/刷新则丢失进度 |

### 1.2 目标

| 目标 | 指标 |
|---|---|
| 自动触发 | 导入完成后自动开始查证，无需前端循环调用 |
| 并行加速 | ≥3 线程并行，500 人查证时间从 40min → ~7min |
| 后台静默 | 大数据量时前端可关闭页面，查证在后台继续 |
| 进度可查询 | 前端可实时查看：总数/已完成/失败/进度百分比 |
| 失败可重试 | 失败用户可单独重试，不影响已成功用户 |

## 三、数据库变更

### 3.1 新增表：chazheng_cert_batch（查证批次记录）

```sql
-- 文件: V20260713_001__add_cert_batch_tables.sql
CREATE TABLE IF NOT EXISTS chazheng_cert_batch (
  id BIGINT NOT NULL COMMENT '批次 ID（雪花 ID）',
  tenant_id BIGINT NOT NULL COMMENT '租户 ID',
  total_count INT NOT NULL DEFAULT 0 COMMENT '总用户数',
  completed_count INT NOT NULL DEFAULT 0 COMMENT '已完成数(原子 UPDATE 递增)',
  status VARCHAR(32) NOT NULL DEFAULT 'processing'
    COMMENT 'processing / completed / failed',
  source_filename VARCHAR(255) NULL COMMENT '导入的原始文件名(Excel),手动触发的批次为 NULL',
  trigger_by BIGINT NULL COMMENT '触发人用户 ID',
  triggered_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  completed_at DATETIME NULL,
  error_message TEXT NULL,
  deleted TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_chazheng_cert_batch_tenant (tenant_id, deleted, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='查证批次';
```

> **审核修订 v1.1 #4**：不再在 batch 表存 `success_count`/`failed_count`/`success_no_cert_count`，
> 这些计数从 `chazheng_cert_batch_item` 表实时聚合（`SELECT status, COUNT(*) GROUP BY status`），
> 避免并发更新计数器的竞态问题。`completed_count` 保留，因为它用原子 `UPDATE SET completed_count=completed_count+1` 递增。

### 关于 `source_filename` 的说明

| 场景 | `source_filename` 值 | 用途 |
|---|---|---|
| Excel 导入触发的查证 | 原始文件名（如 "2026年职业技能名单.xlsx"） | 用户可在批次列表中快速识别"这次查的是哪份名单" |
| 手动触发的查证（如勾选用户后点查证） | NULL | 非导入场景,无文件名 |

在前端批次列表中,可展示 `source_filename` 列,方便用户回溯历史导入记录。

### 3.2 新增表：chazheng_cert_batch_item（批次明细）

```sql
CREATE TABLE IF NOT EXISTS chazheng_cert_batch_item (
  id BIGINT NOT NULL COMMENT '明细 ID（雪花 ID）',
  batch_id BIGINT NOT NULL COMMENT '批次 ID',
  user_id BIGINT NOT NULL COMMENT '用户 ID',
  user_name VARCHAR(64) NULL COMMENT '用户姓名（冗余，便于排查）',
    status VARCHAR(32) NOT NULL DEFAULT 'pending'
    COMMENT 'pending / processing / success / success_no_cert / failed',
  retry_count INT NOT NULL DEFAULT 0 COMMENT '已重试次数',
  error_message VARCHAR(500) NULL,
  started_at DATETIME NULL,
  completed_at DATETIME NULL,
  deleted TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_batch_item_batch (batch_id, status),
  KEY idx_batch_item_user (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='查证明细';
```

### 3.3 旧批次清理策略（审核修订 v1.1 #11）

batch + batch_item 表会无限增长，需定期清理：

| 策略 | 说明 |
|---|---|
| 保留期限 | 已完成(completed)的批次保留 90 天 |
| 清理方式 | 定时任务（Spring `@Scheduled` 或 n8n）每天凌晨执行 |
| 清理逻辑 | `DELETE FROM chazheng_cert_batch_item WHERE batch_id IN (SELECT id FROM chazheng_cert_batch WHERE status='completed' AND completed_at < NOW() - INTERVAL 90 DAY)` + 同步删 batch |
| 软删优先 | 先设 `deleted=1`，7 天后物理删除 |

> 一期可不实现自动清理，但表设计预留了 `deleted` 字段。

### 4.2 CertCheckBatchService（新增）

```java
@Service
public class CertCheckBatchService {
    private final ChazhengUserMapper userMapper;
    private final ChazhengCertBatchMapper batchMapper;
    private final ChazhengCertBatchItemMapper itemMapper;
    private final ChazhengApplicationService certCheckService;
    private final ThreadPoolTaskExecutor executor;

    /**
     * 提交查证批次（前端调用）
     * 1. 创建批次记录
     * 2. 为每个待查证用户创建明细记录（status=pending）
     * 3. 提交到线程池异步执行
     * 4. 立即返回 batchId
     */
    public CertCheckBatchSubmitResp submit(Long tenantId, List<Long> userIds, Long triggerBy);

    /**
     * 查询批次进度（前端轮询）
     */
    public CertCheckBatchProgress progress(Long batchId);

    /**
     * 查询批次详细报告
     */
    public CertCheckBatchReport report(Long batchId);

    /**
     * 重试指定批次的失败用户
     */
    public CertCheckBatchSubmitResp retryFailed(Long batchId);
}
```

### 4.3 线程池配置

```java
@Bean("chazhengCertCheckExecutor")
public ThreadPoolTaskExecutor chazhengCertCheckExecutor(
    @Value("${chazheng.batch.core-pool-size:3}") int coreSize,
    @Value("${chazheng.batch.max-pool-size:5}") int maxSize,
    @Value("${chazheng.batch.queue-capacity:1000}") int queueCapacity) {

    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(coreSize);
    executor.setMaxPoolSize(maxSize);
    executor.setQueueCapacity(queueCapacity);
    executor.setThreadNamePrefix("cert-check-");
    // 队列满时由调用线程执行（降级为同步，避免任务丢失）
    executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    executor.setWaitForTasksToCompleteOnShutdown(true);
    executor.setAwaitTerminationSeconds(60);
    executor.initialize();
    return executor;
}
```

### 4.4 Worker 执行逻辑

```java
/**
 * 单个用户的查证 Worker（提交到线程池）
 */
private Runnable createCertCheckWorker(Long batchId, Long userId) {
    return () -> {
        itemMapper.updateStatus(userId, "processing", null);
        try {
            // 调用重构后的 certCheck 方法（非事务方法，内部自行编排）
            ChazhengUserVO vo = certCheckService.certCheck(userId.intValue());

            // 判断是否查到证
            boolean hasCert = vo.getIsCert() != null && vo.getIsCert() == 1;
            itemMapper.updateSuccess(userId, hasCert ? "success" : "success_no_cert");
            batchMapper.incrementCompleted(batchId, true);

        } catch (Exception e) {
            // 查证失败：记录错误 + 判断是否重试
            int retryCount = itemMapper.getRetryCount(userId);
            if (retryCount < maxRetry) {
                itemMapper.updateRetry(userId, e.getMessage());
                // 重新提交到线程池
                executor.submit(createCertCheckWorker(batchId, userId));
            } else {
                itemMapper.updateFailed(userId, e.getMessage());
                batchMapper.incrementCompleted(batchId, false);
            }
        }
    };
}
```

## 六、限流策略

### 6.1 线程池限流

| 参数 | 默认值 | 说明 |
|---|---|---|
| core-pool-size | 3 | 常驻线程数 |
| max-pool-size | 5 | 高峰可扩到 5 |
| queue-capacity | 1000 | 最多容纳 1000 待处理用户 |
| rejected-handler | CallerRunsPolicy | 队列满时调用线程自己执行（降级同步，不丢任务） |

### 6.2 API 请求限流（RateLimiter）

使用 Guava `RateLimiter` 限制每秒发往第三方接口的请求数：

```java
// 全局共享，所有 Worker 共用同一个限流器
private final RateLimiter rateLimiter = RateLimiter.create(
    chazhengConfig.getRateLimitPerSecond());  // 默认 10 QPS

private void callWithRateLimit(Runnable task) {
    rateLimiter.acquire();  // 阻塞等待令牌
    task.run();
}
```

目的：避免 5 个线程同时狂打第三方接口导致被封 IP。

### 7.2 状态机

```
批次状态：
  pending ──submit──► processing ──全部完成──► completed
                          │
                          └── 异常终止 ──────► failed

明细状态：
  pending ──分配线程──► processing ──查到证──► success
                          │                     └── 无证 ──► success_no_cert
                          │
                          └── 异常 ──未超retry──► retry_count+1 → 重新 processing
                                     │
                                     └── 超 retry ─────────► failed
```

## 八、前端集成建议

### 8.1 操作流

```
1. 用户上传 Excel → 导入
2. 导入成功 → 显示「导入 500 人成功，正在查证...」
3. 显示进度条（每 2 秒轮询 GET /progress）
4. 进度条下方显示实时数字：已完成 320/500 | 成功 300 | 失败 5
5. 完成后 → 显示汇总卡片 + 「查看报告」按钮
6. 用户可关闭页面 → 后台继续 → 下次打开可通过 batchId 继续查看
```

### 8.2 异常处理

| 场景 | 前端表现 |
|---|---|
| 查证进行中关闭页面 | 后台继续，不丢失 |
| 刷新页面 | 通过 batchId（localStorage 缓存）恢复进度 |
| 全部查证完成 | 显示报告，失败用户可勾选后「重试失败项」 |
| 第三方接口持续异常 | 进度条停滞，显示「查证异常，请稍后重试或联系管理员」 |

## 九、性能评估

### 9.1 耗时估算

| 用户数 | 单线程(串行) | 3 线程并行 | 5 线程并行 |
|---|---|---|---|
| 100 人 | ~3-8 min | ~1-3 min | ~1-2 min |
| 500 人 | ~15-40 min | ~5-14 min | ~3-8 min |
| 1000 人 | ~30-80 min | ~10-27 min | ~6-16 min |

> 假设每用户每轮查证耗时 2-5 秒，2 轮模板，含网络抖动。

### 9.2 资源消耗

| 资源 | 3 线程 | 5 线程 |
|---|---|---|
| DB 连接 | ≤5（连接池通常 20，安全） | ≤7 |
| 内存 | ~50 MB（队列 + 进度对象） | ~80 MB |
| 第三方 QPS | ≤10（限流器控制） | ≤10 |

## 十一、关键代码骨架

### 11.1 CertCheckBatchService 核心方法

```java
@Service
@Slf4j
public class CertCheckBatchService {

    private final ChazhengCertBatchMapper batchMapper;
    private final ChazhengCertBatchItemMapper itemMapper;
    private final ChazhengApplicationService certCheckService;
    private final ThreadPoolTaskExecutor executor;
    private final RateLimiter rateLimiter;

    @Value("${chazheng.batch.max-retry:2}")
    private int maxRetry;

    /**
     * 提交批次查证任务
     */
    public CertCheckBatchSubmitResp submit(Long tenantId, List<Long> userIds, Long triggerBy) {
        // 1. 生成批次 ID（雪花）
        long batchId = nextId();

        // 2. 创建 batch 记录
        CertCheckBatchEntity batch = new CertCheckBatchEntity();
        batch.setId(batchId);
        batch.setTenantId(tenantId);
        batch.setTotalCount(userIds.size());
        batch.setStatus("processing");
        batch.setTriggerBy(triggerBy);
        batchMapper.insert(batch);

        // 3. 为每个用户创建 item 记录
        for (Long userId : userIds) {
            ChazhengCertBatchItemEntity item = new ChazhengCertBatchItemEntity();
            item.setId(nextId());
            item.setBatchId(batchId);
            item.setUserId(userId);
            item.setStatus("pending");
            itemMapper.insert(item);
        }

        // 4. 提交到线程池（限流 + 异常隔离）
        for (Long userId : userIds) {
            executor.submit(() -> processOneUser(batchId, userId));
        }

        return new CertCheckBatchSubmitResp(batchId, userIds.size());
    }

    /**
     * 处理单个用户（Worker 执行体）
     */
    private void processOneUser(long batchId, Long userId) {
        // 审核修订 v1.1 #5：updateStatus 必须带 batchId，避免跨批次误更新
        itemMapper.updateStatus(batchId, userId, "processing", null);
        try {
            // 限流等待
            rateLimiter.acquire();

            // 审核修订 v1.1 #12：certCheck 接收 Integer，userId 是 Long
            // chazheng_user.id 是 Integer（自增），Long→intValue 安全
            ChazhengUserVO vo = certCheckService.certCheck(userId.intValue());

            boolean hasCert = vo.getIsCert() != null && vo.getIsCert() == 1;
            itemMapper.updateSuccess(batchId, userId, hasCert ? "success" : "success_no_cert");
            batchMapper.incrementCompleted(batchId);

        } catch (Exception e) {
            handleFailure(batchId, userId, e);
        } finally {
            // 检查批次是否完成
            checkBatchCompletion(batchId);
        }
    }

    /**
     * 失败处理（重试 or 标记失败）
     */
    private void handleFailure(long batchId, Long userId, Exception e) {
        int retryCount = itemMapper.incrementRetry(batchId, userId);
        if (retryCount <= maxRetry) {
            log.warn("查证失败，准备重试 batch={}, user={}, retry={}", batchId, userId, retryCount);
            executor.submit(() -> processOneUser(batchId, userId));
        } else {
            log.error("查证最终失败 batch={}, user={}", batchId, userId, e);
            itemMapper.updateFailed(batchId, userId, e.getMessage());
            batchMapper.incrementCompleted(batchId);
        }
    }

    /**
     * 检查批次是否全部完成（审核修订 v1.1 #1：原子 SQL 避免竞态）
     *
     * <p>原方案先 SELECT 再 UPDATE，并发线程可能读到旧 completedCount，
     * 导致批次永远卡在 processing。改为单条原子 SQL：
     * <pre>
     * UPDATE chazheng_cert_batch
     *   SET status='completed', completed_at=NOW()
     *   WHERE id=? AND completed_count >= total_count AND status='processing'
     * </pre>
     * 多个线程同时执行也只有一个能成功更新（其他因 WHERE 条件不满足而 0 行影响）。
     */
    private void checkBatchCompletion(long batchId) {
        batchMapper.markCompletedIfDone(batchId);
    }

    /**
     * 查询进度（审核修订 v1.1 #3：租户隔离 + #4：从 item 表聚合）
     */
    public CertCheckBatchProgress progress(Long batchId) {
        Long tenantId = SecurityContext.currentUser().getTenantId();
        CertCheckBatchEntity batch = batchMapper.selectById(batchId);
        // 审核修订 v1.1 #3：租户隔离校验
        if (batch == null || !batch.getTenantId().equals(tenantId)) {
            throw new BusinessException(ErrorCode.NOT_FOUND, "批次不存在或无权访问");
        }

        // 从 item 表聚合各状态计数（不用 batch 表的冗余计数）
        Map<String, Long> statusCounts = itemMapper.countByStatus(batchId);
        long success = statusCounts.getOrDefault("success", 0L);
        long successNoCert = statusCounts.getOrDefault("success_no_cert", 0L);
        long failed = statusCounts.getOrDefault("failed", 0L);
        long pending = statusCounts.getOrDefault("pending", 0L) + statusCounts.getOrDefault("processing", 0L);
        long completed = success + successNoCert + failed;

    }
}
```
