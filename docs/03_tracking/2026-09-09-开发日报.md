## 二、今日完成

### 1. 名单导入支持同一选手多工种

- 导入模板固定为：企业名称、姓名、身份证号、手机号、报名工种、报名等级。不再先在页面选择参赛企业或工种，按行匹配企业、身份、工种和等级。
- 同一选手可在文件中占多行报名不同工种；同一赛事内同一选手同一工种仍只能有一条有效报名。
- 批次上的企业/工种选择改为可空；名单行落 `org_id`、`org_name`、`event_work_type_id`、`event_work_type_level_id`、`source_row_no`。
- 选手管理、报名查询、赛段分卷名单同步按工种维度展示，不再把一名选手压成单行单工种。
- 报名确认仍先做赛事时间冲突校验，冲突则整批不插入。

### 2. 停用选手工号，改为身份主键

- 新增、编辑、查询和名单导入不再提供员工编号；选手以身份证号、手机号匹配已有 `player_id`，报名记录以 `player_id` 为选手主键。
- `employee_no`、名单行 `org_code` 列暂保留且改为可空，仅兼容历史数据和外部报表；新代码不读、不写。
- 去掉名单行按员工编号去重的唯一约束，避免同一人报第二工种被拒。
- 文档：`docs/04_requirements/competition-player-registration-employee-no-and-time-conflict.md`；基础合同与激活契约已指向该口径。

### 3. 理论比赛独立控制台

- 新增菜单 `competition_formal_exam`（理论比赛控制台），路径 `/competition/formal-exam`，挂在竞赛管理根菜单下，与赛事创建同级。
- 开考相关权限从赛事创建菜单迁到该入口：`view` / `prepare` / `start` / `force-submit` / `score`。
- 控制台按赛段选择运行实例，支持准备开考、查看场次和考生名单；赛事模块页与选手分卷页补了入口衔接。
- 已有 `competition:exam-session:view` 的角色自动获得该菜单。

### 4. 正式比赛账号清退

- 接口：`POST /api/competition/formal-exam-sessions/{sessionId}/candidates/{candidateExamId}/force-offline`。
- 权限：`competition:exam-session:force-offline`，写入权限表并授予平台管理员及已有开考/强制交卷/理论监考清退角色。
- 行为：只踢掉该选手考试 Sa-Token，平板回到登录页；**不交卷、不改答题状态、不作废已答题目**。未绑定 `player_id` 时拒绝。
- 管理端场次面板增加「清退」确认框，文案与上述语义一致。
- 登录仍是选手级 `maxLoginCount=1`，尚未绑定场次或设备；AccessSession / WebSocket 明确留到后续阶段。

### 5. 正式考试热路径优化（Phase 0 / Phase 1）

Phase 0 先核对审计与源码，补可观测性和干跑压测脚本，不宣称容量数字。Phase 1 落地四项 P0：

- **答题批量同步**：`syncAnswers` 改为单事务、一次场次解析、题目/答案 IN 加载；逐题 ACK；`answeredCount` 最多刷新一次。去掉每题 `REQUIRES_NEW`。业务拒绝按题返回，硬库错误仍整批回滚。
- **轻量状态轮询**：新增 `GET /competition/formal-exam/player/sessions/{id}/status`。选手端先拉一次 context，再带抖动轮询 status；已交/自动交/强制交/缺考以及场次结束/取消后停止轮询。Token 桥增加 3 秒 Caffeine 选手缓存（key 仅 `tenantId:playerId`）。前台恢复统一走 `subscribeFormalExamRecovery`。
- **管理端查询**：场次人数用 SQL `GROUP BY`；`submittedTotal` 取在考终态实时人数，不再用准备时写死的 0。考生分页只加载当前页成绩。面板用父级 `initialData` + `staleTime`，避免打开时重复 `getById`。
- **到期收卷认领**：场次增加 `deadline_at`、`expire_claim_until`、`expire_claim_owner`。调度先认领再收卷；待进入选手批量记缺考；在考选手分块自动交卷；评分仍走独立评分调度。收卷线程池 `AbortPolicy`，Worker 自行 `TenantContextHolder.set/clear`。

可观测性：`FormalExamSqlProbe`、MyBatis SQL 计数拦截、Micrometer（operation/outcome/sql_bucket/phase，无 PII），Actuator 暴露 `metrics`。压测脚本：`scripts/formal-exam-load/run.mjs`，默认 dry-run，`--live` 只探健康检查。

报告：`outputs/competition-formal-exam-phase0-report-20260909.md`、`outputs/competition-formal-exam-phase1-report-20260909.md`；架构审计见 `outputs/competition-formal-exam-realtime-architecture-audit-20260909.md`。

## 五、风险与遗留

- 未提交改动已覆盖 9 月 4、7、8、9 四天主干，体积大。需评审后分提交或一次完整提交，避免把 `dist`、测试报告和本地文件带入仓库。
- `V20260909_001/002` 为 Java 迁移，`003`～`005` 为 SQL；部署前必须核对目标库最大 version，避免与库内已有 `20260909` 版本冲突。`001` 与 `002` 都可能删除工号唯一索引，重复执行依赖 Java 迁移的存在性判断，空库顺序需实跑确认。
- 权限刷新依赖重新登录；控制台菜单和清退权限只改库不够，目标库需核对 `sys_menu`、`sys_permission`、`sys_role_permission`、`sys_role_menu`。
- 批量同步改为单事务后，中途硬库错误会回滚整批；与昨日「逐题提交成功即落库」语义不同，选手端需依赖逐题 ACK 重试。
- 选手状态缓存最多滞后 3 秒；清退仍立即踢 Token，但缓存窗口内个别读路径可能短暂看到旧身份。
- 清退不结束答卷。被清退后若持有同一账号再次登录，仍可能回到原考试状态，产品需确认这是否就是预期。
- 到期扫描认领依赖 `deadline_at`；未跑迁移的库上调度行为与昨日 `TIMESTAMPADD` 扫描不一致。
- 评分仍只覆盖客观题；正式考试绑定实操快照会失败。选手端入口仍靠 URL 带 `sessionId`，控制台尚未提供复制链接/二维码。
- 旧理论监考（`CompetitionTheoryAttempt`）与新正式考试两套并存，今日明确不迁移旧数据，重叠页面待产品确认后再下线。
