## 二、本任务目标

在 `services/platform-api` 的 `com.guoyu.platform.competition` 领域内建立后续理论判分、实操裁判流程、成绩汇总与排名所依赖的数据底座和纯业务计算内核。

本任务只完成“领域模型、持久化结构、Mapper/Repository 边界、纯业务规则和自动化测试”，不做管理端页面，不做完整 Controller/API，不做线上考试会话，也不接入外部系统。

实现后应具备以下基础能力：

1. 可引用并校验 `COMP-SCORE-01` 已发布的赛事、赛段、赛事工种维度赛制 B 规则版本，不重复建立规则表。
2. 可版本化保存理论、仿真、实操三类成绩来源及其确认状态，不覆盖历史成绩。
3. 可表达竞赛裁判的正式/备用身份、选手禁评关系、实操评分版本以及解锁申请历史。
4. 可保存总分计算快照、排名快照及排名条目，为后续 API 和页面提供不可变数据基础。
5. 纯领域服务可正确执行：
   - 多选题答案集合完全一致判分。
   - 固定 3 名有效裁判实操分平均计算。

   - “1334”竞赛排名名次分配。
   - 缺考选手展示但不进入排名池。

## 三、冻结业务规则

### 1. 理论题

- 理论满分为 100 分。
- 90 分钟模板：单选 60 题×1 分、多选 20 题×1 分、判断 40 题×0.5 分。
- 120 分钟模板：单选 120 题×0.5 分、多选 20 题×1 分、判断 40 题×0.5 分。
- 单选题、判断题按标准答案完全匹配判分。
- 多选题只在“选手答案集合 = 标准答案集合”时取得该题全部分值。
- 多选题漏选、错选或多选均得 0 分；无部分分、无倒扣分。
- 多选选项的提交顺序不影响结果。
- 标准答案和判分只能在服务端执行，不得放入选手端投影。
- 本任务只实现纯判分函数和测试，不实现试卷生成、答题会话、保存答案、自动交卷或选手端接口。

### 2. 实操评分

- 每名选手必须有且仅有 3 名有效裁判评分。
- 仅已锁定、未回避、未作废的当前有效版本进入平均分。
- `实操得分 = (裁判1 + 裁判2 + 裁判3) ÷ 3`，结果按 `HALF_UP` 保留 2 位小数。
- 少于或多于 3 个有效分时不得产生正式实操成绩，应返回“待确认/裁判未齐”的领域结果，不能用 0 补齐。
- 裁判缺评、回避、退出或无法完成解锁重评时，由已绑定的现场备用裁判替换；替换关系、原因和历史评分必须可追溯。
- 裁判提交后评分锁定，不允许原地修改。
- 主裁判长只能发起解锁申请并填写原因；系统管理员批准后创建新修订版本，旧版本保留。
- 禁评关系命中时，后续应用层必须阻止该裁判查看、保存和提交对应选手评分。本任务需提供可持久化的数据约束和领域校验能力。
- 不修改认定模块现有的评分业务规则，不把竞赛数据直接写入 `certification_*` 表。通过清晰的竞赛适配边界为后续复用认定能力留口。

### 3. 赛制 B 总分

```text
仿真实操组合分 = (仿真得分 + 实操得分) ÷ 2

总分 = 理论得分 × 理论权重
     + 仿真实操组合分 × 仿真实操组合权重

理论权重 + 仿真实操组合权重 = 100%
```

- 理论、仿真、实操输入均为 0–100 分。
- 两项权重均为 0–100，且合计必须为 100。
- 使用 `BigDecimal`，禁止使用 `double/float` 参与分值和权重计算。
- 本任务不擅自增加最终展示取整规则。内部计算保留足够精度；实操平均分按已冻结规则保留 2 位。若持久化需要 scale，选择不会提前截断有效计算值的精度，并在实施报告说明。
- 仿真接口本期不开发，但数据模型允许未来写入已确认的仿真成绩来源。
- 任一必需成绩来源未确认时，不得生成“已确认”总分。
- 当前只实现赛制 B；不要根据不完整描述自行实现赛制 A。

### 4. 排名

- 按赛事、赛段、工种、规则版本独立排名，不分组、不跨工种比较。
- 缺考选手记 0 分并保留在输出数据中，但不参与排名、不占名次。
- “1334”占位法：若两人并列第 1，下一人是第 3；若两人并列第 3，下一人是第 5。
- 本任务实现一个接收“已经按业务排序键排好序的正常完赛记录”的纯排名函数，只负责相等键的并列判断与竞赛名次分配。
- `competition-scoring-rule-contract.md` 中赛制 A/B 的具体二级排序字段仍留有业务确认文字，本任务不得擅自把某套未完全冻结的排序键固化到数据库查询或 Controller。
- 排名结果必须能够保存为不可变快照；重算生成新版本，不能覆盖旧快照。

## 四、数据模型要求

先检查现有表和实体，再设计最小且完整的数据模型。至少覆盖以下业务概念；可以按项目既有命名规范调整表名，但不得遗漏语义：

1. 竞赛成绩规则版本引用：
   - 复用 `COMP-SCORE-01` 已创建的规则版本实体和表，不得创建第二套评分规则。
   - 本任务的成绩来源、计算快照和排名快照必须引用其已发布版本 ID，并通过成绩域就绪检查确认赛事、赛段、赛事工种和规则范围一致。
2. 成绩来源/成绩修订：
   - 选手、来源类型（理论/仿真/实操）、原始分、确认状态、来源引用、规则版本、修订号、是否当前有效。
   - 新修订不得覆盖旧修订。
3. 裁判分配与禁评：
   - 赛事/赛段/工种、裁判成员、正式或备用、选手范围。
   - 裁判—选手禁评关系、关系类型、原因、配置人和状态。
4. 实操评分：
   - 选手、裁判、评分细则版本引用、修订号、状态、总分、提交/锁定时间、替换来源及原因。
   - 解锁申请、申请原因、申请人、审批人、审批结果和审批时间。
   - 本任务不复制认定模块所有评分项表；需要保留可追溯来源引用和竞赛修订关系。
5. 总分计算快照：
   - 选手、三类来源版本、权重、计算过程所需数值、结果、规则版本、计算版本和确认状态。
6. 排名快照与排名条目：
   - 快照范围、规则版本、快照版本、状态、生成时间。
   - 选手、总分计算版本、显示名次、并列键/并列标识、选手状态。

数据库必须满足：

- MySQL 8.4，主键 `BIGINT`。
- 每个业务实体继承 `BaseEntity`，每张业务表完整包含 `id、tenant_id、deleted、created_by、updated_by、created_at、updated_at`。
- 使用 `DECIMAL` 保存分值和权重，不使用浮点列。
- 对版本、当前有效记录、同一裁判同一选手当前评分、排名快照条目等关键不变量建立必要唯一约束和索引。
- 多租户通过 MyBatis-Plus 插件处理，不在普通业务查询中手拼 `tenant_id`。
- 不修改任何已经存在或已经应用的 Flyway 文件，只新增迁移。
- 迁移中的注释、检查约束、索引和唯一约束应能够表达核心不变量。
- 不为 P0-05 奖项比例、P0-07 公示仲裁/撤销重排、P0-08 仿真回调创建超前业务表；仿真只作为成绩来源枚举和未来来源引用保留。

## 五、代码结构要求

按项目既有分层落在 `com.guoyu.platform.competition` 下：

- `entity/`：数据库实体，不直接暴露给前端。
- `mapper/`：MyBatis-Plus Mapper；返回值使用前做 null 检查。
- `enums/` 或明确的领域类型：规则、来源、状态等，禁止散落魔法字符串。
- `domain/` 或符合现有结构的领域服务：
  - 理论客观题判分器。
  - 三裁判平均分计算器。
  - 赛制 B 总分计算器。
  - 1334 排名分配器。
  - 回避/禁评与评分状态转换校验。
- 如需要 Repository/Service，只实现支撑数据底座所需的最小边界，不提前实现整套 Controller。

领域算法应尽量保持纯函数，便于独立单测；状态转换必须显式拒绝非法路径，例如：

- 已锁定评分直接修改。
- 裁判自行解锁。
- 未批准解锁就创建有效重评分。
- 回避裁判成为有效评分。
- 非 3 个有效裁判分生成正式实操成绩。
- 权重不等于 100 或分值超出 0–100。
- 缺失已确认来源却生成已确认总分。

## 六、测试与验证
