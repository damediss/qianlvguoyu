# 正式比赛并发容量压测执行提示词

## 使用说明

将下方“Agent 执行提示词”完整复制给负责实施的 Agent。任务要求先建设隔离压测能力，再执行 10、100、500、1000、3000 级压测并形成可复核报告。未满足隔离门禁时，只允许完成工具与环境建设，不允许发送大规模写流量。

## 可行性结论

当前方案可执行，但现有仓库尚不具备直接证明 3000 台 Pad 容量的能力：

1. 本机已有 Docker 29.6.2 和 Docker Compose 5.3.1，可以建设独立 MySQL、Redis、RabbitMQ、双 API 节点和反向代理。
2. 本机 Node.js 为 18.20.8，提供 `fetch`，但没有原生 `WebSocket`；压测端必须引入局部 `ws` 依赖、采用容器化 k6/Artillery，或实现等价 WebSocket 客户端，不能把“未尝试建连”记为成功。
3. 现有 `scripts/formal-exam-load/run.mjs` 的 `--scenario/--pads` 主要输出规划；`liveExam` 实际只登录一个账号并建立最多一个 WebSocket，不能形成 N 个并发用户。
4. 当前 `--write-answers` 不会执行答案写入；需要实现正常答题、离线积压、批量同步和提交状态机。
5. 现有 metrics 模式查询 `hikaricp.*`，但业务池是 Druid。应先读取 `/actuator/metrics` 清单，再采集实际存在的 `jdbc.connections.*`、Druid 指标以及正式考试自定义指标。
6. 当前大流量保护只检查 API base URL。即使 base URL 是 localhost，后端仍可能连接共享数据库，因此保护不足。压测编排必须验证后端 JDBC URL 和数据库 schema，明确拒绝 `43.138.163.7`、`gjjddb2026`、`gjjddbpro`。
7. c017 只有 2 名考生，只能作为功能基线；禁止把 c017 或共享测试库用于容量压测。

## 优先修改意见

### P0：压测前必须完成

1. 新增隔离压测 Compose 环境，并使用专用 schema，例如 `gjjddb_load`。
2. 增加双重安全确认：环境变量显式授权 + JDBC/schema 白名单；任何一项不通过立即终止写压测。
3. 把压测器改为真正的 N 用户状态机，每个用户使用独立账号、deviceId、token、AccessSession 和 WebSocket。
4. 为 Node 18 增加局部 WebSocket 实现；依赖只放在 `scripts/formal-exam-load/`，不污染管理端依赖。
5. 实现答案写入、版本递增、提交、离线 20 题恢复、统一截止和结果对账。
6. 修正指标采集，增加 WS 活跃连接、Outbox pending/oldest age、调度延迟、评分积压和 Druid 活跃/等待指标。

### P1：基线后按证据优化

1. `submitted_total` 与 CandidateExam 实际状态必须统一口径：要么事务内原子更新，要么明确废弃聚合字段，监控和收尾统一以候选人状态聚合为准。
2. `force_offline` 要区分 issued、delivered、acked、expired；AccessSession 已 kicked 不能替代设备 ACK。
3. WebSocket Hub 应按 `examSessionId/accessSessionId` 建索引，避免每次事件扫描全部本机连接；发送应使用有界、非阻塞队列。
4. Outbox 的序号生成不要依赖并发不安全的 `MAX(seq)+1`；认领需有租约/超时恢复，失败需指数退避，消费端按 eventId/seq 幂等。
5. 评分当前按候选人串行执行，应在真实基线后评估改为有界并发任务；必须保留幂等、租户上下文参数传递和 `AbortPolicy`。
6. Druid `max-active=20` 不应直接拍脑袋调大。使用 `所需连接数 ≈ 峰值 SQL 请求率 × 平均持有连接时间 × 安全系数` 估算，并受 MySQL 总连接上限约束。
7. 明确场次结束语义：继续坚持“到截止时间才结束”，或新增带审计的“全部终态后人工结束场次”；不能让运营认为选手提交完毕等于评分已开始。

## 五、把压测器改成真实并发状态机

保留现有 dry-run 能力，新增或重构 live runner。Node.js 18 没有全局 WebSocket，因此在 `scripts/formal-exam-load/` 内增加局部 `ws` 依赖，或使用经验证的等价方案。

每个虚拟 Pad 执行：

```text
login
  -> context
  -> realtime ticket
  -> WebSocket connect
  -> application heartbeat every 20s
  -> status poll with 60-120s full jitter while WS connected
  -> answer sync with independent answerVersion
  -> submit or wait for unified deadline
  -> receive status/control event and send ACK when required
  -> final HTTP reconcile
```

必须实现：

1. `--pads N` 真正创建 N 个独立虚拟用户，禁止复用同一 token 模拟 N 台设备。
2. 支持 `--ramp-sec`、`--duration-sec`、`--scenario`、`--shard-index`、`--shard-count`、`--seed`。
3. 支持多个压测进程分片，聚合结果时去重。
4. 正常答题：每个 Pad 平均每 10 秒产生一次答案变更，使用 1～3 条小批次同步。
5. 离线恢复：暂停同步 5 分钟，累积 20 条，再用 0～30 秒 full jitter 恢复，一台 Pad 发送一个 20-item sync 事务。
6. 统一截止：让候选人保持 running，由服务端自动交卷，不允许压测端伪造数据库终态。
7. 正常提交、重复提交、版本冲突、重复登录、旧 generation、晚到 ACK 分成独立场景。
8. WebSocket 收发统计必须是真实 socket 数，不得用计划值代替。
9. 每个请求记录 operation、status、latency、error category；不记录 token、账号密码和答案正文。
10. runner CPU 或 event-loop lag 过高时标记“压测端瓶颈”，不能把它误判成服务端容量上限。

## 六、实际执行矩阵

先单节点，再双节点；每一级通过后才升压：

| 阶段 | Pad | Console | 时长 | 目的 |
|---|---:|---:|---:|---|
| smoke | 10 | 1 | 5 min | 验证脚本、答案、WS、对账 |
| L1 | 100 | 1 | 10 min | 建立基线 |
| L2 | 500 | 5 | 15 min | 发现连接池和 SQL 放大 |
| L3 | 1000 | 5 | 20 min | 验证稳定状态 |
| L4 | 3000 | 10 | 30 min | 目标容量门禁 |
| soak | 1000 或最大稳定档 | 5 | 2 h | 内存、连接、Outbox 泄漏 |

每个容量档至少执行：

1. 登录/入场 ramp，不同时瞬时登录。
2. 3000 WS 稳态和 20 秒 heartbeat。
3. 每 Pad 10 秒一次答案变更。
4. 5 分钟离线后 20 题恢复。
5. 统一截止自动交卷。
6. 最终评分和数据对账。

故障场景单独执行：

1. 双节点运行时滚动重启 api-1，再重启 api-2。
2. Redis 停止 30 秒后恢复，验证 HTTP 答案链仍可用、ticket/WS 明确降级、恢复后重新取 ticket。
3. 测试跨节点 Outbox + Redis Pub/Sub 投递。
4. RabbitMQ 停止只观察平台共存影响，不把它误认为正式考试实时主链故障。
5. 重复登录、旧 token/generation、重复 ACK 和延迟 ACK。

禁止直接从 10 跳到 3000。某一级出现持续 5xx、连接池等待、数据库锁阻塞、Outbox dropped、数据丢失或压测端饱和时，停止升压并保存证据。

## 七、采集指标

### 压测端

- 每个 operation 的请求数、吞吐、错误率
- p50、p95、p99、max
- WS attempted/opened/active/closed/reconnected
- WS 建连和重连延迟
- heartbeat、command、ACK、seq gap、duplicate
- runner CPU、内存、event-loop lag、网络吞吐

### platform-api/JVM

- CPU、RSS、heap/non-heap、线程数、GC pause
- `http.server.requests`
- `formal_exam.http`、`formal_exam.http.count`、`formal_exam.sql.count`
- `formal_exam.sync.*`、`formal_exam.finalize.*`、`formal_exam.ws`
- WS 当前连接数、发送队列丢弃数
- Outbox pending、publishing、dropped、oldest pending age、dispatch latency
- 自动交卷 backlog、claim 竞争、最后一名完成时间
- 评分 backlog、耗时、失败数

### 数据库和连接池

- 先请求 `/actuator/metrics`，发现实际 Druid/JDBC meter 名；禁止继续写死 `hikaricp.*`
- Druid/JDBC active、idle、max、pending/wait
- MySQL Threads_connected、Threads_running、QPS/TPS
- slow query、lock wait、deadlock、buffer pool 命中
- 关键 SQL 的次数和 p95/p99

### Redis/RabbitMQ

- Redis ops/sec、latency、connected clients、blocked clients、内存、Pub/Sub 数量
- ticket/presence 数量只统计 key 数，不读取 token 值
- RabbitMQ messages_ready、messages_unacknowledged、consumer 数和发布确认延迟

采样间隔建议 1～5 秒。保存机器时间、应用时间和数据库时间，确认时钟偏差。

## 八、建议的初始验收线

以下是没有正式业务 SLA 时的临时门槛，必须在报告中标为“建议值”，不能冒充既有合同：

1. 非故障注入阶段 HTTP 5xx/error rate < 0.1%。
2. status/context：p95 ≤ 500 ms，p99 ≤ 1500 ms。
3. answer sync：p95 ≤ 1000 ms，p99 ≤ 2500 ms。
4. submit：p95 ≤ 1500 ms，p99 ≤ 3000 ms。
5. WS 建连成功率 ≥ 99.5%，重连 p95 ≤ 10 秒。
6. Outbox dropped = 0；负载停止后 pending 在 30 秒内清零；允许 at-least-once 重复，但重复必须被幂等处理，最终不得有未修复 seq gap。
7. 答案丢失 = 0；最终数据库答案与虚拟客户端最后确认版本完全一致。
8. 统一截止后 3000 名候选人在 60 秒内全部进入终态，场次随后完成；评分完成目标先暂定 5 分钟，并报告实际分布。
9. JVM 无 OOM、无持续 Full GC；CPU、heap 和连接池不持续超过 80%。
10. MySQL 无死锁、无持续锁等待，连接数和 Threads_running 在负载结束后恢复基线。
11. 压测端自身 CPU、内存、event-loop lag 未饱和，否则该轮结果无效。

## 九、数据正确性对账

每轮结束后自动生成对账结果，至少检查：

1. 期望考生数与 CandidateExam 数相等。
2. 客户端最后 ACK 的 answerVersion 与数据库当前版本一致。
3. 一个 CandidateExam + question_snapshot 只有一条有效答案。
4. terminal 候选人数量与 submitted/auto/forced/absent 分布一致。
5. `submitted_total` 与候选人聚合不一致时必须单独报告。
6. Outbox event_id 无冲突，dropped=0；记录重复投递和 seq gap。
7. AccessSession active/kicked/expired 与命令 ACK 状态一致；issued 未 ACK 要列明。
8. finished 场次必须有 actual_end_time；scoring completed 必须有完整 CandidateResult 和逐题得分。
9. 故障恢复后再次执行 HTTP snapshot reconcile，确保 Redis/WS 不作为业务事实源。

## 十、实施纪律

1. 基线压测完成前，不修改生产业务算法来“美化数据”。允许补压测工具、隔离配置和缺失的无 PII 指标。
2. 如果基线失败，先用指标定位一个主瓶颈，再提出最小修改；修复前后使用同一 seed 和同一场景复测。
3. 涉及异步线程的修改必须显式传入 tenantId/userId，并在 Worker 中 `TenantContextHolder.set`，finally clear；不得访问 SecurityContext。
4. 线程池拒绝策略必须是 AbortPolicy，队列满应返回可观测错误，不能退化到 HTTP 调用线程执行。
5. 不修改已应用 Flyway；需要压测专用表/数据时放在压测环境 seed 中。
