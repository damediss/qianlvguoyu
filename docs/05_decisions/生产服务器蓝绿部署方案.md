## 1. 目标与范围

- **目标**：platform-api 发布零停机；回滚约 1 分钟（启动旧色目录中的上一版 jar + 切流，无需重新构建）
- **范围**：`platform-api`（Java 后端）+ `admin-web`（前端静态资源）；**不含** PHP 老系统（114 服务器，独立部署）与 RENCAI Python 服务（单实例，不参与蓝绿）
- **适用性判定（每次发布前，脚本自动执行）**：本次变更若含**列级破坏迁移**（删列、改列类型、重命名列）或**加严约束**（如新增 UNIQUE）→ **本次不走蓝绿**，按原停机窗口流程发布（复用现有 `/opt/guoyu-platform/deploy.sh` 或对 `guoyu-platform-api.service` 停机替换）；`DROP TABLE`/`DROP INDEX` 不在拦截范围（放行，前提与完整清单见 §6.4）；纯增量迁移（加表/加列/加索引）或无迁移 → 走蓝绿

## 3. 蓝绿架构设计

```
                          ┌─ 当值色（Blue）─ systemd guoyu-platform-api@blue  → 127.0.0.1:8080
nginx :80(反代 /api/) ────┤
      :5173(前端 SPA)      └─ 备用色（Green）─ systemd guoyu-platform-api@green → 127.0.0.1:8081
前端静态: /opt/guoyu-platform/web/{blue,green}/（nginx 5173 root 随色切换）
状态文件: /opt/guoyu-platform/CURRENT_COLOR（blue|green，防切错方向的唯一事实源）
```

- **角色定义**：`当值色` = 接收生产流量的实例；`备用色` = 接收新版本部署与验证的实例。发布 = 备用色升级 → 验证 → 切流 → **立即停旧色** → 角色互换
- **停旧色时机（已拍板）**：**新版本启动成功（健康检查 + 业务冒烟通过）并完成切流后，立即优雅停止旧色**——不设观察期。双实例并存窗口仅为发布过程本身（数分钟），JVM 显式 `-Xms512m -Xmx1g` 下并存峰值可控（§4）
- **回滚语义（与"立即停旧色"配套）**：
  - 旧色实例停止后，其目录中的**上一版 jar 原样保留**——回滚 = 启动旧色实例（30~60s）+ 切流，**约 1 分钟**完成（非秒级，但无需重新构建）
  - 部署脚本覆盖备用色前自动把其现有 jar 备份为 `previous.jar`（保留 1 份）——为连续发布场景提供 N-2 深度兜底
  - 前提不变：走蓝绿的发布，迁移必须对旧代码向后兼容（expand 阶段），切回旧版后旧代码在新 schema 上正常运行

## 4. 内存规划（8GB，**显式限制是硬要求**）

双实例并存窗口仅为发布过程本身（启动验证到停旧色，约 3~5 分钟）。

**关键事实**：现有单元**未配置 JVM 内存参数**，默认最大堆 ≈ 物理内存 1/4 ≈ 2GB——若蓝绿单元照搬现状（不显式限制），双实例峰值保守测算 2 × ~2.3G ≈ **4.6G**，仍 < 8GB 但余量收窄且不可控。**因此 6.1 的新单元必须显式 `-Xms512m -Xmx1g`**，在此基础上：

| 组件 | 预估占用 |
|---|---|
| MySQL 8.4 | ~2.0G |
| 双 JVM 短暂并存（发布窗口，显式 1g 堆） | 2 × ~1.3G ≈ **2.6G（峰值，仅数分钟）** |
| Redis | ~0.2G |
| RENCAI Python | ~0.5G（按现状实测校正） |
| OS + nginx + 常态余量 | ~2.7G |

常态（单 JVM）≈ 4.7G；发布窗口峰值 ≈ 6G < 8G，**可行且余量充足**。首演练 `free -h` 实测校准。

## 7. 标准发布流程（蓝绿模式）

**发布前判定（脚本内置）**：扫描本次新增 `db/migration/*.sql`，命中破坏性关键字（`DROP COLUMN`/`CHANGE COLUMN`/`RENAME` 等）→ 拒绝蓝绿，走停机窗口（复用现有 `/opt/guoyu-platform/deploy.sh`，或对 `guoyu-platform-api.service` 停机替换），本流程终止。

1. 备用色目录存在旧 jar → 脚本自动备份为 `previous.jar`（N-2 兜底，当次发布不触碰当值色目录文件）
2. 构建 jar + 前端 dist，分发到**备用色**目录
3. `systemctl start guoyu-platform-api@<备用色>`——**此刻 Flyway 在共享库执行新迁移**（独立直连，非破坏性前提下对当值色与 PHP 兼容）
4. 健康检查通过（`http://127.0.0.1:<备用端口>/api/actuator/health`）后执行业务冒烟（直连备用色端口，不经过 nginx）
5. 切流：改 `guoyu-platform.conf` 中 upstream server 行与 5173 前端 root（脚本一并改写）→ `/usr/local/nginx/sbin/nginx -t && -s reload`——新流量进入备用色；**存量连接（WS）在旧色**，由客户端重连收敛到新当值色（依赖 5.6）
6. **立即优雅停止旧色**（graceful 排空 ≤30s，`TimeoutStopSec=45` 兜底；存量 WS 由客户端重连收敛）→ `CURRENT_COLOR` 翻转 → 发布完成
7. 一天内可立即开始下一次发布（旧色已停，目录直接复用）

**高频发布（一天多次）的语义**：旧色每次发布后即停止，**回滚 = 冷启动旧色目录中的上一版 jar + 切流，约 1 分钟**；连续发布覆盖 N-1 后，N-2 走 `previous.jar` 恢复（同为分钟级）。只要 expand-contract 规范成立，回滚代码兼容当天已累积的全部迁移（均为非破坏性增量），无需额外动作。

**回滚边界（重要）**：回滚只回滚**代码**，**迁移不回滚**——这正是"破坏性变更不走蓝绿"决策的原因：走蓝绿的发布，其迁移必须对旧代码向后兼容，切回旧版后旧代码在新 schema 上继续正常工作（expand 阶段的加列对旧代码无感知）。

## 10. 实施建议

1. **时机**：数据库合并（gjjddbpro）稳定之后再上蓝绿——两个大变更不叠加
2. **顺序**：先落 SaaS 侧小改（5.1/5.2 随常规发版）→ 确认 WS 重连（5.6，硬前提）→ 服务器端一次性改造（§6）→ **测试环境演练 ≥3 次**（含一次人为故障走 6.7 回滚、一次一天内连续两次发布的高频场景）→ 生产首切选低风险版本
3. **风险接受确认**：回滚为分钟级冷启动（约 1 分钟）、切流后即停旧色无观察期——按 2026-08-30 需求方决策执行；若某次发布风险度高（大功能/大重构），可临时手动延长旧色存活（不启动即可，脚本不强制）
