# 千铝工投云平台与智能体开发部数据库设计与变更管理制度

制度编号：QLGT-YFGL-2026-105　　版本：V1.1　　发布日期：2026-10-16

## 第一章　总则

**第一条**　为规范表结构设计、Flyway 迁移与数据字典维护，防止数据库变更事故，特制定本制度。数据库变更为本项目历史踩坑集中区，本制度的每条规则均来自真实事故或踩坑记录，执行中不得变通。本制度遵循部门制度“简洁、可测试、可维护、持续迭代”的共同标准。

**第二条**　本制度适用于全部系统的数据库设计与变更，包括 SaaS 平台 MySQL 库、PHP 存量库及私有化环境数据库。

## 第二章　表结构设计规范

**第三条**　主键统一使用雪花 ID，类型 BIGINT；列名统一 snake_case，与 Java 命名策略对齐。

**第四条**　业务主表必须包含审计字段六列：tenant_id、deleted、created_by、updated_by、created_at、updated_at，且与后端实体基类字段一一对应；新增或修改表结构时逐列核对，防止“实体有字段、表中无列”事故。

**第五条**　逻辑删除统一使用 deleted 字段并由数据访问层自动处理，禁止业务代码手动拼接；多租户数据表必须包含 tenant_id 并由多租户插件自动过滤，禁止手写租户条件。

**第六条**　字段设计须为取值留足空间：枚举与层级值不使用 TINYINT(1) 存储；与 PHP 存量库交互时注意其 TINYINT(1) 存枚举的历史习惯，解析侧须做兜底。

## 第三章　Flyway 迁移管理

**第七条**　迁移脚本命名：V{YYYYMMDD}_{序号}__{描述}.sql，存放于 db/migration 目录；新建迁移前先查询数据库最大版本号——测试库与生产库两库并行查 MAX(version)，取二者大值并在其上留足间隔递增，不靠文件名猜测。

**第八条**　已应用的迁移文件禁止修改；修正历史问题一律新增迁移。含种子数据的迁移必须幂等，可重复执行不报错；空库必须能执行全部迁移成功。

**第九条**　新增迁移脚本后必须重新编译，并基于 mvn compile 后的构建产物对空库执行一次 migrate 验证，确认全部脚本可成功执行；数据库变更必须在执行前完成备份（衔接 YW-08）。

## 第四章　DDL 评审与上线流程

**第十条**　DDL 变更先评审后执行，评审内容：字段类型与长度、索引设计、对存量数据与大表的影响（锁表风险）、回退方案。

**第十一条**　生产 DDL 按 YW-05 变更流程执行；大表加列、加索引选择业务低峰窗口，执行中监控数据库负载。

**第十二条**　受数据库中间件 SQL 防火墙约束，upsert 语句统一使用兼容语法，不使用新版行别名语法；多数据源场景下，第二数据源不得以 DataSource Bean 形式注册，防止主数据源自动配置退让。

## 第五章　数据字典维护

**第十三条**　所有表与字段必须有注释；数据字典随迁移同步更新，变更谁发起、谁更新。

**第十四条**　每季度核对一次数据字典与实际表结构，差异项 3 个工作日内修正。

## 第六章　附则

**第十五条**　本制度由千铝工投云平台与智能体开发部负责解释。

**第十六条**　本制度自发布之日起施行。
