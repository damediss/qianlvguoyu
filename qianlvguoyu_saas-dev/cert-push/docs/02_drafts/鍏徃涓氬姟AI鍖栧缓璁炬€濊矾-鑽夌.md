# 公司业务三个月 AI 改造行动计划（草稿）

## 一、总体方向

未来三个月数字化与 AI 建设，不只是做一个培训平台、竞赛系统或智能体，而是要完成公司数字化能力的转向：

1. 收回外包，逐步掌握系统、源码、数据、账号、部署和运维主动权。
2. 自研自开发，建立公司自己的产品、技术、数据和 AI 应用能力。
3. 平台全面探索 AI 化，把现有培训、竞赛、认定、课程、项目、报表、客户服务等流程逐步嵌入 AI 能力。
4. 公司各部门、人员和业务全面 AI 化，让 AI 不只是工具，而是变成每个岗位的工作助手、每条业务线的提效系统、每个管理动作的数据支撑。
5. 用 AI 辅助重构旧 PHP 代码为 Java 服务，逐步与原有 Java 系统打通，减少历史系统孤岛。
6. 建设 AI Agent 代理能力，让 AI 不只回答问题，还能代替岗位执行流程任务、调用系统接口、生成材料、跟踪进度和提醒责任人。
7. 建设桌面端 AI 助手，让管理者或员工在电脑上随时调出 AI，对当前打开的系统页面、课程安排、项目进度、材料清单等进行分析、提醒和操作指导。
8. 搭建公司内部知识库，把制度、流程、项目资料、课程资料、题库资料、客户资料、系统文档和外包交付资料沉淀下来，成为 AI 助手和 Agent 代理的基础。
9. 通过接入 ChatGPT 等大模型能力，增加 Agent 代理和岗位 AI 助手，使公司全体员工逐步具备 AI 辅助办公、业务处理、资料生成、数据分析和流程跟进能力。

从管理者视角看，AI 化不是简单买几个软件，也不是让员工自己用 ChatGPT，而是要把公司已有业务流程、资料、数据、系统和岗位职责重新组织起来，让 AI 能真正参与业务执行、管理决策和客户交付。

这次改造的核心，是让公司从“人盯流程”变成“流程推着人走”：过去靠人记、靠人催、靠人问进度；以后由系统和 Agent 按流程节点推动责任人处理，AI 负责生成材料、检查缺项、提醒待办、汇总结果，管理层通过 Agent 面板看进度、看风险、看结果。

三个月后要看到的直接效果：

1. 领导打开 Agent 面板，就能看到重点项目进度、负责人、延期风险、待决策事项和下一步动作。
2. 看到培训、竞赛、认定、课程、工业仿真等核心业务从“靠人盯、靠群催、靠表格汇总”，开始转为“系统记录、流程流转、数据反馈”。
3. 看到外包项目不再是黑盒，源码、数据库、账号、接口、部署文档、仿真工程文件和模型资产的收回情况能清楚呈现。
4. 看到 AI 已经产出实际成果，包括课程初稿、题库辅助、项目周报、会议纪要、材料检查、营销文案和复盘报告。
5. 看到 Agent 开始辅助执行连续任务，包括催办、通知、跟踪、生成材料、反馈结果，减少管理层反复问人、催人。
6. 看到公司内部知识库开始成型，制度、流程、项目资料、课程资料、题库资料、系统文档和外包交付资料可以被检索、引用和复用。
7. 看到全体员工开始接入 AI 能力，员工日常写材料、查资料、做表格、跟项目、做复盘、服务客户时都有 AI 助手或 Agent 可用。
8. 看到平台开始接入 AI 和 Agent 代理，系统不只是录入数据和展示页面，而是能生成、提醒、检查、分析和代办。
9. 看到系统开发从“开发完成却用不起来”，转为小步上线、周周验收、边用边改，业务部门能看到真实可用的变化。
10. 看到公司形成初步可复制的“系统 + 数据 + 知识库 + AI + Agent + 工业仿真”交付能力，为后续做客户项目和形成竞争力打基础。

这里有一个前提：外包成果和系统控制权如果不收回来，真正的智能化也做不了。因为 AI 要接入业务流程、数据库、接口、权限、文档和系统操作，如果这些都掌握在外包手里，公司内部只能做表层问答、材料生成和演示，无法实现真正的平台 AI 化、Agent 代理化和业务自动化。

## 二、第一件事：收回外包

### 1. 为什么必须收回外包

公司现在多个系统依赖外包推进，包括培训 SaaS、竞赛系统、Java 既有平台、Node.js 新开发方向等。如果系统、源码、数据库、服务器和账号长期掌握在外包手里，公司就会出现几个问题：

1. 系统做完但公司没人懂。
2. 需求一改就必须找外包。
3. 数据资产沉淀不到公司内部。
4. 后续 AI 化无法深入接入业务数据。
5. 外包报价、排期、质量和维护都不可控。

所以第一阶段不是马上完全不要外包，而是先把外包从“主导开发”调整为“阶段性协作”，公司内部逐步接管产品、技术、数据和验收权。

换句话说，收回外包不是单纯为了省钱，也不是为了和外包切割，而是为了拿回智能化建设的基础条件。系统、数据、接口、账号、源码和业务规则不在公司手里，AI 就无法深入业务，只能停留在外部工具层面。

### 2. 收回外包要收回什么

| 项目 | 必须收回的内容 |
| --- | --- |
| 源码 | 前端、后端、脚本、配置文件、依赖说明 |
| 数据库 | 表结构、字段说明、初始化数据、备份文件 |
| 接口 | API 文档、接口地址、参数、权限、调用示例 |
| 服务器 | 登录权限、部署路径、运行环境、域名、证书 |
| 账号 | 云服务器、数据库、对象存储、短信、支付、第三方接口账号 |
| 文档 | 需求文档、原型、部署文档、运维文档、测试文档 |
| 交付标准 | 每个模块怎么验收、谁验收、验收不通过怎么处理 |

### 3. 收回外包的三步走

第一步：盘点  
把所有外包项目列出来，包括项目名称、外包团队、合同范围、当前进度、源码位置、服务器位置、账号归属、数据库归属、维护费用和风险。

第二步：交接  
要求外包按项目交付源码、数据库、接口、部署文档和账号权限。没有这些内容，不算完成交付。

第三步：内化  
公司内部建立 Git 仓库、测试环境、资料库和项目看板。后续新需求由内部先写需求和验收标准，外包只做明确边界内的开发协助。

## 三、第二件事：自研自开发

### 1. 自研自开发的目标

自研不是所有代码都自己写，而是公司必须掌握四个核心能力：

1. 产品能力：知道业务要什么，能把需求拆成系统功能。
2. 技术能力：能看懂代码、部署系统、判断方案优劣。
3. 数据能力：能掌握客户、学员、课程、题库、项目、证书、竞赛等核心数据。
4. AI 能力：能把业务资料和系统数据接入智能体、知识库和自动化流程。

外包可以参与开发，但不能替公司思考产品、掌握数据和控制技术路线。

### 2. 自研自开发的切入点

短期不建议一开始做大团队，而是先建立“小核心团队 + 外包协作”的模式。

内部核心团队负责：

1. 需求整理。
2. 原型确认。
3. 技术路线判断。
4. 代码仓库管理。
5. 数据结构管理。
6. 测试验收。
7. AI 场景设计。
8. 运维交接。

外包团队负责：

1. 明确模块开发。
2. 页面和接口实现。
3. 阶段性 bug 修复。
4. 按公司规范提交代码和文档。

### 3. 现有系统重构与统一技术栈

目前至少存在三类系统需要统一梳理和重构：

| 系统 | 当前定位 | 已观察到的核心模块 | 重构方向 |
| --- | --- | --- | --- |
| 竞赛后台 | 管理竞赛理论考试和实操考试 | 考试计划、理论试卷、试题导入、实操题、操作项、参赛人员、考评人员 | 纳入统一 Java 平台，形成竞赛业务统一模块 |
| 原 Java 云平台 | 管理课程、培训、认定、竞赛等业务 | 题库建设、考试管理、培训管理、竞赛管理、信息收集、学习配置、团队管理、人才数据 | 作为统一技术栈和统一业务中台的基础 |
| 现有 PHP 云平台 | 管理课程、培训、认定、竞赛等业务 | 需进一步登录梳理具体功能、数据库和历史业务规则 | 用 AI 辅助理解旧 PHP 逻辑，逐步重构为 Java |

当前已有一个关键问题必须解决：系统虽然已经开发完成，但业务实际用不起来。这个问题不能简单归结为“员工不会用”，而要从业务流程、角色权限、数据准备、页面体验、培训交付、验收标准和后续运营几个方面一起排查。

“开发完成却用不起来”通常说明：

1. 系统功能和真实业务流程没有完全对齐。
2. 业务人员不知道在哪一步使用系统、用系统替代原来哪张表或哪个人工动作。
3. 角色权限、账号、数据初始化、基础配置没有准备好。
4. 老系统、外包系统、Java 平台、PHP 平台之间没有打通，业务需要重复录入。
5. 验收只验了页面和功能，没有验完整业务闭环。
6. 没有形成使用培训、操作手册、问题反馈和持续迭代机制。

所以原 Java 云平台虽然可以作为统一技术栈和业务中台的基础，但前提是先解决“能开发、不能用”的问题。后续重构不能只看功能是否存在，而要看业务是否真正跑起来。

整改原则：

1. 以业务闭环验收系统，而不是以页面开发完成验收系统。
2. 每个模块都要明确使用人、使用场景、输入数据、输出结果和替代的人工流程。
3. 先选一个真实业务场景试跑，例如竞赛理论考试或培训开班流程，跑通后再扩展。
4. 对业务人员使用中卡住的问题，进入快速迭代清单，不再长期挂起。
5. 能用 AI 流程替代的地方，直接把 AI 助手或 Agent 代理嵌进使用流程，降低人工使用门槛。

验收口径要调整为：

1. 不是“功能开发完成”，而是“业务人员能独立完成一条真实流程”。
2. 不是“页面能打开”，而是“数据能录入、能流转、能导出、能追溯”。
3. 不是“外包说交付了”，而是“公司内部能配置、能使用、能维护、能二次迭代”。

统一技术栈的目标不是为了技术统一而统一，而是为了后续平台 AI 化、Agent 代理化和数据打通。如果竞赛、培训、课程、认定分别散在不同技术栈、不同数据库和不同账号体系里，AI 就很难统一读取业务数据、调用系统接口和执行流程任务。

统一技术栈建议方向：

1. 后端逐步统一到 Java 服务体系。
2. 前端逐步统一到一套管理后台框架。
3. 用户、组织、角色、权限统一。
4. 课程、题库、考试、竞赛、培训、认定、证书等核心数据统一建模。
5. 旧 PHP 系统不直接推倒重做，而是先用 AI 梳理业务逻辑，再分模块迁移。
6. 竞赛系统优先重构，因为它同时涉及理论考试、实操考试、试卷试题、人员和评分，是 AI 化和统一平台打通的关键样板。

### 4. 工业项目仿真也要收回外包并建立自研能力

公司还存在一条重要业务线：工业项目仿真，也可以理解为工业生产仿真、虚拟实训仿真、实操训练仿真。目前这类项目也是少部分自研、大部分依赖外包。这个问题同样需要纳入“收回外包”和“自研自开发”的范围。

工业项目仿真不能长期完全依赖外包。原因是：

1. 仿真项目不是单纯做 3D 模型，而是要理解真实生产工艺、设备操作、实操流程、评分标准和安全风险。
2. 如果模型、场景、交互逻辑、引擎工程文件、源码和素材库都在外包手里，公司后续无法复用、修改和二次开发。
3. 仿真内容要和课程、题库、实操考试、竞赛、认定、AI 陪练打通，外包如果不交底，平台 AI 化也接不进去。
4. 工业仿真是公司未来对外竞争力很强的产品线，不能只做成一次性项目交付。

工业仿真项目需要收回的内容包括：

| 类别 | 需要收回的内容 |
| --- | --- |
| 3D 资产 | 设备模型、工具模型、工位模型、车间场景、材质贴图、动画文件 |
| 引擎工程 | Unity/Unreal/其他引擎工程文件、场景文件、交互脚本、打包配置 |
| 业务脚本 | 生产 SOP、操作步骤、异常处置、评分规则、扣分项、教学说明 |
| 交互逻辑 | 点击、拖拽、设备状态、参数变化、流程分支、错误反馈 |
| 数据接口 | 学员、课程、题库、考试、评分、学习记录、实操结果等接口 |
| 素材规范 | 命名规范、版本规范、模型精度、动画规范、资源入库标准 |
| 部署文档 | PC、Web、VR、平板或大屏部署方式、运行环境、性能要求 |

工业项目仿真的自研方向：

1. 内部要能看懂和维护仿真项目，不再只靠外包改模型和改流程。
2. 建立公司自己的工业仿真资产库，包括设备、工位、车间、工具、动作、流程模板。
3. 把真实 SOP 拆成“流程节点、操作动作、判断条件、错误动作、评分点、风险提示”。
4. 把仿真流程接入培训、竞赛、课程、认定和 AI 精准学。
5. 形成“工业仿真 + AI 陪练 + 实操评分 + 学习报告”的产品能力。

例如铝电解相关仿真，可以把以下操作规程拆成可交互流程：

1. 查看槽控机工作显示状态及电压情况，并按效应加工。
2. 判断效应电压是否持续在 35V 以上，如果持续过高，先插入效应棒把电压控制在 35V 以内。
3. 打开出铝洞口，侧身在阳极下方插入效应棒，并关闭炉门。
4. 效应灯熄灭后，到槽控机旁确认效应熄灭和电压稳定。
5. 检查三联件空压总阀、气动柜控制阀门、打壳、下料、电磁阀是否正常动作。
6. 打开烟道端炉门，观察下料点是否堵料、下料是否正常。
7. 回到出铝端，取出效应棒，等明火熄灭后放到废效应棒堆放点。
8. 确认电压稳定后，按 1-2 次“升阳极”键，把电压升到与设定电压差值在 ±50mv。
9. 用预热好的炭渣瓢将出铝口炭渣捞出，倒入炭渣箱内。
10. 清扫出铝口卫生，关闭出铝口。
11. 效应熄灭后半小时内巡检，发现散热孔发红、钢棒发红等异常及时处理。
12. 完成正常效应处理。

这类流程非常适合做成“仿真任务 + AI 陪练 + 操作评分 + 错误复盘”：

1. AI 根据 SOP 自动拆分操作步骤。
2. AI 自动生成训练任务、提示语、风险提醒和扣分点。
3. 学员在仿真环境中按步骤操作，系统记录动作、顺序、用时和错误。
4. AI 实时提示下一步、解释错误原因、提醒安全风险。
5. 训练结束后自动生成实操报告、扣分说明、薄弱项和复训建议。

三个月内工业仿真的收回目标：

1. 盘点现有所有仿真项目、外包团队、工程文件、模型资产、源码、部署方式和合同交付范围。
2. 收回至少一个典型仿真项目的完整工程文件、模型资产、交互脚本和部署文档。
3. 选一个铝电解或实操考试流程，拆成标准化仿真流程模板。
4. 建立仿真资产命名、版本、入库和复用规范。
5. 明确内部 3D/虚拟现实（仿真）工程师、全栈工程师、AI 知识库人员之间的协作方式。
6. 形成工业仿真项目后续“内部主导 + 外包补位”的交付模式。

### 5. 用 AI 重构旧 PHP 代码为 Java

如果公司现有旧系统或历史功能是 PHP 写的，后续要和原有 Java 平台打通，建议把“PHP 旧代码 AI 重构为 Java 服务”列为自研自开发的重要任务。

这件事不是简单翻译代码，而是通过 AI 辅助完成以下工作：

1. 读取和理解旧 PHP 代码，梳理功能模块、业务规则、数据库表和接口逻辑。
2. 把 PHP 中可复用的业务逻辑整理成需求说明、接口说明和测试用例。
3. 按公司现有 Java 系统架构，重构为 Java 后端服务或独立模块。
4. 与原有 Java 平台的用户、权限、数据、流程和接口打通。
5. 对重构后的 Java 模块进行功能对比测试，确保旧功能不丢失、数据不混乱、流程可追溯。

推进原则：

1. 先梳理旧 PHP 系统功能和数据，不直接盲目改代码。
2. 先选一个边界清晰的小模块试点，例如报名、查询、资料上传或报表导出。
3. PHP 代码只作为业务规则和历史逻辑来源，目标是沉淀为 Java 系统可维护能力。
4. AI 负责辅助理解、转换、生成测试和文档，最终架构、接口和验收必须由内部技术负责人确认。

三个月内目标：

1. 完成旧 PHP 系统代码盘点。
2. 选定 1-2 个模块进行 AI 辅助 Java 重构试点。
3. 建立 PHP 到 Java 的重构规范、测试规范和接口对接规范。
4. 形成后续旧系统分批迁移计划。

### 6. 功能拆解：能用 AI 流程替代的就改成 AI 流程

系统重构时不能只把旧功能照搬到新系统里，而要同步判断每个功能是否可以改成 AI 流程。

拆解原则：

1. 先拆业务流程，再拆系统功能。
2. 先找重复填表、重复生成材料、重复检查、重复催办、重复统计的环节。
3. 能由 AI 生成初稿的，就不再让人工从零写。
4. 能由 AI 检查规则的，就不再完全靠人工逐条核对。
5. 能由 Agent 代理跟进的，就不再靠人工反复催。
6. 关键审批、结果确认、对外发送和高风险操作仍保留人工确认。

按现有业务，可以优先替代以下流程：

| 业务环节 | 传统做法 | AI 流程替代方向 |
| --- | --- | --- |
| 竞赛方案 | 人工写方案和通知 | AI 生成竞赛方案、通知、规则说明和时间安排 |
| 理论试卷 | 人工整理题库、组卷、查错 | AI 辅助题库清洗、试题分类、组卷、纠错和难度分析 |
| 实操考试 | 人工配置实操题、操作项、评分表 | AI 辅助生成实操任务、评分细则、考评表和风险提示 |
| 培训计划 | 人工根据需求排班排课 | AI 根据人员、工种、讲师、场地生成培训计划建议 |
| 课程开发 | 人工从零写大纲、课件、题库 | AI 生成课程大纲、课件初稿、讲义和题库 |
| 认定材料 | 人工逐项核对材料 | AI 检查缺失材料、条件匹配和退回原因 |
| 项目周报 | 项目经理手工写 | Agent 自动读取项目进度生成周报和风险清单 |
| 外包验收 | 人工凭页面验收 | AI 辅助检查源码、接口、数据库、文档和测试用例完整性 |

### 7. 开发流程重构：小步快跑，代码先行试错

后续自研自开发不能完全沿用传统外包式流程：大需求先写很厚文档，等全部确认后再开发。公司要建立适合 AI 时代的快速迭代机制，把需求分成小需求、大需求和模糊需求分别处理。

| 需求类型 | 处理方式 | 交付节奏 |
| --- | --- | --- |
| 小需求 | 直接明确目标、页面、字段和验收标准，用 AI 辅助快速生成代码和测试 | 1-3 天内出可用版本 |
| 大需求 | 先拆成业务流程、模块、接口、数据和权限，再分阶段做 MVP | 每周有可测试版本 |
| 模糊需求 | 不急着写完整文档，先做低成本原型或代码样板试错 | 先跑通，再沉淀需求 |

开发流程建议改为：

1. 先用 AI 把口头需求整理成一页需求草稿。
2. 先做最小可运行版本，不追求一开始完整。
3. 让业务人员尽快看到页面和流程，再反馈修改。
4. 每个版本都保留验收标准、变更记录和测试结果。
5. 小需求当天或三天内闭环，大需求拆成周迭代。
6. 模糊需求先上代码试错，用实际使用反馈反推产品定义。
7. 所有代码必须进公司仓库，不能只留在外包电脑或个人电脑。

这种方式的核心是：AI 辅助开发以后，竞争不再是谁一次性写出最完整文档，而是谁能更快把想法变成可用版本，并且不断迭代。

### 8. 三个月内自研要形成的能力

| 能力 | 三个月内目标 |
| --- | --- |
| 代码管理 | 所有项目进入公司 Git 仓库 |
| 测试环境 | 建立公司自己的测试环境和演示环境 |
| 需求管理 | 形成需求文档、原型、验收表模板 |
| 数据管理 | 核心业务数据有字段说明和导出机制 |
| AI 开发 | 能做知识库、提示词、智能体和简单业务自动化 |
| 旧系统重构 | 用 AI 辅助把旧 PHP 模块逐步重构为 Java，并与原有 Java 系统打通 |
| 竞赛系统重构 | 把理论考试、实操考试、试卷试题、人员和评分逐步纳入统一 Java 平台 |
| 工业仿真自研 | 收回仿真工程文件、模型资产、交互脚本和部署文档，建立内部可维护能力 |
| 快速迭代 | 小需求 1-3 天闭环，大需求周迭代，模糊需求先原型试错 |
| 运维管理 | 能独立部署、备份、排查基础问题 |

## 四、第三件事：平台全面探索 AI 化

现有培训部数字化平台原型已经覆盖了培训业务端到端流程，包括领导总览、培训计划、人才数据、培训准备、培训执行、认定补贴、项目收尾、系统集成、移动端、数据统计和系统管理。

如果从管理者角度做 AI 化，不是单独加一个“AI 按钮”，而是让 AI 嵌入每个业务环节。

### 1. 领导总览 AI 化

现有需求：

1. 流程总览。
2. 项目里程碑。
3. 风险预警。
4. 核心指标仪表盘。

AI 化方向：

1. 自动总结本周项目进度。
2. 自动识别延期项目和高风险项目。
3. 自动生成老板汇报摘要。
4. 自动解释指标异常原因。
5. 自动提出下一步处理建议。

示例：

系统发现“腾讯焊工培训开班材料逾期 3 天”，AI 自动生成：逾期原因、影响范围、责任人、建议动作、是否需要领导协调。

现有需求：

1. 企业提交人才数据。
2. 接收与预处理。
3. 去重。
4. 查证。
5. 条件匹配与计算。
6. 输出需求清单。
7. 反馈闭环。

AI 化方向：

1. 自动检查企业上传表格字段是否完整。
2. 自动识别异常数据、重复数据、格式错误。
3. 自动提示缺失材料。
4. 自动解释某个人为什么符合或不符合某个认定条件。
5. 自动生成企业反馈话术。
6. 自动把人才数据转成培训需求清单。

这部分是平台 AI 化的核心，因为它直接决定后续培训规划、开班、认定和补贴。

### 13. 全员 AI 能力与平台 Agent 接入

公司 AI 改造不能只停留在管理层、技术部或少数试点岗位，而是要让全体员工逐步具备 AI 能力。这里的 AI 能力不是让员工随便问问题，而是通过接入 ChatGPT 等大模型能力、公司内部知识库、业务模板和 Agent 代理，把 AI 变成员工日常工作的基础工具。

落到业务上，就是把员工从“人盯流程”里释放出来。流程到了哪个节点、该谁处理、缺什么材料、下一步做什么，由平台和 Agent 自动提示；AI 负责生成、检查、提醒、汇总，员工负责确认、判断和处理关键事项。

全员 AI 能力建设包括三层：

| 层级 | 建设内容 | 目标 |
| --- | --- | --- |
| 员工 AI 助手 | 给员工提供统一 AI 助手入口，可用于写材料、查资料、做总结、生成表格、提炼会议纪要 | 让员工日常办公先用起来 |
| 岗位 Agent | 围绕岗位配置固定 Agent，例如培训专员 Agent、课程开发 Agent、销售跟进 Agent、项目经理 Agent | 让 AI 能理解岗位任务并辅助连续执行 |
| 平台 AI 与 Agent | 在培训、竞赛、认定、课程、营销、项目、报表、工业仿真等平台中嵌入 AI 和 Agent | 让系统从“人操作系统”升级为“系统辅助人推进业务” |

第一阶段要先完成以下能力：

1. 接入 ChatGPT 等大模型能力，形成公司统一 AI 能力入口。
2. 结合公司内部知识库，让 AI 回答和生成时能引用公司自己的制度、流程、课程、项目、客户和系统资料。
3. 给全体员工开放基础 AI 助手，用于材料生成、资料查询、会议纪要、表格整理、项目总结和客户沟通。
4. 给重点岗位配置 Agent 代理，例如项目周报 Agent、课程生成 Agent、材料检查 Agent、营销跟进 Agent、人员协同 Agent。
5. 把平台接入 AI 和 Agent，让员工在系统里就能完成生成、检查、提醒、催办、统计和复盘，不需要在多个工具之间来回切换。
6. 把关键流程节点化，让流程主动推送到人，而不是靠人反复盯流程、问进度、催材料。

平台接入 AI 与 Agent 后，业务平台要具备以下变化：

1. 培训平台：能自动生成开班材料、课程安排提醒、学员学习提醒、结课报告。
2. 竞赛平台：能辅助生成竞赛方案、题库、通知、名单、评分分析和总结。
3. 认定平台：能检查材料缺失、识别不符合项、生成补材料通知。
4. 课程平台：能根据资料生成课程大纲、课件初稿、题库和讲义。
5. 营销平台：能生成宣传文案、客户方案、跟进话术和案例包装。
6. 项目管理平台：能生成周报、识别延期风险、催办责任人、汇总待决策事项。
7. 数据报表平台：能自动解释数据变化、生成领导摘要和异常提醒。
8. 工业仿真平台：能结合操作规程和评分标准，形成 AI 陪练、错误提醒和复盘建议。

三个月内，全员 AI 能力建设要形成三个结果：

1. 全体员工有统一 AI 入口，知道哪些工作可以用 AI 辅助完成。
2. 重点岗位有可试运行的 Agent 代理，能在人工确认下完成生成、提醒、催办、反馈和留痕。
3. 核心业务平台开始接入 AI 和 Agent，平台不再只是记录数据，而是开始辅助业务执行。

### 14. 公司内部知识库搭建

公司内部知识库是 AI 化和 Agent 代理化的基础。没有知识库，AI 只能靠临时输入回答问题；有了知识库，AI 才能基于公司自己的制度、流程、项目经验、课程资料、系统文档和客户资料给出可用建议。

知识库要先服务内部管理，再服务业务交付。建议按以下几类搭建：

| 知识库类型 | 主要内容 | 用途 |
| --- | --- | --- |
| 制度流程库 | 公司制度、审批流程、项目流程、培训流程、竞赛流程、认定流程 | 让员工和 Agent 知道事情应该怎么做 |
| 项目资料库 | 项目方案、合同要点、会议纪要、周报、验收材料、复盘报告 | 支撑项目管理、项目复盘和客户交付 |
| 课程题库库 | 课程大纲、课件、讲义、题库、实操标准、评分规则 | 支撑课程生成、题库生成、考试和竞赛 |
| 客户与营销库 | 客户需求、历史合作、案例、宣传素材、方案模板、报价口径 | 支撑销售跟进、营销推广和方案生成 |
| 系统与外包交付库 | 系统账号、接口文档、部署文档、数据库说明、源码说明、外包交付清单 | 支撑外包收回、系统接管和后续开发 |
| 工业仿真知识库 | 工艺流程、设备说明、操作规程、模型资产说明、交互脚本、评分标准 | 支撑工业仿真自研、AI 陪练和实操评分 |

知识库搭建不能只做“文件上传”，要形成可持续维护机制：

1. 每个部门指定知识库负责人，负责资料收集、分类、更新和过期清理。
2. 建立统一目录结构，例如制度流程、项目资料、课程题库、客户营销、系统文档、工业仿真。
3. 每份资料要有来源、版本、负责人、更新时间和适用范围。
4. 重要资料要结构化，例如流程拆成步骤、表格、检查项、模板和常见问题。
5. 知识库要接入 Agent 面板，让 AI 可以引用公司资料回答、生成、检查和催办。
6. 对敏感资料设置权限，不同岗位只能查看和调用授权范围内的内容。
7. 每个项目结束后，必须把方案、过程资料、问题、经验和复盘沉淀回知识库。

三个月内知识库建设行动计划：

1. 第一个月：立即启动，不等源码和系统代码全部收齐。先用现有制度、流程、项目资料、课程资料、题库资料、客户资料、系统截图、表格和外包已交付文档，搭建最小可用知识库，并接入 Agent 面板做问答、材料检查、课程初稿和项目周报试用。
2. 第二个月：各部门继续维护自己的知识库，把更多业务资料、系统文档、接口说明、外包交付资料和项目复盘补充进去，让知识库支撑课程生成、客户方案、材料检查、项目周报、通知催办等 Agent 场景。
3. 第三个月：形成知识库维护规范，包括资料入库、命名、版本、权限、更新、审核、引用记录和复盘沉淀机制，并把系统源码、数据库说明、接口文档等后续收回资料持续接入。

三个月后领导打开 Agent 面板，应该能看到知识库的建设效果：

1. 哪些部门已经建立知识库，资料数量和更新情况如何。
2. 哪些资料可以被 AI 调用，哪些资料还缺失。
3. 哪些项目、课程、题库、客户案例和系统文档已经沉淀。
4. AI 生成材料时引用了哪些公司内部资料。
5. 部门是否把项目复盘和经验持续回填到知识库。

### 15. AI Agent 代理能力

平台 AI 化不能只停留在“问答”和“生成文案”，还要逐步建设 Agent 代理能力。Agent 代理的意思是：AI 能在授权范围内代表某个岗位或某条流程完成连续任务，包括读取数据、判断状态、生成材料、调用接口、发起提醒、输出结果，并把全过程记录下来。

平台里建议先建设以下 Agent：

| Agent 类型 | 主要作用 | 适用场景 |
| --- | --- | --- |
| 项目管理 Agent | 跟踪项目进度、识别风险、生成周报、催办责任人 | 培训项目、竞赛项目、系统开发项目 |
| 培训执行 Agent | 检查开班材料、提醒学员学习、跟踪签到和出勤 | 开班、培训过程、结课 |
| 认定审核 Agent | 检查资格条件、识别材料缺失、生成补材料通知 | 认定申报、证书办理、补贴材料 |
| 课程开发 Agent | 根据资料生成大纲、课件、题库、讲义和脚本 | 课程部、培训产品开发 |
| 销售跟进 Agent | 整理客户需求、生成跟进话术、提醒复训和续费 | 客户咨询、企业合作、老客户维护 |
| 竞赛运营 Agent | 辅助生成竞赛方案、通知、命题、名单、排名和总结 | 企业竞赛、政府竞赛活动 |
| 代码重构 Agent | 理解旧 PHP 代码、生成 Java 重构方案、测试用例和接口文档 | 旧系统迁移、自研自开发 |
| 领导驾驶舱 Agent | 汇总经营数据、项目风险、部门待办和需拍板事项 | 老板总览、经营例会、周报 |
| 桌面指导 Agent | 识别当前桌面或系统页面，给出业务建议、风险提醒和下一步操作 | 课程安排、项目看板、报表、材料审核 |
| 人员协同 Agent | 根据口令通知指定人员、跟踪是否送达和反馈执行结果 | 叫人到办公室、会议通知、催办协同 |

Agent 代理建设要有边界：

1. 第一阶段先做“建议型 Agent”，由 AI 生成建议、材料和提醒，人来确认执行。
2. 第二阶段做“半自动 Agent”，AI 可以在系统内创建草稿、生成待办、发起通知，但关键动作仍需人工确认。
3. 第三阶段再做“授权执行 Agent”，在明确权限、日志和审批规则后，让 AI 执行低风险重复操作。

Agent 代理必须具备五个基础能力：

1. 任务理解：能理解岗位任务和流程规则。
2. 数据读取：能读取平台内授权范围的数据。
3. 工具调用：能调用系统接口、模板、表格、消息通知等工具。
4. 结果生成：能生成材料、报告、清单、通知和建议。
5. 过程留痕：能记录 AI 做了什么、依据什么、谁确认了结果。

### 16. 桌面端 AI 助手和人员协同 Agent

除了嵌在平台里的 AI 功能，还可以做一个运行在电脑桌面端的小程序，作为公司内部的桌面端 AI 助手。它可以通过快捷键、悬浮按钮或语音唤起，在员工或管理者当前使用电脑时提供实时指导。

#### 1. 桌面端 AI 助手：看当前桌面给建议

功能设想：

1. 用户在电脑上打开培训平台、课程安排、项目看板、报表、Excel 或网页后，随时调出桌面端 AI 助手。
2. AI 在授权范围内读取当前窗口内容或截图，识别当前正在处理的业务场景。
3. AI 根据公司流程、历史数据、规则和知识库，给出下一步建议、风险提醒、检查清单或操作步骤。
4. AI 可以生成待办、通知、修改建议、周报摘要、材料清单，但关键操作由人确认。

例如打开“课程安排”页面时，AI 可以自动提示：

1. 当前课程是否存在讲师、教室、时间冲突。
2. 学员人数和场地容量是否匹配。
3. 是否缺少开班材料、讲师资料、设备安排或考试时间。
4. 哪些班级临近开班但材料未齐。
5. 是否建议调整排课、增加提醒或同步通知相关人员。

这个功能的价值是：员工不用切换到单独的 AI 页面，也不需要重新描述上下文，AI 可以直接结合当前桌面内容给出建议。

#### 2. 人员协同 Agent：一句话摇人并反馈结果

功能设想：

管理者可以直接对桌面端 AI 助手说：

“叫张三来我办公室。”

或者：

“叫培训部负责腾讯焊工项目的人来我办公室。”

Agent 执行流程：

1. 识别指令中的人员、部门、项目或角色。
2. 如果人员不明确，自动查询组织架构、项目负责人和通讯录，必要时向用户确认。
3. 通过企业微信、钉钉、短信、电话或内部系统消息发送通知。
4. 自动说明通知内容，例如“范总请你现在到办公室沟通腾讯焊工培训项目”。
5. 跟踪消息是否送达、是否已读、对方是否回复。
6. 把结果反馈给发起人，例如“已通知张三，企业微信已读，对方回复 5 分钟后到”。

人员协同 Agent 可以扩展到：

1. 叫项目负责人开会。
2. 催办某个材料。
3. 通知某个部门提交资料。
4. 提醒某个人处理系统风险。
5. 自动拉起临时会议或生成会议待办。

#### 3. 桌面端 Agent 的边界

桌面端 AI 助手涉及屏幕内容、通讯录、组织架构和内部消息，所以必须设计权限边界：

1. 只有用户主动唤起时才读取当前屏幕或窗口。
2. 涉及敏感数据时要做权限校验。
3. 发送通知、催办、拉会等动作要有日志。
4. 对外发送消息或影响业务流程的动作，第一阶段必须人工确认。
5. 所有 Agent 执行记录要能追溯：谁发起、通知谁、内容是什么、结果是什么。

这个桌面端小程序可以成为公司 AI 化的统一入口：员工处理业务时，它是业务指导助手；管理层调度人员时，它是人员协同 Agent；技术人员开发时，它是代码和旧系统重构助手。

## 五、AI 对系统平台交付方式和竞争方式的改变

AI 化以后，公司做系统平台不能再按传统外包模式理解。过去交付系统，主要是“调研需求 → 写文档 → 画原型 → 开发 → 测试 → 上线”。这种方式周期长、变更慢、依赖开发人员，竞争主要靠报价低、页面多、功能堆得全。

未来系统平台的交付方式和竞争方式会发生变化。真正有竞争力的平台，不只是把功能做出来，而是能快速理解业务、快速生成原型、快速形成可运行版本，并且内置 AI 助手、Agent 代理、数据分析和持续迭代能力。

### 1. AI 改变系统平台的交付方式

系统交付要从“人工定制开发”升级为“AI 辅助快速交付 + 行业模板复用 + 持续运营迭代”。

| 传统交付方式 | AI 化后的交付方式 |
| --- | --- |
| 靠人工访谈整理需求 | AI 辅助整理访谈纪要、流程图、功能清单和验收标准 |
| 靠产品经理手动画原型 | AI 根据业务流程快速生成页面原型和字段清单 |
| 靠开发人员从零写功能 | AI 辅助生成代码、接口、测试用例和文档 |
| 系统上线后才发现问题 | AI 在需求、测试、数据、流程中提前识别风险 |
| 系统只是工具 | 系统内置 AI 助手和 Agent 代理，能辅助执行任务 |
| 一次性交付结束 | 持续根据业务数据、用户反馈和流程变化迭代 |

未来公司的系统平台交付，应形成以下能力：

1. 需求快速生成能力：把老板口述、部门访谈、旧表格和流程图快速整理成需求文档。
2. 原型快速生成能力：根据业务流程快速生成页面、字段、权限和操作路径。
3. 代码辅助开发能力：用 AI 辅助前后端代码、接口、测试和文档生成。
4. 旧系统迁移能力：用 AI 理解旧 PHP 代码，重构为 Java 服务并接入原有系统。
5. Agent 配置能力：每个平台交付时，不只交付页面，还交付对应岗位的 Agent 代理。
6. 数据治理能力：交付系统时同步交付数据字典、表结构、导出规则和分析口径。
7. 持续运营能力：上线后通过 AI 生成周报、风险、优化建议和二期需求。

### 2. AI 改变系统平台的交付物

以后系统平台交付物不能只包括源码、页面和数据库，还要包括 AI 化交付物。

| 交付类别 | 交付内容 |
| --- | --- |
| 系统交付 | 前端、后端、数据库、接口、部署文档、账号权限 |
| 业务交付 | 业务流程图、角色权限表、字段字典、验收标准 |
| 数据交付 | 数据表结构、数据样例、导入导出模板、统计口径 |
| AI 交付 | 知识库、提示词模板、AI 助手配置、Agent 代理配置 |
| 运营交付 | 周报模板、风险预警规则、项目看板、复盘模板 |
| 迁移交付 | 旧系统功能清单、PHP 到 Java 重构说明、接口对接文档 |

也就是说，未来交付一个平台，不只是交付“系统能点”，还要交付“业务能跑、数据能用、AI 能接、Agent 能代办、后续能迭代”。

### 3. AI 改变系统平台的竞争方式

过去系统平台竞争，主要看谁价格低、谁开发快、谁页面多。AI 化以后，竞争点会变成以下几个方面：

1. 业务理解速度：谁能更快理解行业流程，谁就能更快出方案。
2. 交付速度：谁能用 AI 快速生成需求、原型、代码和测试，谁就能缩短周期。
3. 行业模板积累：谁有培训、竞赛、认定、补贴、课程等行业模板，谁就能低成本复制。
4. 数据能力：谁能把客户、学员、课程、题库、证书、项目数据沉淀下来，谁就能持续优化。
5. Agent 能力：谁的平台能让 AI 代理执行任务，谁的平台就更接近真实智能化。
6. 旧系统迁移能力：谁能把旧 PHP、Excel、人工流程迁移成 Java 平台和 AI 流程，谁就能抢老系统升级市场。
7. 持续运营能力：谁能上线后持续提供 AI 周报、风险预警、流程优化和业务复盘，谁就不只是卖系统，而是参与客户经营。

### 4. 对公司自身的意义

公司现在做内部数字化和 AI 化，不只是为了自己提效，也是在沉淀未来对外竞争能力。

如果公司能先把自己的培训、竞赛、课程、认定、项目管理做成 AI 化样板，就可以形成面向外部客户的解决方案：

1. 企业培训中心 AI 平台。
2. 技能认定与补贴 AI 平台。
3. 企业竞赛 AI 平台。
4. 课程开发与题库生成 AI 平台。
5. 老旧 PHP 系统 AI 辅助 Java 重构服务。
6. 企业数字化 Agent 代理平台。

未来竞争不是单纯卖软件，而是卖“行业系统 + AI 助手 + Agent 代理 + 数据运营 + 持续迭代”的整体能力。

## 六、第四件事：公司各部门、人员、业务 AI 化

从公司管理者视角看，AI 化要分四层推进：

1. 部门 AI 化：每个部门都有自己的知识库、流程助手和报表助手。
2. 岗位 AI 化：每个岗位都有对应的 AI 工作助手。
3. 业务 AI 化：每条业务线都用 AI 改造从获客到交付再到复盘的全过程。
4. Agent 代理化：让 AI 在授权范围内代替岗位执行连续任务，形成“人定规则、AI 跑流程、人做审核”的工作模式。

## 九、业务 AI 化设计

### 1. 获客 AI 化

3. 自动整理客户咨询问题。
4. 自动形成销售跟进话术。
5. 自动识别客户复训和续费机会。

### 1.1 营销推广 AI 化

营销推广也必须纳入公司 AI 化建设。公司后续不能只做内部系统和流程，还要用 AI 支撑获客、品牌宣传、客户转化和复训续费。培训、竞赛、认定、课程开发等业务本身就是可以对外传播和转化的内容资产。

营销推广 AI 化目标：

1. 提高线索获取能力。
2. 提高宣传内容生产效率。
3. 统一销售话术和客户方案。
4. 建立客户线索跟进机制。
5. 把培训、竞赛、认定、课程成果转化为案例和内容。
6. 促进老客户复训、续费和转介绍。

重点场景：

| 场景 | AI 化方向 |
| --- | --- |
| 官网和小程序 | AI 辅助生成业务介绍、案例展示、服务页面、FAQ 和报名入口文案 |
| 短视频和新媒体 | AI 生成短视频脚本、拍摄提纲、标题、封面文案、发布计划 |
| 朋友圈和公众号 | AI 生成活动宣传、培训开班、竞赛成果、政策解读、案例复盘内容 |
| 企业客户开发 | AI 根据行业、工种、企业规模生成培训合作方案和拜访话术 |
| 客户咨询 | AI 生成标准答复、报价说明、流程说明和常见异议处理 |
| 线索管理 | AI 自动整理客户来源、需求、跟进状态和下一步动作 |
| 销售跟进 | AI 自动提醒回访、生成跟进记录、推荐下一次沟通话术 |
| 案例沉淀 | AI 把已完成培训、竞赛、认定项目整理成宣传案例 |
| 复训续费 | AI 根据历史培训记录提醒复训、证书到期、续费和转介绍机会 |

营销推广 Agent 可以配置为：

1. 内容生成 Agent：根据课程、竞赛、培训项目自动生成宣传文案、短视频脚本和公众号文章。
2. 线索跟进 Agent：自动整理客户线索、提醒销售跟进、生成沟通话术。
3. 客户方案 Agent：根据企业需求生成培训方案、竞赛方案或认定服务方案。
4. 案例包装 Agent：把项目成果、获证人数、竞赛成绩、企业反馈整理成对外案例。
5. 复训续费 Agent：根据客户历史数据提醒复训、续费和证书更新。

第一阶段可以先做三个低成本动作：

1. 建立客户线索表，统一记录客户来源、需求、跟进人、跟进状态和下一步动作。
2. 用 AI 生成培训、竞赛、认定三类标准销售话术和方案模板。
3. 选 3-5 个已完成项目，用 AI 整理成宣传案例，用于官网、小程序、公众号和销售拜访。

营销推广的验收口径：

1. 每周是否稳定产出宣传内容。
2. 客户线索是否统一记录和跟进。
3. 销售是否有标准话术和方案模板。
4. 老客户是否有复训、续费和转介绍提醒。
5. 培训和竞赛项目是否能持续沉淀为可传播案例。

### 2. 报名 AI 化

1. 自动校验报名表。
2. 自动识别重复人员。
3. 自动检查缺失字段。
4. 自动生成补充材料通知。

### 3. 培训 AI 化

1. 自动生成课程计划。
2. 自动提醒学习进度。
3. 自动分析出勤风险。
4. 自动生成学习报告。

### 4. 考试 AI 化

1. 自动组卷。
2. 自动分析错题。
3. 自动推荐练习。
4. 自动生成成绩报告。

### 5. 认定 AI 化

1. 自动判断申报条件。
2. 自动检查材料。
3. 自动生成认定清单。
4. 自动跟踪获证进度。

### 6. 补贴 AI 化

1. 自动生成补贴材料。
2. 自动检查模板版本。
3. 自动识别人社退回原因。
4. 自动跟踪申报进度。

### 7. 竞赛 AI 化

1. 自动生成竞赛方案。
2. 自动整理参赛名单。
3. 自动辅助命题。
4. 自动评分分析。
5. 自动生成竞赛总结。

### 8. 复盘 AI 化

1. 自动生成项目总结。
2. 自动提取问题和经验。
3. 自动形成下次项目 SOP。
4. 自动沉淀到知识库。

### 9. 业务 Agent 代理化

业务 AI 化的更高阶段，是把关键业务流程拆成多个 Agent 代理协同执行。

示例一：培训项目 Agent 流程  
客户需求 Agent 整理企业需求 → 培训规划 Agent 生成方案 → 协议 Agent 生成协议草稿 → 开班 Agent 检查材料 → 学习 Agent 跟踪学员进度 → 考试 Agent 分析成绩 → 认定 Agent 检查证书材料 → 归档 Agent 生成项目总结。

示例二：竞赛项目 Agent 流程  
竞赛方案 Agent 生成活动方案 → 报名 Agent 整理参赛名单 → 命题 Agent 辅助题库生成 → 评分 Agent 汇总成绩 → 排名 Agent 生成排名结果 → 总结 Agent 生成活动复盘。

示例三：旧系统重构 Agent 流程  
代码理解 Agent 读取 PHP 代码 → 业务规则 Agent 提取功能逻辑 → Java 重构 Agent 生成模块方案 → 测试 Agent 生成用例 → 接口 Agent 输出对接文档 → 技术负责人审核后进入开发和联调。

## 十、三个月推进路径

### 第一个月：收权、建底座、跑样板

重点：

1. 收回外包项目清单和交付资料。
2. 建立项目看板和周报机制。
3. 明确培训 SaaS 一期 MVP。
4. 跑通公司智能体雏形。
5. 跑通课程 AI 初稿样板。
6. 明确 AI 化优先场景。
7. 盘点旧 PHP 系统代码、数据库和功能模块，选定 Java 重构试点模块。
8. 选定 2-3 个 Agent 代理试点，例如项目周报 Agent、课程生成 Agent、材料检查 Agent。
9. 完成竞赛后台、原 Java 云平台、现有 PHP 云平台的功能清单、数据清单和接口清单初版。
10. 建立小需求、大需求、模糊需求三类开发处理机制。
11. 盘点现有工业仿真项目、外包团队、工程文件、模型资产、交互脚本和部署资料。
12. 设计公司内部知识库目录，先确定制度流程、项目资料、课程题库、客户营销、系统文档、工业仿真六类资料入口。
13. 收集第一批可入库资料，包括公司制度、培训流程、竞赛流程、认定流程、项目模板、课程资料、题库资料、系统文档和外包交付资料。
14. 第一个月就搭建最小可用知识库和 Agent 面板入口，先接现有文档、表格、截图、流程和项目资料，不等待源码、数据库和系统接口全部收齐。
15. 用最小可用知识库支撑 2-3 个立即可见场景，例如制度问答、材料检查、课程初稿、项目周报和会议纪要生成。
16. 接入 ChatGPT 等大模型能力，形成公司统一 AI 助手入口，让员工先具备基础 AI 办公能力。
17. 选定第一批员工 AI 工作场景，例如写材料、查资料、整理表格、生成会议纪要、生成项目周报、输出客户沟通话术。

目标：

1. 公司知道所有系统和外包项目在哪里。
2. 培训平台主流程开始可用。
3. AI 开始在课程、问答和项目管理中产生可见结果。
4. Agent 代理开始在低风险场景中生成材料、提醒待办和辅助跟进。
5. 竞赛系统重构范围明确，理论考试和实操考试的核心数据结构开始统一设计。
6. 工业仿真项目的外包交付清单和收回范围明确。
7. 公司内部知识库不是停留在目录设计，而是第一个月就能被调用，先支撑问答、生成、检查和周报等轻量场景。
8. 全体员工开始有统一 AI 入口，先在低风险办公场景中使用 AI。

### 第二个月：自研接管、系统上线、部门扩展

重点：

1. 培训 SaaS 一期试运行。
2. 竞赛系统阶段上线。
3. 各部门建立知识库和智能体。
4. 内部开始接管代码、数据、接口和部署。
5. 建立需求、测试、验收和运维模板。
6. 用 AI 辅助完成 1-2 个旧 PHP 模块的 Java 重构试点，并与原有 Java 系统接口联调。
7. 将 Agent 代理接入平台数据和模板，形成项目、培训、课程、认定等场景的半自动流程。
8. 竞赛系统优先重构理论试卷、试题、实操题、操作项、参赛人员和考评人员模块。
9. 对能 AI 替代的流程进行改造，例如组卷、试题纠错、材料检查、项目周报和通知催办。
10. 收回至少一个典型工业仿真项目的完整工程文件、模型资产、交互脚本和部署文档。
11. 选一个铝电解或实操考试流程，拆成标准化仿真流程模板。
12. 各部门开始维护自己的知识库，把常用制度、SOP、项目材料、课程材料、客户案例和常见问题入库。
13. 将知识库接入 AI 助手和 Agent 试点，先用于材料检查、课程生成、项目周报、客户方案和问题问答。
14. 推进 AI 全面接入员工工作，把各部门常见重复任务梳理成 AI 模板和 Agent 流程。
15. 在培训、竞赛、认定、课程、营销、项目管理、数据报表、工业仿真等平台中接入 AI 助手或 Agent 试点能力。

目标：

1. 公司具备基本自研和验收能力。
2. 竞赛系统能支撑对外活动。
3. 部门 AI 助手开始进入实际工作。
4. 部分 Agent 代理可以在人工确认后创建草稿、生成通知、输出报表和催办事项。
5. 开发流程从“等完整需求再开发”转为“小步快跑、快速试错、周周可验收”。
6. 工业仿真项目从“外包交付黑盒”开始转为“内部可维护、可复用、可接入平台”。
7. 知识库开始被 AI 调用，不再只是文件堆放，而是能支撑问答、生成、检查和复盘。
8. 员工工作开始从“人自己写、人自己查、人自己催”转为“AI 辅助生成、Agent 辅助跟进、人工审核确认”。
9. 核心平台开始具备 AI 生成、检查、提醒、统计和催办能力。

### 第三个月：稳定运行、全面 AI 化试点、形成机制

重点：

1. 完善平台 AI 化能力。
2. 推进岗位 AI 助手。
3. 固化课程、培训、认定、竞赛、项目管理 SOP。
4. 完成外包交付验收。
5. 形成二期自研计划。
6. 形成旧 PHP 系统分批迁移到 Java 平台的路线图。
7. 形成公司 Agent 代理建设规范，包括权限、日志、审批、工具调用和人工确认规则。
8. 完成统一技术栈路线图，明确哪些系统保留、哪些重构、哪些合并、哪些废弃。
9. 沉淀 AI 辅助开发规范，包括需求生成、代码生成、测试生成、验收和迭代节奏。
10. 形成工业仿真资产库和交付规范，包括模型、场景、交互、评分、AI 陪练和平台接入标准。
11. 形成公司内部知识库维护规范，包括资料入库、命名、版本、权限、更新、审核、引用记录和项目复盘回填机制。
12. 在 Agent 面板中展示知识库建设情况，包括各部门资料数量、更新时间、缺失资料、AI 调用次数和复盘沉淀情况。
13. 形成全员 AI 使用规范，包括可用场景、禁用场景、数据安全、输出审核、敏感信息处理和责任边界。
14. 形成平台接入 AI 与 Agent 的标准，包括接口、权限、日志、审批、人工确认和执行留痕。

目标：

1. 平台从“能用”进入“好用”。
2. AI 从“试用”进入“嵌入流程”。
3. 公司从“依赖外包”转向“内部主导 + 外包协作”。
4. Agent 代理从“演示”进入“可控试运行”，开始成为岗位和流程的一部分。
5. 竞赛、培训、课程、认定核心业务开始统一到同一技术栈和同一数据体系。
6. 工业仿真开始具备内部自研维护能力，不再完全依赖外包。
7. 公司内部知识库开始成为 AI 助手、Agent 代理、项目复盘和员工培训的统一资料底座。
8. 全体员工开始具备基础 AI 工作能力，重点岗位开始有对应 Agent 代理辅助工作。
9. 平台开始从“功能系统”升级为“AI + Agent 参与业务执行的系统”。

## 十一、三个月后要完成的结果

三个月结束后，公司不是只完成一份方案，而是要完成一批可以被管理层检查、可以被业务部门使用、可以继续迭代的实际成果。

1. 完成 Agent 面板第一版：管理层打开 Agent 面板，可以查看重点项目进度、负责人、延期风险、待决策事项、业务数据、外包收回进度和下一步动作。
2. 完成公司内部知识库第一版：制度流程、项目资料、课程资料、题库资料、客户资料、系统文档、外包交付资料、工业仿真资料完成初步入库，并能被 AI 和 Agent 调用。
3. 完成内部知识库与业务流程搭建：把培训、竞赛、认定、课程、项目管理、营销推广、工业仿真等业务流程拆成节点、模板、检查项、责任人和输出物，沉淀到知识库和 Agent 面板中。
4. 完成外包项目收回清单和第一批交付接管：明确哪些源码、数据库、账号、接口、部署文档、服务器权限、仿真工程文件和模型资产已经收回，哪些还未收回，形成责任人和时间表。
5. 完成公司各业务全面接近 AI 化：培训、竞赛、认定、课程、营销推广、项目管理、数据报表、工业仿真等核心业务，都要完成至少一个 AI 辅助场景，不再只停留在人工处理。
6. 完成全员 AI 能力接入：通过接入 ChatGPT 等大模型能力和公司内部知识库，让全体员工具备基础 AI 办公能力，重点岗位具备岗位 AI 助手。
7. 完成核心业务 AI 化试点：形成材料检查、课程生成、题库辅助、项目周报、会议纪要、客户方案、营销文案、通知催办、复盘报告等一批可直接使用的 AI 成果。
8. 完成 2-5 个 Agent 试点闭环：例如项目周报 Agent、课程生成 Agent、材料检查 Agent、人员协同 Agent、营销跟进 Agent，能够在人工确认下完成生成、提醒、催办、通知、反馈和留痕。
9. 完成平台 AI 与 Agent 接入试点：培训、竞赛、认定、课程、营销、项目管理、数据报表、工业仿真等平台开始接入 AI 助手或 Agent 代理，具备生成、检查、提醒、统计、催办和复盘能力。
10. 完成旧 PHP 系统 Java 重构路线和试点：旧 PHP 系统完成模块梳理和 Java 重构路线图，至少选定 1-2 个模块做 AI 辅助重构试点，并与原 Java 平台形成对接方向。
11. 完成竞赛系统重构范围和核心数据设计：理论考试、实操考试、试卷试题、实操题、操作项、参赛人员、考评人员等核心模块纳入统一重构范围，形成数据结构和接口设计。
12. 完成工业仿真收回和自研样板：至少收回一个典型工业仿真项目的工程文件、模型资产、交互脚本和部署文档，并选一个铝电解或实操考试流程拆成标准化仿真流程模板。
13. 完成开发流程重构机制：建立小需求、大需求、模糊需求三类处理机制，形成“小步上线、周周验收、边用边改”的开发节奏，避免再次出现“开发完成却用不起来”。
14. 完成部门 AI 化启动：各部门至少建立自己的知识库、常用模板和 AI 助手使用场景，开始把重复写材料、查资料、催进度、做汇总的工作交给 AI 辅助。
15. 完成管理层可检查的成果清单：三个月结束时，所有成果都要能被检查，包括 Agent 面板、知识库、外包收回清单、系统试点、AI 生成成果、Agent 执行记录、开发看板、仿真样板和后续迭代计划。
16. 形成下一阶段自研和 AI 化路线图：明确第二阶段继续做什么，哪些系统继续重构，哪些业务继续 AI 化，哪些 Agent 进入半自动执行，哪些外包继续收回，哪些能力可以对外形成产品或服务。

一句话总结：

三个月计划的核心，不是展示 AI 概念，而是完成 Agent 面板、内部知识库、业务流程、全员 AI 能力接入、平台 AI 与 Agent 接入、外包收回、AI 试点、Agent 闭环、系统重构和工业仿真样板，让公司从“外包交付、人工推进、资料分散、人盯流程”，转向“内部可管、系统可用、知识可沉淀、流程推着人走、AI 负责生成检查提醒汇总、Agent 可执行、员工有 AI 能力”。
