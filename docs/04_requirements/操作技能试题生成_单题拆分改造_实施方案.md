# 操作技能试题生成：单题拆分改造实施方案

> 版本：v1.0（2026-10-29）
> 状态：已确认，待实施（交付实施 agent）
> 关联：`docs/04_requirements/客观题答案AI检查_一期实施方案.md`（无关，仅同域）；提交 `a0e73d73`（数组模式修正重试，本方案在其之上演进）
> 实施范围：`services/platform-api` 的 `exam/skillgen` 包 + 对应单测；**无数据库结构变更、无前端变更**

## 1. 背景与根因定案

### 1.1 故障现象

生产环境操作技能试题生成（skillgen）频繁失败：

```
WARN c.g.p.e.s.s.SkillGenBatchService - 考评点生成失败：batchId=..., point=A-A-001,
err=模型输出不是试题数组（已调用 3 次，最后错误：模型输出不是试题数组）
```

生产统计（2026-10-29 platform.log）：skillgen LLM 请求 82 次，考评点失败 64 次；数组模式修正重试（`a0e73d73` 上线）仅救回 1 次。

### 1.2 根因（真实 GLM 探针定案，2026-10-29）

用生产日志提取的原始请求体 + 真实 GLM key 做对照探针：

| 探针 | 配置 | 结果 |
|---|---|---|
| 探针 1（约 16:00）变体 A = 生产配置（json_object + effort=low + max_tokens=8192） | 5 题数组 | **成功**，输出 3349 tokens |
| 探针 2（约 16:10）变体 A（同配置同 prompt）× 8 次 | 5 题数组 | **8/8 全部失败**：单对象，completion 556~691（与生产失败完全吻合） |
| 探针 2 同时段变体 F（只生成 1 题）× 3 次 | 单题对象 | **3/3 全部成功** |

**结论**：GLM-5.3-flash 服务端对"一次调用输出 N 题 JSON 数组"的任务结构理解不稳定，**间歇性塌缩成单题对象**；与代码、prompt 措辞、json_object、reasoning_effort、max_tokens 均无关。修正重试（回喂失败输出 + 明确指令）无法纠正服务端的结构倾向。

**同时段单题模式 100% 成功**——模型最稳定的输出形态就是单题对象。本方案顺应该形态，把"数组生成"问题转化为"单题生成 + 组装"问题。

### 1.3 为什么不用其他方案

| 方案 | 否决理由 |
|---|---|
| 继续靠修正重试 | 生产实测 64 失败仅 1 救回，无效 |
| 对象包装契约 `{"questions":[...]}` | 没解决"模型只写 1 题"的倾向，questions 里可能仍只有 1 题 |
| 换大模型（glm-5.3 非 flash） | 成本高、需重新标定；且未证明该模型无同类问题 |
| 调 reasoning_effort=high | 探针 1 单次成功不足为证，未重复验证，不作定案 |

## 2. 现状架构（改造前）

```
SkillGenBatchService.runBlock (SkillGenBatchService.java:417)
  └─ aiService.generateForPointWithRepair(..., expectedCount=5)
       ├─ generateForPoint(...)            // 1 次 LLM 调用（jsonMode=true）
       ├─ parseQuestions(content)          // 期望 5 题数组；白名单键 questions/data/items/result
       ├─ 数量 != 5 或解析失败 → 回喂失败输出重试，最多 2 次（共 3 次调用）
       └─ 返回 SkillGenGeneration(items, content, attempts, usage累计)
  └─ validator.validateAll(questions, 5)   // 题数 + 逐题规则 + 查重
  └─ saveDrafts(...) / incrementDone / incrementFailed
```

问题集中在 `generateForPointWithRepair` 的"1 次调用要 5 题数组"契约。改造**只动这一层及其 prompt**，`runBlock` 对外接口、validator、saveDrafts、熔断、多轮补跑、`DISPATCHED_NODES` 全部不变。

## 3. 目标架构（单题拆分）

```
SkillGenBatchService.runBlock（仅日志口径微调，其余不变）
  └─ aiService.generateForPointWithRepair(..., expectedCount=5)   // 签名不变，内部改为拆分
       ├─ 循环 n = 1..5（串行）：
       │    ├─ buildSingleUserPrompt(point, l2, l1, n, 5, 已生成题名列表)
       │    ├─ generateForPoint(...)                // 1 次 LLM 调用，产出 1 题
       │    ├─ parseSingleQuestion(content)          // 单对象 / 1元素数组 / 包装对象取第1个
       │    ├─ validator.validate(item)              // 逐题规则（五要素/配分/步长/保底…）
       │    ├─ 与已生成题目查重（checkDuplicates）
       │    ├─ 任一失败 → 回喂失败输出 + 错误原因，重试该题，最多 2 次（该题共 3 次调用）
       │    └─ 成功 → 加入 items，记录题名供后续题目回喂
       ├─ 全部 5 题成功 → 返回 SkillGenGeneration(items, 末次content, 总调用次数, usage累计)
       └─ 某题 3 次仍失败 → 抛 BusinessException("第 N 题生成失败：原因（该题已调用 3 次）")
```

**关键性质**：
- 每次 LLM 调用只要求输出 **1 个 JSON 对象**（模型最稳定形态），从根上规避数组塌缩。
- 逐题即时校验 + 逐题重试，失败定位到具体某题，不再"5 题整体报废"。
- 串行而非并行：后续题目的 user prompt 需要"已生成题名列表"来防重复，串行才能携带该上下文。
- `runBlock` 对外拿到的仍是 5 题 + usage 累计，下游全部不变。

## 4. 详细设计

### 4.1 Prompt 改造（`SkillGenPromptBuilder`）

**system prompt**：命题硬性要求 1~8 条**原样保留**（这是命题质量的核心，不能动）。仅改"输出要求"段与示例：

- 输出要求段改为：
  ```
  输出要求：只输出 1 个 JSON 对象（一道完整试题的本体），不要输出 JSON 数组、不要 questions 等包装字段、
  不要输出任何其他文字、解释或 markdown 围栏。对象结构：
  {"name":"试题名称","durationMinutes":整数分钟,"examForm":"实操",
   "sitePrepare":{"equipment":[{"name":"…","unit":"…","qty":"…"}]},
   "examineePrepare":"考生自带清单","requirements":"具体考核要求","negatives":"否定项说明",
   "scoring":[{"item":"评分要素","score":"配分","scoreDesc":"评分标准","maxDeduct":"最大扣分","step":"步长"}]}
  scoring 中的配分/最大扣分/步长用数字字符串；配分合计必须为 100。
  ```
- 示例改为**单个试题对象**（取现 2 元素示例中的第 1 题，去掉数组 `[]`），示例说明改为"输出示例（仅示范格式与颗粒度，内容不得照抄）"。

**user prompt**：新增 `buildSingleUserPrompt(point, l2, l1, n, total, generatedNames)`：

```
考评点代码：A-A-001
考评点名称：…
重要程度：X
所属考评范围（一级）：…，权重 …%，选考方式 …
所属考评范围（二级）：…，权重 …%，选考方式 …
技能要求原文：
…
请为该考评点生成第 {n} 道完整试题（共 {total} 道；每道均含准备要求、考核试题、评分标准三部分；
本题分值 100 分）。本题是第 {n} 道，必须与该考评点的其它试题覆盖不同工况/侧面/参数组合，不得同义改述。
已生成试题名称（禁止重复或同义改述）：{name1}、{name2}、…      // n=1 时省略此行
只输出 1 个 JSON 对象（该题本体），不要数组、不要其他文字。
```

`buildUserPrompt`（旧的 5 题数组版）可保留供对照测试，或标记 `@Deprecated` 待清理；一期保留不删，避免影响既有测试断言。

### 4.2 AI 服务（`SkillGenAiService` / `SkillGenAiServiceImpl`）

**接口签名不变**：
```java
SkillGenGeneration generateForPointWithRepair(Long tenantId, String baseUrl, String apiKey,
    String modelId, String thinking, String reasoningEffort, int maxTokens,
    String systemPrompt, String userPrompt, int expectedCount);
```
`userPrompt` 参数改为**仅作基础信息模板**（实现内部按 n 重新构建单题 prompt；见 4.4 的调用方配合）。

**新增/调整**：
- `parseSingleQuestion(String rawContent)` → `SkillQuestionItem`：
  - 复用 `extractJson` 剥围栏/杂文字。
  - 接受：单对象（主形态）；1 元素数组（取 `[0]`）；白名单包装对象（`questions/data/items/result` 取数组第 1 个）。
  - 其余（空内容、多元素数组、非 JSON）抛 `BusinessException(BAD_GATEWAY, "模型输出不是单题对象")`。
  - 建议作为接口 `default` 方法或实现内 public 方法，便于单测直接调用。
- 单题重试逻辑（每题最多 `MAX_REPAIR_ATTEMPTS + 1 = 3` 次调用）：
  - 触发条件：`parseSingleQuestion` 失败；或 `validator.validate(item)` 非空；或与已生成题目查重命中。
  - 重试 prompt = 当前题 user prompt + `【上次输出有误】{原因}` + 回喂失败输出（截断 4000 字符）+ "请重新输出 1 个 JSON 对象（该题本体），不要数组。"
  - 3 次仍失败 → 抛 `BusinessException(BAD_GATEWAY, "第 " + n + " 题生成失败：" + 原因 + "（该题已调用 3 次）")`。
- `generateForPointWithRepair` 返回的 `attempts` 语义改为**总 LLM 调用次数**（无重试时 = expectedCount = 5）；`usage` 为全部调用累计；`content` 为末次成功输出（仅审计用途）。
- `parseQuestions`（数组版）保留，不删（兼容与既有测试）。

**逐题校验**：复用现有 `SkillQuestionValidator`：
- `validate(item)` 做单题规则校验（五要素非空、考生准备保底、否定项标准表述、时长 5~240、评分 3~10 行、配分=最大扣分=5 的倍数、步长=5、扣分项数=maxDeduct/5、配分合计=100）。
- `checkDuplicates(items_so_far + item)` 做名称 + 名称|要求组合查重。
- 注意：单题阶段**不做** `validateAll` 的"题数=5"检查（那是组装后由 runBlock 的 `validateAll` 兜底）。

### 4.3 差异化与查重

- 每次调用 user prompt 附"已生成试题名称"列表（n=1 为空），引导模型避开重复。
- 生成后立即 `checkDuplicates`；命中则该题重试（重试 prompt 中再次强调已生成题名）。
- 组装 5 题后，`runBlock` 现有 `validator.validateAll(questions, 5)` 仍做最终整体校验（含查重），双保险。

### 4.4 调用方（`SkillGenBatchService.runBlock`）改动

- 仍调用 `generateForPointWithRepair(...)`，参数不变；其中 `userPrompt` 传新增的
  `SkillGenPromptBuilder.buildBaseUserPrompt(point, l2, l1)`（仅考评点基础信息，不含输出指令）。
- **实现内部**按 n 调用 `buildSingleUserPrompt(baseInfo, n, total, generatedNames)` 拼装单题 prompt。
  - 实施取舍：方案原写"传 `buildUserPrompt(...)` 后由实现内部忽略其 5 题数组指令"。实际改为**新增无指令的
    `buildBaseUserPrompt`**——若传入仍带"只输出 JSON 数组，恰好 5 个元素"的旧 prompt，会与单对象契约
    直接冲突，模型可能被拉回数组形态。`buildUserPrompt` 保留（`@Deprecated`）仅供对照测试。
  - 备选（更显式）：`runBlock` 改传 `point/l2/l1` 给 AI 服务新参数；为控制改动面未采用，已在 JavaDoc 写清。
- 日志口径：`gen.attempts()` 正常 = 5，> 5 表示有重试。把现有"修正重试后成功 attempts>1"改为：
  ```java
  if (gen.attempts() > SkillBlueprintApplicationService.PER_POINT_QUOTA) {
    log.info("考评点单题拆分含重试完成：batchId={}, point={}, 总调用={}",
        batch.getId(), point.getFullCode(), gen.attempts());
  }
  ```
- 成功/失败计数、usage 累计、`saveDrafts`、熔断、多轮补跑逻辑全部不变。

### 4.5 配置与性能

- **无需数据库变更**。`V20261029_004`（max_tokens=16384）保留即可；单题输出 ~800 tokens，16384 或 8192 都够用。
- `thinking=enabled + reasoning_effort=low` 保持：单题思考需求低，low 足够且更快；**不要**为求稳盲目调 high（成本高且未证明必要）。
- 耗时：单题每次约 10s（low），5 次串行约 50s，与数组模式（~60s）相当。
- 成本：system 前缀（命题规则 + 输出契约 + 示例）5 次相同，命中 GLM prompt 缓存后边际成本低；输出合计约 4000 tokens，与数组模式相当。探针需记录 `cached_tokens` 验证缓存命中。

## 7. 灰度与回滚

- **灰度**：部署后先跑 1 个真实批次观察日志（应出现"单题拆分"相关日志、无批量塌缩失败），再放量。
- **旧批次兼容**：数组模式失败的旧批次（如 2115641600602492929）可直接用新代码"重试失败块"，单题拆分对旧批次同样有效，无需数据迁移。
- **回滚**：异常时回滚 jar 至上一版本即可（旧代码与 prompt 在 git 历史）；新旧代码共用同一套 validator/表结构，无数据兼容问题。

## 8. 风险与注意事项

1. **串行耗时**：5 次串行约 50s/块，与数组模式相当；不要为提速改并行（会失去"已生成题名"上下文导致重复）。
2. **查重依赖模型配合**：回喂题名只能降低重复概率，最终靠 `checkDuplicates` + 重试兜底；若某题反复重复导致 3 次失败，该块失败属正常防守，可重试。
3. **prompt 缓存**：成本优势依赖 GLM 缓存命中，探针必须记录 cached_tokens；若缓存未命中导致成本明显上升，再评估精简 system 前缀。
4. **不要动命题规则 1~8 条**：那是命题质量的核心，本方案只改输出契约与示例。
5. **attempts 语义变化**：从"重试次数"变为"总调用次数"，前端/导出若展示该字段需同步口径（检查 `SkillGenBatchVO` 与导出是否用到 attempts；若只用 usage 则无需改）。
6. **保留数组解析**：`parseQuestions` 不删，供兼容与对照；`buildUserPrompt` 旧 5 题版一期保留。
7. **密钥纪律**：探针真实 key 从测试库读取，仅用于诊断调用，不入仓库、不打印、不写入日志文件。

### 10.4 成本与耗时偏差（可解释）

- **每块 token**：单题模式 13.8k~18.2k；数组模式生产单次成功约 4.8k（prompt 1,485 + completion 3,349）。按"每个成功点"折算，数组模式生产样本（82 请求 / 18 个成功点）≈ 9.6k，单题模式 ≈ 15.3k，**约 1.6 倍**。
- 差异全部来自输入侧：system 前缀（命题规则 + 契约 + 示例，约 1,480 tokens）由 1 次变 5 次；其中 38.8% 命中 GLM prompt 缓存。输出侧两边相当（单题 5 次合计 completion ≈ 5.1k，数组 3.3k，单题内容更详细）。
- 换来的是确定产出：数组模式生产 64/82 点归零（每点 3 次调用全废），单题模式 15/15 且失败定位到具体题号。**按"每个可用试题块"的有效成本计，单题模式不高于数组模式**。
- **耗时**：单题约 24s/题（effort=high），每块 108~141s，较数组模式（~60s）约 2 倍；块并发 5 不变，23 点批次约 10 分钟可完成。若要提速可把该模型配置的 `reasoning_effort` 降到 low（方案 §4.5 口径），本次未改配置。
