## 三、任务目标

在 `services/platform-api` 的 `com.guoyu.platform.competition` 领域内完成：

1. 从当前租户、当前赛事工种对应的已终审题库中选择客观题。
2. 按冻结模板创建 A、B 两套独立版本试卷。
3. 把题干、选项、标准答案、分值、题型、判分规则和来源审计字段复制为不可变快照。
4. 校验 A/B 卷采用同一模板、同一时长、同一满分，并保存等值性审核记录。
5. 为同一工种创建多个不重叠的理论考试时段，每个时段固定绑定一个已发布试卷版本。
6. 将合格选手固定分配到一个场次和一个试卷版本，场次开放后禁止随机换卷。
7. 允许选手通过独立竞赛选手 Token：
   - 查看本人的考试分配。
   - 开始本人考试。
   - 仅获取本人试卷的无答案题目投影。
   - 暂存本人答案。
   - 幂等交卷并取得服务端判分结果。
8. 自动判分后，在同一事务内生成或返回一个可追溯的、已确认的 `theory` 类型 `competition_score_source` 修订。
9. 所有后台写操作记录操作日志；选手答题、开始和交卷记录独立审计字段、请求 ID 和服务端时间。

## 四、冻结业务规则

### 1. 理论模板

仅支持以下两个模板：

| 模板 | 时长 | 单选 | 多选 | 判断 | 总分 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `THEORY_90` | 90 分钟 | 60 题 × 1 分 | 20 题 × 1 分 | 40 题 × 0.5 分 | 100 |
| `THEORY_120` | 120 分钟 | 120 题 × 0.5 分 | 20 题 × 1 分 | 40 题 × 0.5 分 | 100 |

规则：

1. 模板来自当前范围唯一已发布的 `competition_score_rule`，不得由请求临时覆盖。
2. 试卷发布前必须同时校验题型、题量、单题分值、总分和考试时长。
3. 题库原始 `score` 不能覆盖模板规定分值；竞赛快照分值按模板冻结。
4. 只允许 `single`、`multi`、`judge` 三种客观题进入本任务试卷。
5. `answer`、`analysis`、`cal`、`essay`、`explain`、`fill`、`drafting` 等主观或非冻结题型不得进入本任务试卷。

### 2. 题库来源与答案适配

1. 只允许选择当前租户、未删除、有效且 `final_check_status = 1` 的题目。
2. 题目必须可经 `exam_knowledge_structure.course_id → exam_course.work_type_id` 追溯到当前 `competition_event_work_type.work_type_id`。
3. 题库当前 `answer` 为 JSON 数组，常见元素包含 `content`、`isCorrect`，部分还包含 `score`。必须建立明确的题库答案适配器：
   - 校验 JSON 类型和必要字段。
   - 为每个选项生成稳定的快照选项键，不把“数组位置碰巧相同”当作长期答案标识。
   - 从 `isCorrect` 生成标准答案集合。
   - 单选必须恰好 1 个正确项。
   - 多选必须至少 2 个正确项。
   - 判断必须恰好 1 个正确项且能投影为两个明确选项。
   - 空数组、重复键、无法识别的正确项、题干为空或答案格式错误时拒绝入卷。
4. 快照保存题库来源 ID、来源类型、来源组织、出题人、原题更新时间或可用的来源版本标识，便于审计。
5. 题库原记录后续修改、删除或重新审核，不得改变已发布试卷快照。

### 3. A/B 卷

1. A、B 卷分别具有独立的快照 ID 和版本号。
2. 同一赛事、赛段、赛事工种、规则版本、卷别下只能有一个当前发布版本；重做试卷生成新版本，不覆盖旧版本。
3. 发布后禁止增删题目、修改题序、分值、标准答案或判分规则。
4. A/B 卷发布并用于同一榜单前，必须存在一条已批准的等值性审核记录。
5. 等值性审核至少校验并记录：
   - 同一赛事、赛段、赛事工种和规则版本。
   - 一份 A 卷和一份 B 卷。
   - 同一理论模板。
   - 同一考试时长。
   - 同一理论满分 100。
   - 审核状态、审核人、审核意见和审核时间。
6. 业务未冻结 A/B 卷题目重合率、难度分布阈值和自动等值算法，本任务不得自行增加阻断规则；可保存统计摘要供人工审核。

### 4. 分时场次与固定分配

1. 场次范围为同一赛事、赛段和赛事工种。
2. 每个场次固定绑定一个已发布且已通过 A/B 等值性审核的试卷版本。
3. 场次至少包含名称、顺序号、开始时间、结束时间、容量、状态和绑定试卷。
4. 同一赛事、赛段、赛事工种的场次时间不得重叠。
5. 场次容量必须大于 0；有效选手分配数不得超过容量。
6. 同一选手在同一赛事、赛段、赛事工种只能有一个当前有效理论场次分配。
7. 只有资格审核通过、已生成 `contestant` 赛事成员、工种已确认且与场次工种一致的选手可以分配。
8. 场次开放后，已分配选手的场次和试卷版本不可直接修改；更正必须在未开始前撤销旧分配并新建修订，保留原因和操作者。
9. 不实现随机换卷；选手开始考试时读取预先固定的 `paper_snapshot_id`。

### 5. 作答、交卷与自动判分

1. 每个有效分配最多产生一个当前有效考试 attempt。
2. 开始考试由服务端创建或幂等返回 attempt，记录服务端开始时间。
3. 选手只能访问与本人 `playerId` 对应的 registration、contestant member 和有效分配。
4. 答案暂存只允许在 attempt 可答状态进行；请求必须包含题目快照 ID 和客户端请求 ID。
5. 同一客户端请求 ID 重试不得产生重复答案记录或错误版本推进。
6. 服务端只接受当前试卷快照内的题目；跨卷题目、其他选手 attempt、其他租户、其他场次一律拒绝并记录 warn。
7. 交卷请求必须包含幂等请求 ID。首次成功交卷后：
   - attempt 锁定。
   - 后续答案保存被拒绝。
   - 重复交卷返回相同 attempt、总分和成绩来源 ID。
8. 判分全部在服务端执行，复用 `CompetitionTheoryObjectiveScorer`：
   - 单选和判断按标准答案完全匹配。
   - 多选按答案集合完全一致。
   - 漏选、错选、多选和空答案得 0 分。
   - 未作答题得 0 分。
9. 保存逐题结果：标准答案快照引用、选手答案快照、题目分值、实际得分和判分规则版本。
10. 总分使用 `BigDecimal` 汇总，正常模板结果必须在 0–100。
11. 判分成功后创建 `competition_score_source`：
   - `source_type = theory`
   - `raw_score = attempt 总分`
   - `confirmation_status = confirmed`
   - `source_system = competition-theory-exam`
   - `source_reference = attempt 的稳定引用`
   - 引用当前赛事、赛段、赛事工种、选手和已发布规则版本
   - 修订号和 current 约束复用 `COMP-SCORE-02`
12. attempt 与理论成绩来源必须双向可追溯。重复交卷不得创建第二个当前理论成绩来源。
13. 本任务只验证正常开放时间内的显式开始和显式交卷。超时自动交卷、宽限时长、补考、断网恢复和管理员代交规则未冻结，不得自行实现。

## 五、最小数据模型

先检查已有表和命名，再设计最小完整模型。建议覆盖以下概念，名称可按项目规范调整，但语义不得缺失：

1. `competition_theory_paper_snapshot`
   - 赛事、赛段、赛事工种、评分规则、模板、卷别 A/B。
   - 版本号、时长、题目数、总分、状态。
   - 发布人、发布时间、来源摘要。
2. `competition_theory_paper_question`
   - 试卷快照、题库来源 ID、题序、题型。
   - 题干快照、选项快照、标准答案快照。
   - 题目分值、判分规则代码/版本。
   - 来源组织、出题人和来源审计字段。
3. `competition_theory_equivalence_review`
   - A 卷、B 卷、模板、审核状态。
   - 统计摘要、审核意见、审核人和审核时间。
4. `competition_theory_exam_session`
   - 赛事、赛段、赛事工种、试卷快照。
   - 场次号、名称、开始/结束时间、容量和状态。
5. `competition_theory_candidate_assignment`
   - 场次、试卷快照、contestant member、registration/player 引用。
   - 分配修订、当前标识、状态、分配/撤销原因和时间。
6. `competition_theory_attempt`
   - 分配、选手、场次、试卷快照、规则版本。
   - 状态、开始/交卷/判分时间、总分。
   - 交卷幂等键、成绩来源 ID、锁定版本。
7. `competition_theory_answer`
   - attempt、题目快照、选手答案。
   - 保存版本、最后请求 ID、最后保存时间。
   - 判分状态、题目分值和实际得分。

数据库必须满足：

- 所有新增业务实体 `extends BaseEntity`。
- 每张新增业务表完整包含 `id、tenant_id、deleted、created_by、updated_by、created_at、updated_at`。
- 主键和所有新增业务引用统一为 `BIGINT`；引用旧题库的 `INT` ID 时，在 competition 快照表中使用可容纳其值的明确字段并做好转换，不修改旧题库主键类型。
- 分值统一使用 `DECIMAL`，不使用浮点列。
- JSON 快照字段使用 MySQL `JSON` 或项目内统一序列化文本；若使用 JSON，必须验证结构且禁止把标准答案暴露到选手 VO。
- 对试卷版本、当前发布卷、场次号、当前选手分配、attempt、题目答案和幂等键建立必要唯一约束及索引。
- 多租户由 MyBatis-Plus 插件处理，普通业务查询不得手拼 `tenant_id`。
- 不修改任何已应用 Flyway，只新增迁移。
- 权限种子必须幂等，并将新权限授予平台管理员 `role_id = 2000`；不得只建权限码不授权角色。

## 六、应用服务与 API 边界

### 1. 后台 API

在现有竞赛后台鉴权体系中提供最小 API，路径可按项目现有风格调整：

- 创建试卷草稿快照。
- 校验试卷模板。
- 发布试卷新版本。
- 提交/审批 A/B 等值性审核。
- 创建、更新未开放场次。
- 批量分配合格选手。
- 查询试卷、场次、分配和考试进度。

后台写接口必须：

- 使用 `@PreAuthorize`。
- 校验租户、赛事组织范围和成绩域就绪状态。
- 记录操作日志。
- 对无权限、跨组织、跨工种、无效规则版本和发布后修改打印 warn/error。

建议权限码按现有竞赛规范落地并避免魔法字符串，例如：

- `competition:theory-paper:view`
- `competition:theory-paper:manage`
- `competition:theory-session:view`
- `competition:theory-session:manage`
- `competition:theory-result:view`

最终命名必须先检查仓库已有权限码，避免重复或不一致。

### 2. 选手 API

放在现有独立竞赛选手 Token 保护范围 `/api/competition/player/**` 下：

- 查询本人理论考试分配。
- 开始本人考试。
- 获取本人无答案题目投影。
- 保存本人单题答案。
- 交卷。
- 查询本人交卷结果。

选手 API 必须满足：

1. 只接受 `CompetitionPlayerPrincipal`，平台管理员 Token 不能冒充选手。
2. 从当前 player 身份反查 registration 和 contestant member，不接受客户端提交任意 contestant ID。
3. 每次访问校验当前租户、本人分配、场次、试卷和 attempt。
4. 题目投影只返回题目 ID、题型、题干、选项、题序和分值。
5. 严禁返回标准答案、解析、题库来源组织、出题人、另一卷信息和其他选手状态。

## 七、事务、幂等与并发正确性

本任务不做容量优化，但必须保证单实例和数据库层面的基本正确性：

1. 创建试卷快照、发布试卷、分配选手、首次开始、交卷判分和成绩来源落库分别定义清晰事务边界。
2. 交卷状态转换使用条件更新、乐观锁或等价手段，避免两个并发请求产生两次有效交卷。
3. 幂等键必须与租户、attempt 和操作类型共同约束，不能跨用户碰撞。
4. Mapper 返回值先判空。
5. 本任务若不使用异步线程，不得为了“性能”自行增加线程池。
6. 若确有异步代码，必须在请求线程捕获 tenantId/playerId/userId 并通过参数传递，Worker 线程独立设置和清理 `TenantContextHolder`，全调用链禁止直接读取 SecurityContext。
7. 题目标准答案只在服务端判分事务中读取，日志不得打印标准答案或完整选手答案。

## 八、测试与验收

至少新增并通过以下测试。

### 1. 模板与题库适配

- `THEORY_90` 严格校验 `60/20/40` 和 `1/1/0.5`，总分 100。
- `THEORY_120` 严格校验 `120/20/40` 和 `0.5/1/0.5`，总分 100。
- 题量、题型、单题分值、时长或总分任一不符时拒绝发布。
- 非终审、停用、已删除、跨租户或跨工种题目拒绝入卷。
- 旧题库答案 JSON 正常解析；空数组、非法 JSON、缺少 `isCorrect`、单选多个正确项等异常被拒绝。

### 2. 快照不可变与 A/B 等值

- 发布后修改题目、答案、分值或题序被拒绝。
- 题库源题后续修改不影响已发布快照。
- A/B 卷模板、时长或满分不一致时不能批准等值性。
- 审核批准后可用于场次；未批准或被拒绝时不能开放场次。
- 重做试卷生成新版本，旧版本仍可查询。

### 3. 场次与选手分配

- 同一工种可创建两个不重叠时段，分别固定 A、B 卷。
- 场次重叠、容量小于分配人数、跨工种试卷绑定被拒绝。
- 合格且工种已确认选手可以分配。
- 资格不通过、无 contestant member、工种不一致或重复当前分配被拒绝。
- 场次开放后直接换卷被拒绝。

### 4. 选手安全

- 未登录返回 401。
- 平台 Token 不能访问选手考试 API。
- 选手只能读取本人分配、attempt 和题目投影。
- 尝试读取其他选手、其他卷、跨租户或跨工种数据被拒绝并记录 warn。
- 题目投影序列化测试明确断言不含标准答案、解析和来源审计字段。

### 5. 答题、交卷与判分

- 开始考试幂等返回同一 attempt。
- 单题保存幂等；跨卷题目拒绝。
- 交卷后继续保存答案被拒绝。
- 单选、判断完全匹配得分，不匹配为 0。
- 多选顺序不同仍得满分；漏选、错选、多选和空答案均为 0。
- 未作答题按 0 分计入总分。
- 正常模板总分正确汇总为 0–100 的 `BigDecimal`。
- 两次相同交卷请求返回同一结果。
- 两个并发交卷请求最多生成一个已确认理论成绩来源。
- `competition_score_source` 的赛事、赛段、工种、选手、规则版本、来源类型、分数和 attempt 引用正确。
- 已确认理论来源旧修订不被覆盖；需要重考的规则未冻结，本任务不得通过测试偷偷实现覆盖逻辑。
