# 默认模板导出 优化实现方案

> 版本：v1 · 2026-09-15 · 状态：待评审

## 一、背景与问题

### 1.1 线上报错现象

`POST /api/training/sign-up-people/export/default-template/check` 返回：

```json
{
  "data": {
    "url": null,
    "jindu": "15/15",
    "error": 1,
    "msg": "导出完成但未找到压缩包。已查找=/opt/guoyu-platform/storage/cdn/down/2026强强碳素自费认定中级班-资料收集_t285.zip（down目录存在）"
  }
}
```

任务 `endtime>0`、`errorMsg` 空、`jindu=15/15`（打包完成），但 `result_file` 为空、磁盘 zip 找不到。

### 1.2 根因（已通过日志与 git 历史定位）

`8170e2a`（Sep 14 10:17，正常）之后为"防旧缓存下载"做了三次提交，叠加引入回归：

| 提交 | 改动 | 引入的回归 |
|---|---|---|
| `aa7d7fb` 14:51 | zip 带 `_t{taskId}` 后缀；复用分支重新提交；新增 PATH A 早返回 | 多实例下重新提交导致同 taskId 并行打包；PATH A 早返回不写 `result_file` |
| `f767b5e` 17:53 | 新增 `result_file` 列；`resolveExportZip` 收窄到只认 `*_t{taskId}.zip` | 兜底匹配范围缩小，跨实例磁盘落空就彻底找不到 |
| `b09fb13` 09:25 | `result_file` 改为上传 COS 后才写；check 只认 `/api/files/` URL | PATH A/B 早返回时 `result_file` 永远空，check 既拿不到 URL 又磁盘落空 |

**直接触发**：多实例部署 + `runningExportTaskIds` 是进程内集合（不跨实例）→ 两台机器并行打包同一 taskId → 后完成者走 PATH A 早返回不写 `result_file` → check 落在该实例时 `result_file=null`，磁盘扫描又跨实例落空 → 报"未找到压缩包"。

日志证据（`platform.log`）：
```
09:09:32.028 checkExport: 等待产物可见 taskId=277 age=0s resultFile=null
09:09:32.254 doRunExport(331): 结束时任务已成功，保留 zip taskId=277
```
277/279 靠本机磁盘兜底成功；285 的 check 落在无 zip 的实例上 → 失败。

### 1.3 `8170e2a` 为何没问题

- 无 `result_file` 列，成功标志就是 `endtime>0 && !errorMsg`；
- `resolveExportZip` 宽匹配 `signUp.files` 里任意 `.zip`；
- 无 PATH A/B 并发取消删 zip 逻辑。

## 二、优化目标

1. **正确性**：保证文件一定能正常导出下载，多实例下不丢 `result_file`。
2. **大数据量**：数百上千人也能正常导出，不 OOM、不超时。
3. **速度**：在正确性前提下尽可能快。

## 三、实现方案（分优先级）

### P0-1 `result_file` 两段式写入（修复线上报错，最关键）

**文件**：`TrainSignUpDefaultTemplateExportService.java` `doRunExport`

**现状**：打包完成 → 上传 COS → 成功后才 `set(result_file, /api/files/{id}/download)`。上传失败/PATH A/B 早返回时 `result_file` 永远空。

**改为两段式**：
1. 打包完成、校验 zip 存在后，**立即** `UPDATE ... set(result_file=zipRelative)`（磁盘相对路径 `down/xxx_t285.zip`），同时 `set(endtime, endSec)`、`set(errorMsg, null)`。此刻 check 即可从磁盘兜底下载。
2. 随后上传 COS，成功后**再** `UPDATE ... set(result_file=/api/files/{id}/download)`（覆盖为下载 URL，跨实例可访问）。
3. 上传 COS 失败不回滚 `result_file`（保留磁盘路径，仍可下载），仅记 warn 日志。

**check 侧**：`isStoredDownloadUrl` 优先返回下载 URL；否则走磁盘扫描返回 `publicUrl(zipRelative)`。两种都认。

**预期效果**：即使 COS 上传失败/被并发取消，磁盘上有 zip 就能下载，不再出现"导出完成但未找到压缩包"。

### P0-2 PATH A/B 早返回时补写 `result_file`

**文件**：`TrainSignUpDefaultTemplateExportService.java` `doRunExport` PATH A（`:320-329`）与 PATH B（`:364-373`）

**现状**：PATH A/B 发现 `endtime>0` 时直接 return，不写 `result_file`。

**改为**：早返回前判断 `result_file` 是否为空，若空且本机 zip 存在，补写 `result_file=zipRelative` 再 return。

```java
// PATH A 伪码
if (latest.getEndtime() > 0) {
  if (hasText(latest.getErrorMsg())) {
    deleteQuietly(zipAbsolute);
  } else if (!hasText(latest.getResultFile())) {
    // 任务已被别处置成功但 result_file 仍空，补写磁盘路径
    taskMapper.update(null, new LambdaUpdateWrapper<>()
        .eq(getId, taskId).eq(getResultFile, "")  // 仅当空时补
        .or(w -> w.isNull(getResultFile))
        .set(getResultFile, zipRelative));
  }
  return;
}
```

PATH B 同理：`updated==0` 且 `after.errorMsg` 空且 `after.resultFile` 空且本机 zip 存在 → 补写。

### P0-3 跨实例互斥：复用分支不重新提交 + DB 唯一约束

**文件**：`TrainSignUpDefaultTemplateExportService.java` `startExport`；DB 迁移脚本

**现状**：`aa7d7fb` 复用分支在 `idsOut` 为空时 `submitExportAfterCommit` 重新提交。多实例下两台机器各自重新提交 → 并行打包。

**改为**：
1. 复用分支**永不重新提交**（`f767b5e` 已改，需确认线上部署版本；若线上仍是 `aa7d7fb`，紧急回滚此分支逻辑）。
2. `startExport` 查 `endtime=0` 任务时加 `SELECT ... FOR UPDATE`（在事务内），或对 `train_sign_up_self_task` 加部分唯一索引 `(sign_up_id) WHERE endtime=0` 防止同 signUp 同时存在两个进行中任务。
3. 保留 `runningExportTaskIds` 作为单进程内的二次防重，但不再作为唯一依赖。

**迁移脚本**：
```sql
-- 防止同一报名计划同时存在多个进行中任务
CREATE UNIQUE INDEX uk_sign_up_self_task_running
  ON train_sign_up_self_task (sign_up_id) WHERE endtime = 0;
```

### P0-4 `resolveExportZip` 兜底恢复宽匹配

**文件**：`TrainSignUpDefaultTemplateExportService.java` `resolveExportZip`

**现状**：只认 `*_t{taskId}.zip`，跨实例磁盘落空就彻底找不到。

**改为**（恢复 `8170e2a` 风格兜底，但保留 taskId 精确匹配优先）：
1. 首选 `findZipByTaskId(cdnPath, taskId)` 扫 `*_t{taskId}.zip`；
2. 次选 `task.resultFile`（磁盘相对路径）；
3. 兜底：扫 `signUp.files` 里**本任务**的 zip（`endsWithTaskZip`），再扫任意 `.zip`（仅当 `endtime>0` 且无 `result_file` 时）；
4. 找到即返回 `publicUrl(relative) + "?v=" + taskId`。

### P1-1 前端轮询去掉 90 次硬上限 + 指数退避 + 取消按钮

**文件**：`ClassSignUpPeoplePanel.tsx` `handleDefaultTemplateExport`

**现状**：`for (let i = 0; i < 90; i++)` 每 2s 一次，约 3 分钟超时。大批量必然超时。

**改为**：
1. 循环改为 `while (!finished)`，无硬上限；
2. 轮询间隔指数退避：`2000 → 4000 → 8000 → 15000`（上限 15s）；
3. 模态框显示"已耗时 + 进度 + 预估剩余"；
4. 加"取消导出"按钮，调 `POST .../default-template/cancel`（新增接口，后端 `failTask(task, "用户取消")`）；
5. 关闭模态框时停止轮询（清 timer），但后台任务继续，提示"已后台导出，可在导出记录查看"。

### P1-2 多人并行打包（最大提速点）

**文件**：`SignUpPeopleDefaultTemplatePackService.java` `run`

**现状**：逐人串行 `processPerson`，15 人约 20-30s，100 人 3-5 分钟。

**改为**：
1. 用 `CompletableFuture` 或 `parallelStream` 按人并行，每人独立 `XWPFDocument` 实例（POI 非线程安全，但每人独立对象即可）；
2. 并发度 `min(人数, CPU核数, 8)`，通过 `signUpExportExecutor` 或独立 `ForkJoinPool` 控制；
3. **汇总 Excel 写入需同步**：`ExportContext.bmallWb/examGxWb/examAllWb` 是共享 `Workbook`，`appendSummaryRows` 需 `synchronized` 或改为每人线程局部缓冲、最后合并；
4. `copyPersonAssets`（图片拷贝/裁剪）天然可并行；
5. `finalizeZip` 仍在主线程串行执行。

**注意**：并行后 `updateTaskProgress` 回调会并发写 `idsOut`，需改为原子计数器（见 P2-3）或同步。

### P2-1 模板字节缓存

**文件**：`SignUpPeopleDefaultTemplatePackService.java`

**现状**：`loadClasspathTemplate` 每人每份 docx 都读 classpath，100 人 × 4 模板 = 400 次 IO。

**改为**：服务启动时（`@PostConstruct`）把 6 个模板（3 docx + 3 xlsx）`byte[]` 缓存到内存 `Map<String, byte[]>`，`fillDocxTemplate`/`copyOrCreateExcel` 从缓存复制而非读 classpath。

### P2-2 zip 上传改流式

**文件**：`TrainSignUpDefaultTemplateExportService.java` `doRunExport`；`FileApplicationService`

**现状**：`Files.readAllBytes(zipAbsolute)` 把整个 zip 读进 `byte[]`，几百 MB 时 OOM 风险。

**改为**：`fileApplicationService` 增加流式上传接口 `storeFromStreamForTenant(tenantId, InputStream, size, fileName, contentType, visibility)`，用 `Files.newInputStream` 流式上传 COS，不一次性读全量。

### P2-3 进度存储改计数器

**文件**：`TrainSignUpSelfTaskEntity`；DB 迁移；`TrainSignUpDefaultTemplateExportService`

**现状**：`idsOut` 是 JSON 数组，1000 人时每次 `updateTaskProgress` 都序列化/反序列化整个数组。

**改为**：
1. 加列 `done_count INT DEFAULT 0`、`total_count INT DEFAULT 0`；
2. `progressOf` 改读 `done_count + "/" + total_count`；
3. `updateTaskProgress` 改为 `UPDATE ... set(done_count=done_count+1)`（原子自增，无需同步）；
4. `idsOut` 保留但仅在结束时写一次完整列表（用于校验完整性），过程不再更新；
5. 迁移脚本：
```sql
ALTER TABLE train_sign_up_self_task ADD COLUMN done_count INT NOT NULL DEFAULT 0;
ALTER TABLE train_sign_up_self_task ADD COLUMN total_count INT NOT NULL DEFAULT 0;
```

### P2-4 COS 上传与打包解耦（异步上传）

**文件**：`TrainSignUpDefaultTemplateExportService.java` `doRunExport`

**现状**：打包完成 → 同步上传 COS → 才写 `result_file`。用户必须等上传完成才能下载。

**改为**（在 P0-1 两段式基础上进一步）：
1. 打包完成 → 写 `result_file=zipRelative`（磁盘）→ check 立即可返回磁盘下载 URL；
2. **异步**提交 COS 上传任务到 `signUpExportExecutor`；
3. 上传成功后 `UPDATE ... set(result_file=/api/files/{id}/download)`；
4. 用户不用等 COS 上传就能下载（走本机磁盘/CDN 回源），上传 COS 只是跨实例与长期存储兜底。

### P3-1 分批查询人员

**文件**：`TrainSignUpDefaultTemplateExportService.java` `doRunExport`

**现状**：`peopleMapper.selectList(in id)` 一次性全量加载。

**改为**：`idsIn` 分批（每批 100）`selectList`，处理完释放，配合 P1-2 并行打包控制内存峰值。

### P3-2 磁盘空间治理

**文件**：`SignUpPeopleDefaultTemplatePackService.java`；新增清理脚本

**现状**：工作目录用完即删（已有），但 zip 本身保留在 `{cdn}/down/`。

**改为**：
1. COS 上传成功后删本地 zip（P2-4 异步上传成功后触发）；
2. 失败则保留并标记，定期清理脚本兜底（清理 7 天前的 `*_t*.zip`）；
3. 打包工作目录异常残留时启动时清理。

### P3-3 `signUpExportExecutor` 线程池调优

**文件**：线程池配置类

**现状**：`[sign-up-export-1]` 疑似单线程。

**改为**：独立配置核心/最大线程数与队列容量，并发导出任务数 × 每任务并行度（P1-2），避免与 HTTP 线程池抢资源。

## 五、验收标准

1. **P0 验收**：多实例下连点导出，check 不再返回"导出完成但未找到压缩包"；`result_file` 始终有值（磁盘路径或下载 URL）。
2. **P1 验收**：100 人导出 ≤ 60s 完成；前端轮询不超时；取消按钮可中断。
3. **P2 验收**：500 人导出不 OOM；进度条流畅；COS 上传失败仍可从磁盘下载。
4. **回归**：同标题多次导出 URL 不同（防旧缓存）；勾选变更可取消旧任务；权限校验不变。

## 六、风险与回滚

- **P0 改动小且向后兼容**，可独立发布止住线上报错。
- P1 并行打包需充分测试 POI 并发安全，建议先在测试环境跑 100 人验证。
- P2 计数器需 DB 迁移，配合灰度。
- 若 P0 上线后仍有问题，可回滚 `resolveExportZip` 到 `8170e2a` 宽匹配作为最终兜底。
