# 认定归档模块开发文档

## 1. 模块定位

认定归档模块属于“认定管理”下的子模块，用于对已完成的认定任务进行基础信息归档和资料信息归档。

归档前置条件：

- 只有认定任务状态为“已完成”的任务允许归档。
- 归档数据应保存为历史快照，避免后续原任务数据变化影响已归档内容。
- 归档模块的数据表统一使用 `certification_` 前缀，明确归属认定管理模块。

模块分为两个子功能：

1. 认定任务基础信息归档
2. 认定任务资料信息归档

## 2. 业务范围

### 2.1 基础信息归档

基础信息来源于筹备期中已完成的认定任务。

归档内容包括：

| 信息项 | 说明 |
| --- | --- |
| 任务名称 | 已完成认定任务名称 |
| 任务编号 | 已完成认定任务编号 |
| 认定完成时间 | 任务完成时间 |
| 认定人数 | 参与认定人数 |
| 认定范围 | 工种、等级、范围等 |
| 考务配置 | 姓名、角色 |
| 设备配置 | 设备名、设备编号、设备数量 |
| 考场配置 | 考场、考试类型 |
| 考评员配置 | 考评员姓名 |

基础信息归档流程：

1. 用户进入认定归档页面。
2. 系统查询状态为“已完成”的认定任务。
3. 用户选择需要归档的任务。
4. 系统生成基础信息归档表单。
5. 用户确认后归档。
6. 系统保存基础信息快照。

### 2.2 资料信息归档

资料信息主要来源于外部文件导入，分为认定材料和考生材料。

认定材料包括：

### 3.2 考生清单 Excel

清单字段：

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| 考生编号 | 是 | 系统内考生编号 |
| 姓名 | 是 | 考生姓名 |
| 身份证号 | 是 | 推荐作为业务唯一键 |
| 文件夹名称 | 是 | ZIP 中对应的考生文件夹 |

示例：

| 考生编号 | 姓名 | 身份证号 | 文件夹名称 |
| --- | --- | --- | --- |
| KS001 | 张三 | 440101199001010001 | 张三_440101199001010001 |
| KS002 | 李四 | 440101199001010002 | 李四_440101199001010002 |

系统优先依据身份证号进行唯一关联；如历史数据中身份证号缺失，再考虑使用考生编号。

## 6. 文件存储方案

### 6.1 前期确认方案

前期开发阶段可以先使用本地目录存储文件。

建议方案：

```text
业务层统一调用 FileStorageService
一期实现 LocalFileStorageService
后期可替换 MinioFileStorageService 或 OssFileStorageService
```

数据库只保存文件元数据和 `file_key`，不保存文件二进制内容。

不要将文件直接存入数据库 BLOB，也不要在数据库中保存绝对磁盘路径。

### 6.2 本地目录配置

建议配置：

```yaml
certification:
  archive:
    storage-type: local
    storage-root: D:/qianlvguoyu/storage
```

真实文件路径由系统拼接：

```text
storage_root + file_key
```

数据库中保存：

```text
file_key = certification/archive/RW202606001/10001/candidates/440101199001010001/ID_CARD/idcard.pdf
```

### 6.3 文件 Key 设计

认定任务材料：

```text
certification/archive/{taskNo}/{archiveId}/task-materials/{materialType}/{fileName}
```

考生材料：

```text
certification/archive/{taskNo}/{archiveId}/candidates/{idCard}/{materialType}/{fileName}
```

导入原始 ZIP：

```text
certification/archive/{taskNo}/{archiveId}/import-batches/{batchId}/{zipFileName}
```

### 6.4 本地存储注意事项

1. 上传目录不要放在项目源码目录中。
2. 本地目录需要配置读写权限。
3. 文件名需要做安全处理，防止 `../` 等路径穿越。
4. 文件上传时记录 `file_hash`，用于去重、完整性校验和后期迁移校验。
5. 文件访问必须通过后端接口，不直接暴露本地磁盘路径。
6. 后续迁移到 MinIO 时，保持数据库中的 `file_key` 不变。

### 6.5 大数据量影响说明

如果文件直接存数据库，会带来以下问题：

| 问题 | 影响 |
| --- | --- |
| 数据库体积快速膨胀 | 备份、恢复、迁移变慢 |
| 查询性能下降 | 大表和大字段会影响数据库缓存和索引维护 |
| 下载占用数据库连接 | 文件预览和下载会消耗数据库连接资源 |
| 扩容成本高 | 数据库扩容比文件存储扩容更复杂 |
| 备份策略不灵活 | 业务数据和文件数据无法分层备份 |

推荐最终演进方向：

```text
本地目录存储 -> MinIO 或统一文件服务
```

前期先使用本地目录是可行的，但代码结构必须从一开始预留可替换的文件存储接口。

## 7. 导入校验规则

ZIP 导入时需要校验：

| 校验项 | 说明 |
| --- | --- |
| ZIP 格式 | 文件必须是合法 ZIP |
| 清单文件 | 必须包含考生清单 Excel |
| 清单字段 | 考生编号、姓名、身份证号、文件夹名称必填 |
| 身份证号 | 不允许重复 |
| 文件夹 | 清单中的文件夹必须存在 |
| 考生匹配 | 文件夹和清单需要能匹配 |
| 必传材料 | 必传材料必须齐全 |
| 文件类型 | 限制 PDF、图片、Office 等允许类型 |
| 文件大小 | 校验单文件大小和总文件大小 |
| 重复材料 | 同一考生同一材料类型不允许重复 |
| 文件可读性 | 文件不能为空，且能正常读取 |

异常类型：

```text
MISSING_EXCEL           缺少清单 Excel
INVALID_EXCEL_FORMAT    清单格式错误
CANDIDATE_DUPLICATED    考生重复
FOLDER_NOT_FOUND        文件夹不存在
MATERIAL_MISSING        材料缺失
MATERIAL_DUPLICATED     材料重复
UNSUPPORTED_FILE_TYPE   文件类型不支持
FILE_READ_FAILED        文件读取失败
```

## 10. 权限与安全

建议控制：

1. 只有具备认定归档权限的用户可以归档。
2. 只有已完成任务允许归档。
3. 文件下载和预览必须经过权限校验。
4. 身份证号等敏感信息展示时应脱敏。
5. 存储文件时应防止路径穿越。
6. 记录上传、删除、确认归档等关键操作日志。

## 12. 结论

认定归档模块应围绕“已完成任务归档快照”和“材料文件归集”设计。

本期确认的关键设计如下：

1. 数据表统一使用 `certification_` 前缀。
2. 文件前期可以使用本地目录存储。
3. 数据库只保存文件元数据和 `file_key`，不保存文件二进制。
4. 文件存储通过 `FileStorageService` 抽象，后期可平滑切换到 MinIO。
5. 考生材料采用“ZIP 压缩包 + 考生清单 Excel”的导入方式。
6. 考生关联优先使用身份证号，避免姓名重名问题。
7. 材料数据使用统一材料表，避免为每类材料反复增加字段。
