# 竞赛模块全链路现状与成绩专项衔接缺口

> 核对日期：2026-07-29
> 核对范围：当前仓库中的竞赛 Flyway、`platform-api/competition`、`admin-web/competition`、竞赛需求与技术决策文档。
> 结论：成绩与排名专项可以开发，但不能直接从成绩表和排名算法开始；必须先补齐“赛前编排桥接”，否则成绩无法可靠关联工种、赛段、规则版本、参赛选手和裁判权限。

当前讨论并冻结的 `COMP-SCORE-00 V1.0` 主要覆盖第 4～7 环节：

- 第 4 环节中的赛制 B 权重、理论模板、A/B 卷、裁判数量和回避规则。

## 3. 从已实现内容进入成绩专项时的链路缺口

### P0-01：竞赛工种仍是文本，不能作为排名与规则主键

名单表只有 `competition_roster_item.work_type VARCHAR(64)`。选手扩展没有工种 ID，赛事也没有“本赛事启用哪些工种”的正式关系。

这会导致：

- 同一工种因空格、简称或错别字被拆成多个榜单。
- 无法可靠关联现有 `exam_work_type` 题库工种。
- A/B 卷、权重、裁判和排名无法使用同一稳定业务键。
- 选手名单确认后无法证明其属于哪个已发布赛项工种。

必须新增“赛事工种/赛项”关系，并把选手关联到该关系；导入文本只能作为原始值或待匹配输入，不能直接作为成绩和排名分区键。

### P0-02：赛段存在于 Service，但没有可调用入口

`CompetitionStageApplicationService` 已存在，但没有对应 Controller，管理端也没有赛段页面。当前赛事发布逻辑只校验赛事字段和参与企业，没有校验赛段。

结果是数据库虽然有 `competition_stage`，正常业务操作却无法稳定创建和维护赛段，后续成绩只能接受任意或空 `stage_id`。

### P0-03：资格审核服务没有 API，合格选手池无法闭环

`CompetitionRegistrationApplicationService` 已实现分页和审核，但没有 Controller。需要审核的赛事无法通过正常 API 完成 `pending_audit → eligible_unactivated/eligible_activated`。

成绩链路必须只接受具备有效参赛资格且已绑定 `contestant` 赛事成员的选手，因此该入口必须补齐。

### P0-04：评分规则没有配置实体，赛事可以在规则缺失时发布

当前 `competition_event` 没有理论模板、理论权重和仿真实操组合权重；也没有独立规则版本表。赛事发布不会校验：

- 是否选择 90/120 分钟理论模板。
- 理论权重与仿真实操组合权重是否合计 100%。
- 是否为每个赛事工种形成已锁定规则版本。

如果先写成绩表，后续只能为已产生的分数补猜规则，违反“先冻结规则再比赛”的业务顺序。

### P0-05：赛事角色表不等于裁判可评分

当前只有角色和赛段授权表，且 `CompetitionEventMemberService` 只实现了选手成员创建。尚缺：

- 组委会管理员/主裁判长绑定裁判的用例和权限。
- 裁判关联赛事工种、赛段以及正式/备用身份。
- 裁判—选手禁评名单。
- 同单位、亲属、师徒等回避命中后的统一拒绝校验。

因此不能把“存在 referee 角色”直接解释为“可为任意选手评分”。

### P0-06：理论成绩来源的上游尚不存在

当前竞赛域没有：

- 工种—理论模板配置。
- 考试场次与容量。
- 同工种不同时间场次。
- A/B 卷版本和场次固定映射。
- 选手—场次—试卷版本分配。
- 题目/标准答案/分值/判分规则快照。

纯判分算法可以先实现，但正式理论成绩来源必须在这些上游对象存在后才能落库。

### P1：选手 H5 和真实端到端仍未闭环

选手认证后端已有实现，但当前仓库没有 `apps/competition-h5`。这不阻塞后台数据底座开发，却会阻塞“选手实际进入考试并查看已发布成绩”的完整验收。

### P1：预留总分字段不能作为成绩事实表

`competition_contestant_profile.total_score` 是 `DECIMAL(12,2)` 的可变汇总字段，没有规则版本、成绩来源版本和计算过程。它只能作为后续查询投影或废弃兼容字段，不能成为最终成绩事实来源。

## 4. 修正后的开发顺序

| 顺序 | 任务 | 目标 | 进入下一步的门槛 |
| ---: | --- | --- | --- |
| 1 | `COMP-SCORE-01`：赛前编排与成绩域桥接 | 补齐赛事工种、选手工种归属、赛段 API、资格审核 API、赛制 B 规则版本和发布前校验。 | 能从真实赛事、合格选手和已发布规则得到稳定的 `event + stage + eventWorkType + contestant` 计算范围。 |
| 2 | `COMP-SCORE-02`：成绩数据底座与纯业务内核 | 建立成绩来源、实操评分修订、解锁、计算和排名快照；实现多选、3 人平均、赛制 B、1334。 | Flyway、领域测试、编译和状态机测试通过。 |
| 3 | `COMP-SCORE-03`：理论试卷与考试执行 | 题集快照、90/120 模板、A/B 卷、分时场次、选手分配、答题/交卷和自动判分。 | A/B 场次可产生可追溯的已确认理论成绩来源。 |
| 4 | `COMP-SCORE-04`：竞赛实操评分适配 | 复用认定评分能力，补齐裁判绑定、正式/备用、禁评、锁定和解锁重评。 | 每名选手恰好 3 个有效锁定分并形成竞赛实操成绩。 |
| 5 | `COMP-SCORE-05`：总分与排名应用链路 | 完成来源确认、总分计算、缺考过滤、按工种 1334 排名和内部快照。 | 后台可复核并重算新版本，不覆盖历史。 |
| 6 | `COMP-SCORE-06`：管理端与基础 E2E | 赛段、工种、规则、裁判、评分监控、成绩和排名页面及端到端验收。 | 当前 `COMP-SCORE-00 V1.0` 功能闭环通过。 |
| 7 | `COMP-PERF-00～05`：并发容量专项 | 批量暂存、交卷幂等、缓存限流、监控、压测和全规模模拟赛。 | 达到冻结容量和零丢答案/零重复有效交卷目标。 |

P0-05 奖项比例、P0-07 公示仲裁与撤销重排、P0-08 仿真接口仍保持后置，不插入当前成绩闭环与并发专项之间。

## 5. 当前任务的正确定位

原先直接生成的“成绩数据底座与纯业务计算内核”任务方向没有错，但顺序提前了一步。它应调整为 `COMP-SCORE-02`。

当前真正应新开的第一个开发任务是 `COMP-SCORE-01：赛前编排与成绩域桥接`。完成该任务后，才能保证后续成绩、裁判和排名数据使用的是稳定业务主键与已发布规则，而不是名单文本、可变总分字段或临时关联。
