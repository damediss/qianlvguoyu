## 0. 已确认决策与阅读约定

### 0.1 需求方已拍板（2026-10-24）

| 决策点 | 已确认口径 |
|---|---|
| 二期范围 | **编写协同闭环**：章节分配、我的任务、按节编写、提交/打回/通过、进度、版本留痕、整册 docx 导出 |
| 专家账号与入口 | 使用管理端 `sys_user`；在 admin-web 提供独立“我的编写任务 / 我的审定任务”工作台 |
| 分配粒度 | **每章 1 名主笔 + 1 名审定人**；章下所有节继承归属 |
| 编写与审定粒度 | **按节保存、提交、通过、打回**；章进度由节状态汇总，不做“整章一次性提交” |
| 编写方式 | 在线编写为主，复用 `md-editor-rt`；支持图片、预览、自动保存、提交版本快照、并发防覆盖 |
| Word 边界 | 二期支持单节/单章/整册 **docx 导出**，不做 Word 回传、不研究 Word 合并算法 |

### 0.2 本文统一语言（ubiquitous language）

- **工程 / 分册**：`textbook_project`，一个“工种 × 方向 × 等级”的教材工程。
- **章**：`textbook_outline.node_level=2`，任务分配的最小单位。
- **节**：`textbook_outline.node_level=3`，正文、提交、审定的最小单位。
- **点**：`node_level=4`，标准知识点/技能点，只作为编写要求和覆盖检查依据，不单独分配。
- **主笔（writer）**：当前章节编写责任人，必须是本工程章分配中指定的 `sys_user`。
- **审定人（reviewer）**：当前章节审定责任人；与主笔不能是同一人。
- **教研/管理员**：拥有 `textbook:project:manage` 的管理端用户，负责分配、改派、进度管理、完成与导出。
- **提交快照**：每次“提交审定”时生成的不可变正文版本；自动保存草稿不等于生成提交快照。

### 0.3 明确不做（防止实施范围膨胀）

1. 不接 LLM，不做要点扩写、口述整理、自动正文生成，不新增模型配置和异步 LLM 线程池。
2. 不做素材库、案例库、写透/删除标记、习题映射、试教看板、学员端教材阅读。
3. 不做多人同时在线 co-edit；不做 Word 上传回写、修订合并、批注导入。
4. 不做短信、微信、邮件通知；逾期与待办由工作台呈现。
5. 不把现有考评 `task_expert` / `platform_user` 专家体系套到教材编写上。

## 1. 一期事实与二期必须修正的风险

### 1.1 可直接复用

- `textbook_project` / `textbook_outline` 已有完整树结构、目标字数、`source_no`、`sort_no`、软删与租户字段。
- 工程状态已有 `parsed → outlined → reviewed`；`reviewed` 在一期表示“**大纲评审通过**”。
- 大纲接口、目录导出、RBAC、`@AuditLog`、file 模块存储与受控下载响应、POI、`md-editor-rt`、`sanitize-html` 均已存在。
- 后端当前分页真实契约为 `PageResponse<T>(items, page, pageSize, total)`；本功能沿用现有类，**不另造 records/list 第二套分页结构**。若实施时全局类已统一变更，以当时代码为准。
- 所有雪花 ID 在 API/TS 中继续使用字符串。

### 1.2 不能沿用的旧行为

一期 `rebuild` / 改学时系数触发的 `regenerate` 会删除部分旧节并生成新 ID。如果正文按 `section_id` 关联，重建会产生孤儿正文。

因此二期采用**编写期结构冻结**：

- 首个有效章分配创建后，或任一正文记录存在后，工程进入结构保护状态。
- 后端必须拦截身份变化操作，不能只禁用前端按钮。
- 允许保留的安全编辑：章/节标题、目标字数、同级排序。
- 禁止的身份变化操作见 §5.4；需要重建时必须先取消全部分配且确认无任何正文。

### 1.3 两套账号不能混用

- `sys_user`：管理端登录，`PlatformUserPrincipal` 内含 `userId/tenantId/roleCodes/permissionCodes`。
- `platform_user`：学员/App 登录，现有考评专家分配使用这套身份，但教材管理接口当前基于管理端 RBAC。

二期所有 `writer_id/reviewer_id` 均指 **`sys_user.id`**。禁止在前端传姓名代替 ID，禁止仅凭角色名放行具体章节。

## 2. 角色、入口与端到端流程

### 2.1 三类工作视角

| 视角 | 能看什么 | 能做什么 |
|---|---|---|
| 教研/管理员 | 全量工程、全部章节正文与进度 | 分配/改派/取消、查看全部内容、结构安全编辑、完成工程、导出 |
| 主笔专家 | 仅自己作为主笔的章及章下节 | 编辑草稿、上传图片、提交、查看历史、导出自己章节；不能审定自己提交的内容 |
| 审定专家 | 仅自己作为审定人的章及章下节 | 查看正文与编写要求、逐节通过/打回、必要时撤销通过；不能改正文 |

一个用户可同时拥有编写与审定角色，但**同一章的 writerId 与 reviewerId 不得相同**；审定时还要校验当前审定人不是该次提交的 `submittedBy`，防止改派后变相自审。

### 2.2 主流程

```text
一期：工程 outlined → 教研点击“大纲评审通过” → reviewed
   ↓
二期：教研进入“编写管理” → 为每章选择主笔、审定人、截止日期、编写说明
   ↓（首个有效分配后 project.status=writing）
主笔：“我的编写任务” → 章节工作台 → 按节自动保存草稿 → 提交审定
   ↓
审定人：“我的审定任务” → 逐节通过 / 打回（打回必须填意见）
   ↓ 打回后：主笔修改并重新提交，产生新的提交快照
教研：查看全册进度；全部章节有效分配且全部节通过后点击“完成编写”
   ↓ project.status=done
教研：导出正式整册 docx；过程中也可导出带状态标识的审阅稿
```

## 3. 状态机与关键业务规则

### 3.1 工程状态

沿用 `textbook_project.status`（现有 VARCHAR 足够，无需改列）：

| 状态 | 页面文案 | 进入条件 | 允许动作 |
|---|---|---|---|
| `parsed` | 已解析 | 一期兜底态 | 按一期规则处理 |
| `outlined` | 大纲已生成 | 骨架生成/重建后 | 大纲编辑、评审 |
| `reviewed` | 大纲已评审 | 一期评审通过 | 可开始分配；尚不能编写正文 |
| `writing` | 编写中 | 首个有效章分配创建；或 done 被重新打开 | 分配、编写、审定、审阅稿导出 |
| `done` | 编写完成 | 教研手动“完成编写”，校验全通过 | 只读、正式 docx 导出；可重新打开 |

约束：

1. 列表和详情把 `reviewed` 文案从笼统“评审通过”改为“**大纲已评审**”，避免与节审定混淆。
2. `done` 不自动产生。即使 100% 通过，也要教研确认后点击“完成编写”。
3. 完成条件必须同时满足：`chapterCount > 0`、`sectionCount > 0`、每章至少 1 节、每章有有效分配、全部节 `approved`、无 `[待专家补充]` 占位。禁止用“空集合全称条件”把零章/零节工程判为完成。
4. **done 的唯一退出入口是 C6**：仅 `textbook:project:manage` 可执行 done → writing，正文状态不自动改变。审定人不能在 done 直接撤销通过；需教研先重开。
5. done 下只允许查看、导出和 C6 重开。分配/取消、正文保存/提交/审定/恢复、图片上传/删除、工程编辑、大纲编辑、工程删除等写操作一律 409，不能在文档其他位置另开旁路。
6. C5/C6 都必须在工程行锁内重新读取状态与完成条件；C5 还要求 `WHERE status='writing'`、C6 要求 `WHERE status='done'` 的条件更新并检查影响行数，防并发重复流转。

### 3.2 节正文状态 `textbook_section_content.content_status`

| 当前状态 | 动作 | 下一状态 | 操作者与必要条件 |
|---|---|---|---|
| 无记录 | 首次保存 | `draft` | 当前主笔；baseVersion=0；工程 writing |
| `draft` | 自动/手动保存 | `draft` | 当前主笔；baseVersion 匹配 |
| `returned` | 修改后保存 | `returned` | 当前主笔；保留“已打回”标识直到重新提交 |
| `draft` / `returned` | 提交审定 | `submitted` | 当前主笔；正文非空；生成 submit 快照与 submit 记录 |
| `submitted` | 通过 | `approved` | 当前审定人；不能是 submittedBy；记录 approve |
| `submitted` | 打回 | `returned` | 当前审定人；意见必填；记录 return |
| `approved` | 撤销通过 | `returned` | 当前审定人；工程必须为 writing；原因必填；记录 reopen |
| `submitted` / `approved` | 主笔保存 | 不变，返回 409 | 先由审定人打回/撤销，主笔不能绕过 |

补充规则：

- `submitted` 和 `approved` 对主笔只读；审定人始终不能编辑正文。
- 打回后允许主笔编辑，但状态保持 `returned`，便于任务列表持续提示；重新提交后才进入 `submitted`。
- 每次提交、通过、打回、撤销均使 `content.version + 1`，所有写接口都使用 baseVersion 防旧页面覆盖新状态。
- 改派不改变任何节状态、正文、快照或审定记录。
- 新主笔可继续编辑 draft/returned；已 submitted 的内容仍需审定人处理，不能因为改派主笔就自动退回草稿。
- 原主笔改派后立即失去章节访问权；其未保存的浏览器草稿不得再写入，前端要保留本地副本供人工拷出。

### 3.3 章任务状态（冗余查询字段，正文状态才是事实源）

`textbook_chapter_assignment.task_status` 是列表查询缓存。每次正文保存/提交/审定/恢复、分配/取消后，必须在**同一事务**调用统一的 `refreshChapterSummary(chapterId)` 重算，禁止各 Controller 自行拼状态。

先统计章下全部节（不是只统计已有正文记录的节）：

- `sectionCount`：章下 `node_level=3` 的存活节数。
- `approvedCount / submittedCount / returnedCount / draftCount`：对应正文状态数量。
- `untouchedCount = sectionCount - 已有正文记录节数`。
- `startedCount`：有非空 Markdown，或曾进入 submitted/approved/returned 的节数。

计算优先级：

```text
sectionCount = 0                         → 不允许分配（数据异常提示）
approvedCount = sectionCount             → approved
returnedCount > 0                        → returned
submittedCount + approvedCount = sectionCount → reviewing
startedCount > 0                         → writing
否则                                     → assigned
```

这意味着“部分节已提交、部分节仍在写”整体仍显示 writing；审定人的“待审定”队列**不只看 task_status**，而以 `submittedCount > 0` 为队列条件。

### 3.4 分配、改派、取消

1. 仅 reviewed/writing 工程可分配；done 必须先重新打开。
2. 章必须属于该工程且 `node_level=2`，章下至少一节。
3. 主笔与审定人均为同租户、`status=enabled` 的 `sys_user`：
   - 主笔必须同时拥有 `textbook:task:view` 和 `textbook:content:write`；
   - 审定人必须同时拥有 `textbook:review:view` 和 `textbook:content:review`。
4. 每章一条当前分配记录；改派更新原记录并 `assignment_version+1`，不是每天插入一条“当前分配”。
5. 批量分配单事务、全量预检、全部成功才提交；任一失败返回具体章名和原因，不部分生效。
6. 取消分配：`active=0`、`assignment_version+1`。不删除正文、快照、审定记录；原主笔/审定人立即失去入口，管理员仍可见。
7. 重新分配已取消的章：复用原记录、重新 `active=1`，避免逻辑删除唯一键导致无法再次分配。
8. 截止时间为空表示不限；`dueDate < 今天 && taskStatus != approved` 前端显示“已逾期”，不自动改状态、不阻止编写。

### 3.5 一期旧接口的状态白名单（必须同步收紧）

现有 `PUT /textbook/projects/{id}` 可携带 `status` 和结构字段，二期不得让它绕过新状态机。`applyStatusTransition` 改为显式白名单：

| 操作 | 允许条件 |
|---|---|
| `outlined → reviewed` | 一期“大纲评审通过”唯一入口；manage |
| `reviewed → outlined` | 仅未结构锁定时允许，表示撤回大纲评审；manage |
| `writing → done` | 只允许 C5，旧 PUT 禁止 |
| `done → writing` | 只允许 C6，旧 PUT 禁止 |
| writing/done → outlined/parsed/reviewed | 旧 PUT 一律 409 |
| 同一请求同时携带结构字段和 status | 400；结构变更后必须单独发起评审 |

结构身份变化（新增/删除节点、rebuild、改 functionNos/学时/系数触发 regenerate）只允许 `parsed/outlined` 且未锁定。reviewed 如确需改结构，先显式撤回为 outlined，再修改、重新评审；不得“同一请求重建并立即 reviewed”。标题、目标字数、同级排序可在 outlined/reviewed/writing 修改，done 一律只读。

## 4. 权限设计（后端最终裁决）

### 4.1 角色与权限码

保留一期：`textbook:project:view / manage / export`。新增 4 个权限码：

| 权限码 | 用途 |
|---|---|
| `textbook:task:view` | “我的编写任务”菜单、读取自己主笔章节 |
| `textbook:content:write` | 保存、提交、恢复版本、上传本节图片 |
| `textbook:review:view` | “我的审定任务”菜单、读取自己审定章节 |
| `textbook:content:review` | 通过、打回、撤销通过 |

新增两个业务角色（只建角色和权限，不向真实用户自动授权）：

| role code | 名称 | 权限 |
|---|---|---|
| `TEXTBOOK_WRITER` | 教材编写专家 | task:view、content:write + 我的编写任务菜单 |
| `TEXTBOOK_REVIEWER` | 教材审定专家 | review:view、content:review + 我的审定任务菜单 |

平台管理员 role 2000 按现有“全功能”惯例授予新权限和新菜单；但**角色权限不是章节归属**，即使管理员拥有 content:write，未指定为当前主笔也不能改正文。

### 4.2 三层授权模型

所有章节/节接口都依次校验：

1. **功能权限**：Spring `@PreAuthorize` 判断能否执行该类动作。
2. **工程可见性**：`textbook:project:view` 可只读全部；否则必须存在该章有效分配。
3. **章节归属与状态**：写操作必须当前 writer；审定操作必须当前 reviewer；再校验工程/节状态。

对象级无权访问统一返回 404（避免探测其他工程/章节是否存在）；有身份但缺少功能权限由 Security 返回 403。跨租户仍由 MyBatis-Plus 插件过滤，服务层不得手写 tenant 条件替代插件。

### 4.3 权限矩阵

| 能力 | project:view | project:manage | 当前主笔 | 当前审定人 |
|---|---|---|---|---|
| 全量工程列表/大纲 | 是 | 是 | 否（只看自己的任务） | 否 |
| 查看全部章节正文 | 是 | 是 | 仅自己章 | 仅自己章 |
| 分配/改派/取消 | 否 | 是 | 否 | 否 |
| 修改大纲安全字段 | 否 | 是 | 否 | 否 |
| 编辑/提交节正文 | 否 | 仍需同时是当前主笔且有 write | 是 | 否 |
| 通过/打回/撤销通过 | 否 | 仍需同时是当前审定人且有 review | 否 | 是 |
| 完成/重新打开工程 | 否 | 是 | 否 | 否 |
| 整册导出 | project:export | project:export | 否 | 否 |
| 自己章/节导出 | 是 | 是 | 是 | 是 |

### 4.4 后端统一入口 `TextbookAccessService`

做成深模块，Controller 不各自查询 assignment 后拼 if：

```java
// 仅 HTTP 请求线程使用；二期没有 Worker 调用
ChapterAccess requireChapterRead(Long chapterId);
SectionAccess requireSectionRead(Long sectionId);
SectionAccess requireCurrentWriter(Long sectionId);    // task:view + content:write + active + writing
SectionAccess requireCurrentReviewer(Long sectionId);  // review:view + content:review + active + writing
ProjectAccess requireProjectView(Long projectId);
ProjectAccess requireProjectManage(Long projectId);    // 还要求 project:manage
```

`ChapterAccess/SectionAccess` 一次装载并返回 `project/chapter/section/assignment/principal`，后续 Service 不重复查询、不从前端接收 tenantId/userId 作为授权依据。

**读取授权与写能力计算必须分离**：`project:view` 只表示可读，不能提前把上下文标成 readOnly，否则“同时拥有 project:view 的当前主笔”会被误判为不能写。工作台 VO 独立返回 `relations/canWrite/canReview/readOnlyReason`。

伪代码：

```java
boolean allowed = has('textbook:project:view');
assignment = activeAssignmentOf(chapter.id);
boolean writer = assignment != null && has('textbook:task:view')
    && assignment.writerId == currentUserId;
boolean reviewer = assignment != null && has('textbook:review:view')
    && assignment.reviewerId == currentUserId;
if (!allowed && !writer && !reviewer) {
  throw new BusinessException(ErrorCode.NOT_FOUND, '章节不存在或无权访问');
}
return new SectionAccess(..., writer, reviewer);       // 此处不裁决 canWrite/canReview
```

写/审定方法必须再分别比较当前 ID、对应内容权限、工程/节状态，不能调用 `requireSectionRead` 后误以为就能写。`relations` 可包含 manager/writer/reviewer 多个值，页面按当前模式使用 canWrite 或 canReview。

## 5. 数据模型（5 张新表，均为 Flyway 新迁移）

统一：雪花 BIGINT 主键、`tenant_id`、`deleted`、`created_by/updated_by/created_at/updated_at`；不建跨租户物理外键，逻辑关联由 Service 校验；软删使用 `deleteById/deleteBatchIds`。

### 5.1 `textbook_chapter_assignment`（章当前分配 + 查询进度缓存）

| 列 | 类型 | 说明 |

### 5.6 教材资产专用受保护文件区（file 模块必须同步改造）

代码复核确认：现有 `accessPolicy='private'` **不等于实际私有**。`GET /files/{id}/download(-url)` 只校验登录和同租户；匿名 `/exam/files/**` 可按 objectKey 读本地文件；COS 还可能生成公开 URL/预签名 URL。因此只新增 A2 不足以保护教材图片。

二期新增统一 `ProtectedFileAccessGuard` 和受保护 key 前缀 `protected/`。教材资产固定写入 `protected/textbook/{tenantId}/{yyyy}/{MM}/{uuid}.{ext}`：

1. file 模块增加受保护上传能力（如 `uploadProtectedForTenant(tenantId,file,'textbook')`），只负责安全生成 objectKey、存文件与元数据，不感知教材权限。`FileStorage.put` 需携带 protected 标记（或新增 `putProtected`）：local 仅改变受控目录，COS 据此显式设置对象私有 ACL，不能仅改 key 名称。
2. `ProtectedFileAccessGuard` 统一识别**URL 解码并规范化后**的 `protected/**`，同时拒绝 `%2F`、反斜杠、`..`、重复编码等路径变形，不能只 `startsWith` 原始请求串。以下通用入口对该区域**默认拒绝**，不能因为调用者同租户就放行：
   - `GET /files/{id}` 返回的公开 URL、`GET /files/{id}/download-url`、`GET /files/{id}/download`；
   - `DELETE /files/{id}`（防止绕过 A3 的快照引用检查）；
   - 通用 `presignedDownloadUrl` / `resolveExportFetchUrl`；
   - `/exam/files/**` 的本地读盘与 remote fallback，含 nginx/CDN 等价路径。
3. 教材 A2 是唯一在线读取入口：先经 `TextbookAccessService` 校验，再调用 file 模块内部 `buildDownloadResponse(tenantId,fileId,true)`。内部 Service 间读取（如 docx 导出）不受 Controller 通用拒绝影响，但也必须先做教材授权。A3/工程删除完成教材侧校验后，可调用 file 模块内部删除/提交后清理；被拒绝的是通用 `DELETE /files/{id}` 外部入口，不是内部清理能力。
4. 元数据查询可返回文件名/大小/类型，但受保护文件的 `url` 必须为 null；A1/A2 VO 只返回 `textbook-asset://` 和 A2 地址，不返回 objectKey、COS 地址或公开 URL。
5. local：受保护目录不能由 nginx alias 直接暴露；`/exam/files/protected/**` 必须在 Controller 最前面拒绝，部署侧再加一道 404 规则。
6. COS：受保护对象必须是私有 ACL，不能用公开桶策略或公开预签名绕开；如现网桶强制 public-read，则教材资产改用独立私有桶/受控存储配置，不能只靠 Java 校验。生产验收必须用未登录浏览器直接访问 objectKey 对应 URL 验证失败。
7. 其他既有业务文件不改 objectKey、不改变行为；只有 `protected/**` 默认拒绝，后续业务可复用同一安全区域。

### 5.7 结构冻结与一期接口改造

把判断收敛为 `TextbookStructureGuard`：

```java
boolean locked = existsAnyContent(projectId) || existsActiveAssignment(projectId);
```

| 一期操作 | 未 locked | locked 后 |
|---|---|---|
| 改章/节 title、targetWords、sortNo | outlined/reviewed 允许 | writing 允许；done 禁止 |
| 新增/删除大纲节点 | 仅 parsed/outlined；reviewed 必须先撤回 | 一律 409 + 原因 |
| 手动 rebuild | 仅 parsed/outlined | 一律 409 + 原因 |
| 改 functionNos / trainingHours / wordsPerHour 触发 regenerate | 仅 outlined | 一律 409 + 原因 |
| 改工程名称 | 非 done 允许 | 非 done 允许 |
| 删除工程 | 非 done 二次确认；任务、正文、快照、审定记录、资产元数据级联软删，文件按 file 模块提交后清理 | 同左；done 先由教研重开 |

若确需重建：先撤回大纲评审并取消所有有效分配；只要仍有正文记录就不允许重建。无正文且全部取消后，在工程锁内再次检查 locked 才允许重建，工程保持 outlined，之后必须重新评审和分配。

**分配记录与重建的唯一键规则**：不能每次重建都把全部旧分配软删，否则同一保留章第二轮会撞 `(tenant_id,chapter_id,deleted)`。`regenerate` 必须向调用方返回“保留原 ID 的章 / 被移除的章”：

- 保留原 ID 的章：保留其 `active=0` 分配行，下次分配复用该行；
- 被移除的章：软删对应分配行（这些旧节点 ID 不会再次复用）；
- 新增章：没有历史分配，后续插入新行。

这样同一手工保留章连续两轮“取消→重建→重新分配”不会产生重复软删历史或唯一键冲突。

## 6. 后端接口契约

统一前缀 `/textbook`；成功 `{code:'0',message,data,traceId}`；错误码 400/401/403/404/409/413/415/500。所有写操作加 `@AuditLog(module='textbook', ...)`。

W3 自动/手动保存不得把整篇 `contentMd` 写入审计详情。给现有 `AuditLog` 注解增加向后兼容的 `includeArgs() default true`，Aspect 仅在 true 时记录 args；W3 使用 `includeArgs=false`，保留操作者、时间、方法、targetId 等元数据。其他含长正文的响应也不得使用 includeResult=true。

通用约定：

- 请求和响应中的 ID 均为字符串；日期 `yyyy-MM-dd`，时间 `yyyy-MM-dd HH:mm:ss`。
- 分页请求 `page/pageSize`，响应 `items/page/pageSize/total`。
- 自动保存与冲突处理接口前端使用 `silentError:true`，由页面按场景展示，禁止全局 toast 与页面弹窗重复。
- 内容版本冲突：HTTP 409，`data.reason='VERSION_CONFLICT'`，并携带 `currentVersion/currentContentMd/currentUpdatedAt/currentUpdatedByName`，前端不得静默覆盖。
- 分配版本冲突：HTTP 409，`data.reason='ASSIGNMENT_VERSION_CONFLICT'`，并携带 `currentAssignment:AssignmentVO`。`assignmentVersion=null` 仅表示数据库从未有该章分配；已取消（active=0）的记录重新分配时也必须传当前版本。

| # | 方法与路径 | 权限 | 默认筛选 |

筛选口径：

- writing 任务：`assigned/writing/returned/reviewing/approved/overdue`。
- review 任务：`pending`（submittedCount>0）、`returned`（returnedCount>0）、`approved`、`all`。
- 同一章可能同时满足“有待审定节”和“有打回节”，允许在两个筛选中出现，不强行合并成单一展示状态。
- 默认排序统一为 `overdue DESC, latestSectionUpdatedAt DESC NULLS LAST, assignmentId DESC`，数据库按现有 MySQL 语法实现，不能照抄 NULLS LAST 关键字。

统计卡由 T3/T4 提供，**不受 status/keyword/overdueOnly/分页影响**，只按当前用户 + active 统计；不能用当前页 items 合计。字段定义：

```json
// T3 WritingTaskSummaryVO（卡片可点选对应筛选；各口径可能相交，不要求相加等于总数）
{"assignedCount":1,"writingCount":2,"pendingReviewCount":1,"returnedCount":1,"approvedCount":3}
// assignedCount：taskStatus=assigned；writingCount：taskStatus=writing；
// pendingReviewCount：submittedCount>0；returnedCount：returnedCount>0；
// approvedCount：taskStatus=approved

// T4 ReviewTaskSummaryVO
{"pendingCount":2,"returnedCount":1,"partialApprovedCount":1,"approvedCount":3}
// pendingCount：submittedCount>0；returnedCount：returnedCount>0；
// partialApprovedCount：approvedCount(节)>0 且 taskStatus!=approved；approvedCount：taskStatus=approved
```

必须补“任务总数大于 pageSize 时统计卡仍是全量”的测试。

**空正文契约（不能用 404 表示）**：授权通过但尚无正文记录时，W2 返回 200：`contentExists=false, contentStatus=null, contentMd='', wordCount=0, version=0, submitRevision=null, currentSnapshotId=null`；W1 同样用 `contentExists=false/contentStatus=null`。首次保存成功后为 `contentExists=true/contentStatus='draft'/version=1`。对象越权仍返回 404，前端不得把 404 当初始化空正文。

`latestReviewRecord` 是最近一条 submit/approve/return/reopen，供页面直接展示；完整时间线走 W6。`submittedByName` 是实际提交人，不能因后来改派而显示成新主笔。

W1/W2 的 `submitRevision/currentSnapshotId` 是**当前内容所对应的提交快照**，只在 contentStatus=submitted/approved 时非空；draft/returned 下为 null。打回意见针对哪一版由 `latestReviewRecord.submitRevision` 表示，恢复或继续编辑后不得还把旧快照标成“当前正文版本”。这些 VO 字段可由最新 submit 快照与当前状态派生，无需在当前正文表增加循环外键。

W5：

- `action=approve`：仅 submitted → approved，comment 可选。
- `action=return`：仅 submitted → returned，comment 必填。
- `action=reopen`：仅 approved → returned，comment 必填。
- 每次均校验 `baseVersion`、`submittedBy != 当前审定人`；状态不符返回 409，不在后端悄悄跳过。
- 工程 done 下 W5 全部 409；只有教研 C6 重开为 writing 后才允许 reopen。

## 7. 核心事务与防御规则

### 7.1 统一工程锁与锁顺序（消除改派/完成/重建竞态）

仅比较 `baseVersion` 不能防止“授权检查后管理员完成改派，原主笔仍写入”的 TOCTOU。二期所有相关写操作使用同一顺序：

```text
SELECT project ... FOR UPDATE
  → SELECT assignment ... FOR UPDATE（存在时）
    → SELECT content ... FOR UPDATE（存在时）
      → 锁后重新读取并校验 active、writer/reviewer、工程状态、内容状态、baseVersion
        → 写数据并 refreshChapterSummary
```

- C3/C4 分配/改派/取消、W3/W4/W5/W9、A1/A3、C5/C6、一期工程 update/status、结构重建/工程删除都必须先锁同一个 project 行；多章批量按 chapterId 升序锁分配，避免死锁。
- 工程行是本工程写操作的粗粒度互斥点。正文保存只持短数据库事务，不在锁内调用 LLM/HTTP/COS/磁盘，实测可接受；不得以缩小锁范围为由重新引入改派竞态。
- 图片 A1 可先做一次预检并在锁外上传存储，但写入资产元数据前必须按上述顺序加锁、重新授权；失败则删除刚上传文件。长文件 IO 不放在工程锁内。
- C5 complete 在工程锁内重新查询所有章/节/分配/占位，不只用缓存；与 reopen/cancel/首次分配/rebuild 自然互斥。
- StructureGuard 的无分配/无正文检查也必须在工程锁后执行，防“检查通过后首个分配恰好创建，rebuild 又删除节点”。
- 并发测试必须用栅栏/ CountDownLatch 控制两个线程真正交错，不能只测“先改派、后请求”。

### 7.2 保存草稿

```text
HTTP 线程：
1. 按 §7.1 锁 project → assignment → content，锁后 requireCurrentWriter，
   确认工程 writing、分配 active。
2. 无记录（contentExists=false）可首存；已有记录状态必须 draft/returned，否则 409。
3. 校验 contentMd 长度（≤1,000,000 字符）、Markdown 安全与资产归属。
4. baseVersion=0：插入唯一当前正文，插入后 version 必须为 1；唯一键冲突按 409 处理。
   baseVersion>0：UPDATE ... WHERE id=? AND version=?；影响行数=0 → 409，后续写操作才递增。
5. 计算 wordCount/checkReport；updatedBy/At 由 BaseEntity 填充。
6. 同事务 refreshChapterSummary。
7. 返回最新 SectionContentVO。
```

不要只依赖 `@Version` 注解或假定 MP 乐观锁插件存在；实施时使用显式版本条件更新并检查影响行数。

### 7.3 提交审定

1. 与保存相同的工程锁、主笔/状态/baseVersion 校验。
2. 正文经 Markdown 转纯文本后必须非空白；只有图片不算可提交正文。
3. 重新计算检查报告；检查有警告仍可提交，由前端二次确认，**不拦截专家判断**。
4. 生成 `snapshot_type=submit` 快照，`submit_revision=当前最大+1`。
5. 当前正文置 submitted，记录 submittedBy/At，清空 reviewedBy/At，version+1。
6. 写 review_record(action=submit)，同事务刷新章进度。

### 7.4 通过 / 打回 / 撤销

1. 按工程锁锁定后 `requireCurrentReviewer`，校验 active 与 baseVersion；done 一律 409。
2. 当前用户不得等于 submittedBy；章 writer/reviewer 同人也在分配时拦截。
3. 严格按 §3.2 状态迁移；return/reopen 的 comment trim 后 1~1000 字。
4. 更新正文、version、reviewedBy/At；追加 review_record；刷新章进度。
5. approve 不自动完成工程；done 只能先由教研 C6 重开，审定人不得直接改工程状态。

### 7.5 恢复历史版本

1. 按工程锁锁定并校验当前主笔、工程 writing、baseVersion、当前状态 draft/returned。
2. 校验 snapshotId 确实属于本节；不能拿其他节快照恢复。
3. 先把当前内容保存为 `before_restore` 快照（submit_revision=null）。
4. 用选中的快照覆盖当前 contentMd，**保持原状态：draft→draft、returned→returned**，不得借恢复清除打回标识。
5. 清空当前轮 submittedBy/submittedAt/reviewedBy/reviewedAt（历史仍在 review_record）；version+1，重算字数/检查报告并刷新章进度。
6. 返回最新 W2；整个步骤一个事务，失败时 before_restore 与正文更新一起回滚。

### 7.6 并发与改派

- 同节两个浏览器标签：第二个旧 baseVersion 保存返回 409，不覆盖第一个。
- 自动保存请求必须串行：前端上一次未返回不得并发发起下一次；返回乱序时只接受版本更高的响应。
- 改派后原主笔保存返回 404/409，前端弹“任务已改派”，保留本地未保存内容，不反复重试。
- 快照序号和 submit_revision 均在工程锁内查最大值并依赖唯一键兜底；冲突返回 409 可重试，不生成重复版本。
- 必须覆盖真正并行的 complete/reopen、complete/cancel、rebuild/首次分配、改派/保存、改派/审定、删除图片/提交测试。

## 8. Markdown、检查与图片安全

### 8.1 统一 `TextbookMarkdownSupport`

前端复用 `md-editor-rt`；后端增加一个 Markdown 解析/渲染实现（建议 `flexmark-java`，实施时在 pom 统一管理版本），供保存校验、字数/覆盖检查、docx 导出共同使用，禁止三套各自理解 Markdown。

允许：标题、段落、粗斜体、列表、引用、表格、代码块、http/https/mailto 链接、内部图片。

禁止：

- 原始 HTML block/inline（含 script、iframe、style、事件属性）。
- `data:`、`javascript:`、`blob:`、外链图片。
- 不属于本节的 `textbook-asset://id` 引用。
- 伪造 assetId、跨章/跨工程/跨租户资产引用。

前端预览继续使用 sanitize-html 作为第二道防线；后端校验失败不保存，不能“前端过滤后就算安全”。

### 8.2 图片显示与导出

- 编辑器上传成功后插入 `![图注](textbook-asset://{assetId})`。
- 在线预览时前端先把内部 URI 替换为经授权 A2 获得的 blob URL；关闭工作台统一 revoke。
- docx 导出时后端再次校验每个资产归属，再经 file 模块内部受控读取字节，不通过服务端自回环 HTTP 拉取；资产存储与通用入口防护严格按 §5.6。

### 8.3 字数与确定性检查（非 LLM）

后端将安全 Markdown 渲染后取纯文本，统一：

```text
wordCount = 纯文本去除所有空白字符后的字符数（标点计入，Markdown 标记/图片 URI 不计）
```

`checkReport`：

```json
{
  "wordCount":1200, "targetWords":5000,
  "minSuggestedWords":4000, "maxSuggestedWords":6000,
  "withinTargetRange":false,
  "uncoveredPoints":[{"pointId":"9201","title":"换极表知识","dimension":"theory"}],
  "placeholderCount":1,
  "checkedAt":"2026-10-24 12:00:00"
}
```

- 字数建议区间 = targetWords ±20%；无 targetWords 则不做区间判断。
- 覆盖检查取该节直接子级全部理论/技能点；去除编号、空白和常见标点后做**完整标题包含匹配**。未命中只表示“可能未覆盖”，不可伪称语义覆盖判定。
- `[待专家补充]` 计数；final 导出和完成工程禁止仍有占位。
- 这些结果均为提示，除“空正文”和 final 占位外不阻止提交/通过。

## 9. docx 合成导出设计

新增 `TextbookBookExporter`，复用一期 `ExportFile` 与 Controller 下载响应方式，使用 POI XWPF。

### 9.1 内容与顺序

1. 按 outline 的 parentId + sortNo + id 顺序遍历篇/章/节；不根据分配顺序、姓名或 ID 排序。
2. 篇 → Heading 1，章 → Heading 2，节 → Heading 3。
3. 节下输出当前正文；标准点不自动重复追加到正文后。
4. review 模式：空节插入“[本节未编写]”，非 approved 节在节标题下标注“草稿/待审定/已打回”；`[待专家补充]` 黄色高亮。
5. final 模式：仅 done 可导出；再次后端校验全部 approved 和无占位，不能仅相信前端按钮状态。

### 9.2 样式映射（实施基线）

- 封面：教材名（工种-方向-等级）、标准版本、导出时间；review 模式额外标“编写审阅稿”。
- 正文：宋体 12pt、1.5 倍行距；篇/章/节标题用黑体并设置 Heading 级别以生成 Word 导航。
- 节内 Markdown h1~h6：统一映射为自定义“节内标题”样式（加粗、字号按级递减、正文级 outline level），**不得映射成 Word Heading 1/2/3**，不进入教材篇/章/节三级导航；导出测试需断言篇/章/节导航未被正文标题污染。
- 列表保留项目符号/编号；引用左缩进；代码块等宽字体；表格使用 Word 表格并加边框。
- 图片按原始比例缩放，版心最大宽度约 15cm；无法读取的图片在 review 稿中显示明确占位并记录 warn，final 导出则失败并指出节名。
- 链接显示“文字（URL）”；不保留任何脚本/原始 HTML。

### 9.3 文件名与边界

- 单节：`教材节_{工种}_{章}_{节}_{yyyyMMddHHmm}.docx`。
- 单章：`教材章_{工种}_{章}_{yyyyMMddHHmm}.docx`。
- 整册：`教材正文_{工种}_{方向}_{等级}_{review|final}_{yyyyMMddHHmm}.docx`。
- 文件名 sanitization 复用现有下载口径，特殊字符替换，Header 使用 UTF-8 filename*。
- 二期导出为同步、有界操作：前端 timeout 120s；实现需以 100 节、30 万字、50 张图片做性能测试。若实测超过时限或内存不可控，应先限制单次图片总量并明确 413，再考虑异步导出，禁止无界加载后静默超时。

- 无合适人选时给明确提示：“请先在用户管理中为该账号绑定教材编写专家/审定专家角色”，不能提交一个无权限用户。
- 批量分配：先勾选章，再统一选主笔/审定人/日期/说明；确认页列出将影响章数。已存在的分配显示“将改派”，提交后整批成功或整批失败。
- 改派已有 submitted/approved 内容的章时，Modal 明示：“改派不改变已提交/已通过状态”，避免误以为会重置。

### 10.4 我的任务 `TextbookMyTasksPage`

- 顶部统计卡直接调 T3/T4：编写模式显示待开始、编写中、待审定、已打回、已完成 5 卡；审定模式显示待审定、已打回、部分通过、全部通过 4 卡。卡片点击切换列表 status，统计数字仍保持当前用户全量口径，不受分页/筛选影响；相交口径在卡片下注明，不强行求和。
- 表格：教材（工种/方向/等级）、章、截止、字数进度、节进度、状态、最近更新、操作。
- 主笔操作按状态显示 `开始编写/继续编写/查看提交/修改打回`；审定人显示 `去审定/查看`。
- 逾期红字且排序优先；默认按“逾期 → 最近更新倒序”。
- 空态区分：“还没有分配编写任务”与“当前筛选无结果”；不显示全量工程入口。

### 10.5 主笔工作台 `TextbookWritingWorkbenchPage`

桌面三栏：左侧 260px 节导航，中间自适应编辑器，右侧 320px 编写要求与检查；窄屏右栏移到编辑器下方，主操作仍平铺。

**左栏：**

- 章标题、总进度；节列表按 sortNo，不按状态重排。
- 每节显示标题、状态图标、实际/目标字数；当前节高亮；有打回意见显示红点。
- 顶部筛选仅作显示过滤：全部/未完成/待审定/已通过。

**中间：**

- 章/节标题、状态 Tag、目标字数、保存状态（未保存/保存中/已于 HH:mm:ss 保存/保存失败）。
- `MdEditor`：编辑与预览切换；图片通过 A1 上传；工具栏不出现外链图片入口。
- 主操作平铺：`保存草稿`、`提交审定`、`历史版本`、`导出本节`。
- submitted/approved/非当前主笔时只读，并在顶部说明原因和当前处理人，不能只把按钮变灰。

**右栏：**

1. 编写要求：章/节目标字数、标准理论点/技能点原文、分配说明、审定人。
2. 检查结果：建议字数区间、可能未覆盖点、待补充占位；标明“仅供检查，不代替专家判断”。
3. 最近审定意见：审定人、时间、意见；历史记录可查看完整时间线。

**自动保存与离开保护：**

- 停止输入 3 秒触发一次；连续输入时最长 30 秒兜底一次；Ctrl+S 手动保存。
- 自动保存串行；失败保留编辑内容和本地备份，指数退避最多 2 次后暂停并提示手动重试。
- 切换节/返回/关闭页面前若 dirty，先尝试保存；失败则弹选择“继续留下 / 放弃未保存内容离开”，不可直接丢稿。
- 本地备份键含 username+sectionId+baseVersion；保存成功清除，加载时仅在服务端版本仍匹配时提示恢复。
- 409 冲突弹窗：显示服务端版本/更新人/时间，提供“加载服务端最新”和“下载我的草稿为 .md”；不自动以后到内容覆盖先到内容。

**提交：**

- 先确保最新草稿保存成功，再 submit；检查有警告时 Popconfirm 列出“字数偏离/疑似未覆盖/待补充”。
- 提交成功切只读、刷新章进度与审定人队列，不自动跳下一节，便于主笔检查提交结果。

### 10.6 审定工作台 `TextbookReviewWorkbenchPage`

复用三栏结构，但中间为只读渲染：

- 左栏节状态；中间正文与图片；右栏编写要求、当前提交版本、主笔、提交时间、历史意见。
- 主操作平铺：`通过`、`打回`、`导出本节`；已 approved 时显示 `撤销通过`。
- 打回/撤销打开 Modal，意见必填（1~1000 字）；通过后显示下一待审定节按钮，减少返回列表次数。
- 审定人不能修改 Markdown、不能替主笔提交，接口也无“管理员代审”隐藏入口。

### 10.7 历史版本 `TextbookVersionDrawer`

- 列表：提交第 N 版/恢复前快照、时间、操作人、字数；最新当前版本单独标识；W7 分页加载，抽屉底部“加载更多”，不一次拉取全部历史。
- 查看：选快照与当前内容并排渲染；二期不实现字符级 diff 算法。
- 恢复：仅当前主笔且 draft/returned 可操作；若当前 dirty 先提示；后端先存 before_restore，再恢复正文且保持 draft/returned 原状态，不用恢复操作清除打回。
- submitted/approved 时只允许查看，不允许恢复覆盖。

```text
  TextbookStructureGuard.java            // 一期/二期共用结构保护
  TextbookProjectLockService.java        // project → assignment → content 统一锁顺序
  TextbookSectionAssetApplicationService.java
  TextbookBookExportApplicationService.java
domain/
  TextbookMarkdownSupport.java           // 安全、纯文本、检查共用
  TextbookContentChecker.java

  FileApplicationService.java            // 受保护上传、受控内部读取；不改变既有文件行为
  ExamTaskXimuController.java            // /exam/files/protected/** 最前面拒绝
```

部署配置还需检查 nginx/CDN/COS 公开访问路径（§5.6），不能只改 Java。

事务边界在 ApplicationService；Controller 不直接访问 Mapper；`TextbookProgressService.refreshChapterSummary` 由写操作同事务调用。

**流程引擎边界**：本二期沿用一期已有的 textbook 表内状态机，不为每节创建 Flowable 流程实例。这里的提交/打回是单章内轻量编写状态，不是新增多级组织审批流；若后续加入编委会会签、多级终审等跨角色流程，再单独评估 BPMN/Flowable，不在本期暗中引入第二套状态源。

**审计共享小改造**：`AuditLog` 新增 `includeArgs() default true`，`AuditLogAspect` 按该标记决定是否记录 args，既有调用默认行为不变；W3 显式关闭，避免自动保存把正文灌入日志。

二期没有 AI 和异步批处理，保存/审定/导出均保持 HTTP 同步有界执行，**不要为了“显得高级”新增 `@Async`**。若后续引入 AI 或异步导出，必须另行设计 HTTP 线程捕获 tenant/user、Worker TenantContextHolder 与 AbortPolicy 的完整链路。

## 14. 实施顺序（tracer bullet，不按层横切）

| 阶段 | 纵向切片 | 交付与门槛 |
|---|---|---|
| M0（0.5~1 人天） | 复核当前代码/两库迁移取号；冻结本文 API/状态/权限；准备 2 个专家测试账号 | 契约无歧义；角色种子可独立验证 |
| M1（3~4 人天） | **最窄闭环**：1 章分配 → 1 节保存 → 提交 → 打回/通过 → 单节 docx | 后端权限与版本冲突测试先绿；不等全部页面 |
| M2（3~4 人天） | 教研分配页 + 我的任务 + 三栏工作台 + 全章进度 | 两主笔一审定人可走通；前端 Vitest |
| M3（4~5 人天） | 受保护文件区与通用入口防护、图片、历史快照/恢复、自动保存冲突处理、结构冻结、改派与工程锁 | 越权/丢稿/孤儿正文/通用文件绕过/真正并行测试齐绿 |
| M4（3~4 人天） | 单章/整册 review/final docx、完成/重开、菜单种子、e2e | 主链路 e2e + 真实 docx 目检 + 验收清单 |
| 合计 | **约 15~19 人天** | 不含 LLM/素材/案例/习题/Word 回传 |

实施时每阶段都保持可运行：先打通最窄端到端，再横向增加章数、版本和导出，不先建完全部表/页面后才发现权限模型冲突。

## 15. 上线与存量兼容

1. 一期已有工程无分配、无正文，行为不变；reviewed 工程由教研首次分配后自动进入 writing。
2. 不做正文/分配历史数据回填；`textbook_section_content` 等新表从空开始。
3. 一期目录导出 md/xlsx 保持原路径与格式；正文 docx 是新接口。
4. 菜单/角色种子上线后，先由 admin 创建或选择 2 名主笔、1 名审定人绑定角色，再开放试用；不自动把现有考评专家转为教材专家。
5. 生产验证顺序：迁移三步链 → 候选人 → 分配 → 编写/审定 → 导出 → 权限反例。图片还需在未登录和同租户非归属账号下分别验证 objectKey/fileId/通用下载/预签名均不可读；任何一步失败不继续扩大专家范围。
6. 回滚代码时不得删除新表；若新代码已产生正文，旧代码不具备编写页但数据仍保留，恢复新版本后可继续使用。

## 16. 需求方审核时重点看什么

1. **每章一名主笔和一名审定人、节随章归属**是否符合实际组织方式。
2. **主笔提交后只读、独立审定人逐节通过/打回**是否符合实际审稿流程。
3. **改派不重置内容状态**、**进入编写后冻结节点身份**是否是可接受的约束。
4. 二期只做在线编写与 docx 导出，不做 AI/素材库/案例库/Word 回传，边界是否准确。
5. 页面是否足够简单：专家只需要“我的任务 → 编写/审定”，其余分配、进度、导出由教研处理。

以上口径在本文中均已按已确认方案展开；如审核修改其中任一项，应同步修改状态机、权限矩阵、接口和测试，不允许只改页面文案。
