## 1. 结论速览

| 维度 | 现状 | 结论 / 优化项 |

## 2. 现状核实（逐条证据）

### 2.1 并发：批次间并行，批次内严格串行

已做到：异步拆分符合 AGENTS.md LLM 规范 #7（`submit` 秒回 batchId，Worker 异步，前端轮询）；批次间并发 `theoryGenExecutor`（`AsyncConfig.java:84-95`）+ AbortPolicy 503 兜底（坑 #12/#14）；线程边界干净（tenantId/userId 参数传递、Worker 自行 set/clear `TenantContextHolder`、禁调 `SecurityContext`）；暂停只挡新块（踩坑 #18）。

未做到：`processBatch` for 循环逐个考评点串行调 LLM（`TheoryGenBatchService.java:183-195`），1 批次 = 1 线程。以 200 考评点细目表估算（单块 30~60s，实测基线可查 `exam_theory_gen_draft.gen_duration_ms`），整批 **1.5~3.5 小时**。串行是主方案明确设计，非实现走样，但当时未考量"块间无依赖、可并行"。

块级并行可行性：考评点间无依赖；查重仅块内（`TheoryQuestionValidator.checkDuplicates:164`）；落库按块 insert；done/failed 计数走 SQL 原子自增。需重新设计的仅是熔断口径与暂停派发点。

### 2.2 缓存（v0.2 按官方文档更新）

1. **应用层零缓存**：无"同考评点重复生成 → 复用结果"机制。
2. **厂商侧缓存已确认可利用**：GLM 隐式上下文缓存自动命中、无需 API 参数，GLM-5.3-Flash 在支持列表，命中部分约按标准价 50% 计费（§2.5）。现有 prompt 结构天然有利：system prompt 批次内恒定（`TheoryGenPromptBuilder.buildSystemPrompt:38`），user prompt 仅含点数据。缺的是**观测**（命中量不可见）与**防回归**（后续改动不得把变化文本拼进 system prompt）。
3. **费用可观测性为零**：`batch.token_usage` 恒为 0——`FaqLlmClient.chatCompletion` 只回传 content，完整响应（含 `usage`）在边界被丢弃（`executeChatCompletion` 已拿到完整 JsonNode，`FaqLlmClient.java:170`）。违反 AGENTS.md LLM 规范 #10。

### 2.3 缺陷：恢复/重试会把已完成考评点重新生成（静态分析结论）

`processBatch` 循环全部考评点，无"该点已有草稿则跳过"判断；`resume:335` / `retryFailed:357` 重新提交后从第 1 个点重跑 → 草稿重复插入 + token 双倍花费 + `done_points` 可超 `total_points`。`retryFailed` 注释"已完成草稿保留"与实现不符。生成耗时长（数小时），用户暂停再继续是常见操作，触发概率不低。P1 实施时先补复现测试再修复。

### 2.4 同蓝图跨批次重复生成（记录在案，本期不处理）

查重不跨批次：删旧批次后重新提交会再次生成相似题目。是否做"与历史草稿相似度去重"属产品决策（多批次产出更多样的题也可能是期望行为），后续单独立项。

### 2.5 智谱官方文档核实结论（2026-09-06，https://docs.bigmodel.cn）

| 核实项 | 官方结论 | 对本项目的影响 |
|---|---|---|
| thinking 参数 | `thinking:{type:"enabled"\|"disabled"}`；`reasoning_effort` 为**顶层**字段 | 现实现一致 ✓ 无需改 |
| GLM-5.3-Flash 思考 | **不可关闭**（disabled 报错）；`reasoning_effort` 仅支持 `max/high/low` | 现默认 `low` 合法 ✓；submit 需加配置校验（P0） |

## 3. 改进项

### P0 前置修正：model_id 官方编码 + GLM 配置校验（新增，最先做）

**背景**：R2/R3。种子 `model_id='GLM-5.3-Flash'` 与官方编码 `glm-5.3-flash` 不符；GLM-5.3-Flash 传 `thinking=disabled` 或非法 `reasoning_effort` 会直接报错（表现为整批块失败）。

**方案**：
1. 新 Flyway 迁移（版本号执行时实时 `SELECT MAX(version)` 取号）：`UPDATE exam_faq_model_config SET model_id='glm-5.3-flash' WHERE model_code='theory-gen-glm' AND model_id <> 'glm-5.3-flash'`（幂等可重放；不动已应用的 `V20260904_013`）
2. `submit` 增加配置校验（baseUrl 含 bigmodel 时，口径 R9）：`thinking` **显式等于 `'disabled'`** → 拒绝并提示"GLM-5.3 系列不可关闭思考"（空/null 不发 thinking 节点、API 默认 enabled，合法放行）；`reasoning_effort` **非空**且 ∉ {max, high, low} → 拒绝
3. 主方案 v1.2 C3 的种子值以本修正为准

**验收**：单测覆盖两条校验分支；迁移在测试库重放幂等；`DESCRIBE`/`SELECT` 核对落库值。

### P1 修复恢复/重试全量重跑 + 块落库原子化（止损）

**方案**：
1. `processBatch` 循环前一次性查出本批次已有草稿的考评点集合，循环内跳过：

```java
Set<Long> doneNodeIds = draftMapper.selectList(new LambdaQueryWrapper<TheoryGenDraftEntity>()
        .eq(TheoryGenDraftEntity::getBatchId, batchId)
        .select(TheoryGenDraftEntity::getNodeId))
    .stream().map(TheoryGenDraftEntity::getNodeId).collect(Collectors.toSet());

for (TheoryBlueprintNodeEntity point : points) {
    // 状态检查（保持现有：每块派发前重读，R8 后同时校验 run_id）
    if (doneNodeIds.contains(point.getId())) {
        continue;   // 断点续跑：已完成点不调 LLM
    }
    ...
}
```

2. **编排独占权 run_id**（R8 缺陷修复）：新迁移为 `exam_theory_gen_batch` 加 `run_id BIGINT NULL`；`submit`/`resume`/`retryFailed` 每次发起编排时生成新 `run_id`（雪花 ID），`processBatch` 启动时捕获本次 run_id，逐块状态检查改为"状态 = RUNNING **且** run_id 与本次一致"才继续派发——旧编排器读到新 run_id 即自行退出，杜绝双编排器
3. **块落库原子化**（R4 并入）：`saveDrafts` 当前逐题 insert 无事务，中途异常留"半块"会导致跳过误判。改为块级事务（因同类自调用 `@Transactional` 不生效，用 `TransactionTemplate`），一块草稿要么全落要么全不落。此后"该点有草稿"="该块完整完成"成立
4. `resume`/`retryFailed` 的编排重入逻辑不变（仅补 run_id 生成），语义自动变为断点续跑

**边界说明**：草稿在审核环节被人工删除后重试，该点会重新生成（`deleted=0` 由 MyBatis-Plus 自动过滤）——这正是期望行为。

**风险**：低。纯减少调用量，不新增并发。

**验收**：单测（mock LLM client）：① 3 点批次第 2 点后暂停→恢复，断言已完成点 LLM 调用次数为 1（未被重复调用），草稿不重复，`done_points` 不超 `total_points`；② 失败批次 retryFailed 仅重跑失败点；③ saveDrafts 模拟中途异常，断言该点草稿整体回滚；④ run_id 竞态：模拟旧 run_id 编排器在状态恢复 RUNNING 后检查，断言其停止派发

### P2 Token usage 采集与落库（费用度量，P4 前提）

**方案**：
1. `FaqLlmClient` 新增 `chatCompletionDetailed(...)`：返回 DTO `{content, promptTokens, completionTokens, totalTokens, cachedTokens, durationMs}`；内部复用现有 `executeChatCompletion`（完整响应已在手）。**新增参数 `responseTimeoutSeconds`**（R5 拍板：理论生成链路传 180，既有调用走原全局 90s 默认值）。现有 `chatCompletion` 委托新方法后丢弃扩展字段——**FAQ 等既有调用方签名与行为不变，零回归**
2. usage 解析按双口径（模型配置可切换厂商）：GLM 读 `usage.prompt_tokens_details.cached_tokens`；DeepSeek 读 `usage.prompt_cache_hit_tokens`；两者皆无则 cachedTokens=0。字段缺失按 0 记不报错（输出零信任）
3. `TheoryGenAiService.generateForPoint` 改返回 detailed DTO；`processBatch` 每块经 SQL 原子累加 usage（R10），失败块的已产生用量同样计入；日志逐块打印 prompt/completion/cached/duration
4. 新 Flyway 迁移加列（已拍板）：`exam_theory_gen_batch` 增 `prompt_tokens BIGINT`、`completion_tokens BIGINT`、`cached_tokens BIGINT`，默认 0；批次收尾时一并写入（现有 `token_usage` 继续累加 total_tokens，兼容既有展示）

**改动点**：`FaqLlmClient`（新增方法，不改既有签名）、`TheoryGenAiService(Impl)`、`TheoryGenBatchService`、新迁移。`FaqLlmClient` 为 FAQ 链路共用组件，改动前按 AGENTS.md 并行约束取得模块 owner 授权。

**验收**：单测（桩响应）：双口径解析、聚合落库、usage 缺失容错；FAQ 链路回归测试全绿；真实试产批次后 `prompt_tokens>0`。

### P3 批次内块级并发（等待时间，收益最大）

**方案**：编排/执行分离。`theoryGenExecutor` 线程只做编排，块任务跑新增 `theoryGenBlockExecutor`：

- 新池：`ThreadPoolTaskExecutor`（坑 #14 具体类型 + `@Qualifier`），core=max=**5**（决策 #1 拍板，做成配置项可调）、queueCapacity=N（吸收"信号量释放→线程就绪"交接抖动，在飞 LLM 调用数由同源信号量保证 ≤ N）、AbortPolicy（坑 #12）
- 编排循环：`semaphore.acquire()`（permits=5，R11：配置键 `theory.gen.block-concurrency`，默认 5）→ 读批次状态（非 RUNNING **或 run_id 与本次不一致**（R8）停止派发）→ P1 跳过已完成点 → 提交块任务；循环结束后 join 全部 future 收尾置 DONE。已派发块跑完才停（踩坑 #18 语义一致）
- **拒绝处理写明**：semaphore 先 acquire 再 submit，正常不会拒绝；若 `RejectedExecutionException`（池关闭等极端情况）→ release 信号量并计该块失败
- **熔断口径**（R7 定稿）：保持原语义——按块**完成顺序**计连续失败数（线程安全计数器，成功归零、失败 +1），≥5 停止派发并等在飞块结束后置 FAILED。与串行版语义一致，无非预期行为变化
- **限流口径**（R7 定稿）：GLM 1302/1305 与 HTTP 429 统一计块失败，由"重试失败块"兜底，不做块内退避重试（简单口径；试产后若限流频发再评估升级）
- **峰值并发说明**：批次间 max=2 × 块内 5 = 同账户最多 10 路并发调用。GLM 限流按账户权益等级配置（控制台可查），若试产出现 1302 则调低 N（配置项）或批次间并发降为 1
- 超时：块调用经 P2 新方法传 `responseTimeoutSeconds=180`（R5 拍板）
- 多租户：每 Worker 线程独立 set/clear `TenantContextHolder`（踩坑 #15/#17），全链路禁调 `SecurityContext`（陷阱 #2）

**预期收益**（200 点、单块 40s 估算，基线以 `gen_duration_ms` 实测为准）：

| 并发度 | 整批耗时（估算） | 相对现状 |
|---|---|---|
| 1（现状） | ≈ 2.2 小时 | — |
| 3 | ≈ 45 分钟 | ~3× |
| **5（拍板）** | **≈ 27 分钟** | **~5×** |

**风险与对策**：厂商限流（N 可配 + 1302 口径 + 峰值说明）；缓存命中率略降的可能性（同批次调用仍在分钟级窗口内，实施后用 P2 的 `cached_tokens` 实测验证）；并发语义复杂化（单测覆盖全成功/熔断/暂停/断点续跑四路径）。

### 8.7 自动补跑（2026-09-06，需求方提出：缺口批次无法继续完成）

**需求背景**：E2E 批次"已完成"但进度 144/200（56 点失败），原"重试失败块"仅支持 FAILED 状态，缺口无法补齐。

**已实施**：
1. **编排内自动补跑**：`processBatch` 改为多轮循环（上限 `MAX_DISPATCH_ROUNDS=3` 轮 = 首轮 + 2 轮补跑）。每轮派发前重查"已有草稿的考评点"（与 P1 断点续跑同一机制），只跑缺口点；轮间退避 `n×retry-backoff-base-millis`（默认 10s，配置键 `platform.theory.gen.retry-backoff-base-millis`），退避期间分片睡眠并持续响应暂停/编排接替；全部完成即提前收敛为 DONE
2. **熔断语义**：连续失败熔断每轮独立计数；触发即整体终止（系统性故障不再浪费补跑调用），置 FAILED
3. **轮次耗尽仍有缺口** → FAILED，fail_reason 注明"自动补跑 N 轮后仍有 M 个考评点未完成"
4. **人工兜底**：`retryFailed` 放宽——失败批次或**已完成但有缺口**（done<total）的批次均可重试；前端"生成任务"列表对后者显示"补跑缺口"按钮
5. 配置：`platform.theory.gen.retry-backoff-base-millis`（默认 10000，环境变量 `PLATFORM_THEORY_GEN_RETRY_BACKOFF`）

**测试**：新增 OPT-18（首败后自动补跑至全量 DONE）、OPT-19（持久失败 3 轮耗尽 → FAILED）、OPT-20（done-with-gap 人工重试放行/无缺口拒绝）；OPT-05/06 适配多轮语义；测试基建补"草稿持久化模拟"（insert 累积 → selectList 反映已落库集合，多轮跳过依据）。39/39 通过。
