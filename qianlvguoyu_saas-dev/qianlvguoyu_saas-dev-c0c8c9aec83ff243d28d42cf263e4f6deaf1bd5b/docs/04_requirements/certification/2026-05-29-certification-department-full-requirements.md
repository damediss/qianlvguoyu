# 认定部功能模块完整落地需求设计

版本：V1.0  
日期：2026-05-29  
适用项目：千铝国昱云平台 `qianlvguoyu_saas-dev`  
原型来源：`D:\new_proj_docs\认定工作流程`、项目内 `prototypes/certification`  

## 1. 文档目标

本文档将认定部原型页面整理为可开发、可测试、可上线的完整需求设计。设计目标不是还原静态页面，而是形成认定部全流程业务系统：

- 支持认定需求、认定任务、认定执行、归档、补贴和数据看板的完整闭环。
- 支持工作流程中的提交、审核、驳回、复核、归档等关键审批动作。
- 支持多类业务数据结构化存储，包括任务、人员、资料、考场、设备、材料、考试结果和归档档案。
- 支持文件全生命周期管理，包括上传、业务关联、版本、审核、归档、下载和审计。
- 复用现有平台底座，包括多租户、用户角色权限、统一文件服务、审计日志、API 响应规范和前端技术栈。

## 2. 建设原则

1. 完整闭环优先：所有原型中出现的页面、动作和业务对象都纳入需求，不以 MVP 名义裁剪核心链路。
2. 业务状态后端可信：前端只展示和发起动作，流程阶段、审批结果、资料完整性和归档状态以后端为准。
3. 文件只存元数据和引用：业务表保存 `file_id`、文件用途、版本、状态和归属，不保存文件内容。
4. 审批过程可追踪：每次提交、审核、驳回、复核、撤回、归档必须形成记录，可按任务和业务对象回溯。
5. 数据按任务归集：认定任务是主业务容器，考生、资料、检查清单、考试结果、档案都必须能回到任务。
6. 可分阶段交付但不丢设计：实施可以分批，数据模型、流程状态和权限边界按最终落地一次设计。

## 3. 与现有平台关系

### 3.1 现有能力复用

- 后端主服务：继续在 `services/platform-api` 内实现，新增 `certification` 业务包。
- 文件服务：复用现有 `/files` 上传、查询、下载能力。
- 权限体系：复用系统用户、角色、菜单、权限码和 `@PreAuthorize`。
- 多租户：所有认定业务主表必须包含 `tenant_id` 并受 MyBatis-Plus 租户插件约束。
- 审计日志：写操作、审批动作、文件关联和归档动作必须记录审计。
- 前端管理端：在 `apps/admin-web` 中新增认定部页面和路由，使用 Ant Design Pro、TanStack Query、Zustand。

### 3.2 新增能力边界

- 新增认定部业务域 `certification`，不混入 `trainingdepartment`。
- 新增轻量流程状态与审批记录模型。短期在 `platform-api` 内实现；后续可迁移或对接 Flowable。
- 新增资料项模板、检查清单模板、归档目录模板，用于驱动页面和校验规则。
- 新增任务维度数据看板聚合接口。

## 5. 完整业务流程

### 5.1 总流程

```mermaid
flowchart LR
    A["认定需求提出"] --> B["需求受理与任务创建"]
    B --> C["任务准备阶段"]
    C --> D["任务准备审批"]
    D -->|通过| E["认定筹备"]
    D -->|驳回| C
    E --> F["认定前准备"]
    F --> G["理论笔试"]
    G --> H["实操考试"]
    H --> I["认定归档"]
    I --> J["归档复核"]
    J -->|通过| K["补贴申领/资料档案/数据沉淀"]
    J -->|驳回| I
```

### 5.2 阶段定义

| 阶段编码 | 阶段名称 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| demand | 需求提出 | 企业或内部录入认定需求 | 需求被接收或关闭 |
| task_prepare | 任务准备 | 需求转任务或手动创建任务 | 五类准备文档提交审批 |
| task_review | 任务准备审批 | 准备文档提交 | 企业审核和内部审核均通过 |
| preparation | 认定筹备 | 任务准备审批通过 | 学员名单、10 项资料、申报材料、考场/考评员基础配置完成 |
| pre_exam | 认定前 | 筹备完成 | 考试材料、设备、考务人员三类清单完成 |
| theory_exam | 理论笔试 | 认定前完成 | 理论检查清单、成绩备份、合格情况反馈完成 |
| practical_exam | 实操考试 | 理论阶段完成或业务允许并行 | 实操检查清单、评分记录、结果反馈完成 |
| archive | 认定归档 | 理论和实操完成 | 归档文件齐全并执行归档 |
| archive_review | 归档复核 | 提交归档 | 复核通过 |
| closed | 闭环完成 | 归档复核通过 | 可进入补贴申领和档案查询 |

### 5.3 状态规则

任务状态包括：草稿、进行中、待审核、已驳回、已通过、待归档、归档复核中、已闭环、已取消。

业务对象通用状态包括：草稿、已提交、审核中、已通过、已驳回、待补充、已归档。

阶段推进必须由后端校验：

- 未完成任务准备审批，不允许进入认定筹备。
- 学员名单为空，不允许进入资料导入。
- 资料导入未达到必需项完整性要求，不允许生成申报材料。
- 认定前材料、设备、人员清单未完成，不允许提交认定前阶段完成。
- 理论检查清单未提交，不允许标记理论笔试完成。
- 实操检查清单 20 项未全部处理或必传附件缺失，不允许提交实操完成。
- 归档 6 项必需文件未齐，不允许执行归档。
- 未执行归档，不允许提交归档复核。

## 7. 核心业务模块需求

### 7.1 认定需求管理

用于采集企业或内部发起的认定需求。

字段要求：

- 需求编号、需求来源、企业名称、联系人、联系电话。
- 工种/职业、认定等级、计划认定人数、期望考试月份。
- 需求说明、附件、当前状态、创建人、创建时间。

功能要求：

- 新建、编辑、关闭需求。
- 需求转任务，一条需求只能生成一个有效任务。
- 需求转任务后保留来源关联。
- 需求关闭需填写原因。

### 7.2 认定任务管理

任务是认定部全流程的主对象。

字段要求：

- 任务编号、任务名称、任务来源、关联需求。
- 工种、等级、计划人数、实际人数、考试日期、任务负责人。
- 当前阶段、任务状态、进度百分比、风险等级。
- 备注、创建人、更新时间、租户信息。

功能要求：

- 支持任务列表、筛选、搜索、按阶段和状态统计。
- 支持手动创建任务和需求转任务。
- 支持进入任务工作台和流程总览。
- 支持取消任务，取消后不可继续推进，但保留已产生数据。

### 7.3 任务准备五表

包括任务策划任务书、任务成员表、任务 WBS、进度计划、风险登记册。

共同要求：

- 每类表单支持查看、编辑、保存草稿、提交审核。
- 支持文件附件和结构化字段并存。
- 支持版本记录，审核通过后再次修改需形成新版本。
- 五表全部提交后可发起任务准备阶段审批。

审批要求：

- 企业审核和内部审核可串行或并行配置。
- 驳回必须填写意见，驳回后回到可编辑状态。
- 通过后锁定本版本，可在后续阶段查看。

### 7.4 认定筹备

包含学员导入、资料导入、申报材料生成、考场配置、考评员配置。

学员导入要求：

- 支持从已培训学员、认定考生或 Excel 导入。
- 按证件号、手机号、任务 ID 去重。
- 记录导入批次、来源、成功数、失败数和失败原因。
- 学员列表需脱敏展示身份证号。

考生资料要求：

- 每名考生维护 10 项资料，资料项可配置是否必需。
- 每项资料支持上传文件、状态、备注、审核结果。
- 任务层面统计资料完整率。
- 资料不完整时标记风险项并阻断后续关键提交。

申报材料要求：

- 可基于任务、学员和资料生成申报材料包。
- 生成结果作为文件记录保存。
- 重新生成需形成新版本，不覆盖历史。

考场和考评员配置要求：

- 考场支持容量、地址、联系人、设备条件和状态。
- 考评员支持基础信息、证件、工种/等级资质、任务分配。
- 同一任务下考评员分配应记录角色和有效状态。

### 7.5 认定前准备

包含考试材料、考试设备、考务人员三类清单。

考试材料清单：

- 材料名称、数量、责任人、准备状态、附件、备注。
- 支持批量初始化模板项。
- 必需材料未完成时不允许认定前阶段完成。

考试设备清单：

- 设备名称、型号、数量、场地、状态、检查人、附件、备注。
- 支持设备异常登记。

考务人员清单：

- 人员类别：考评员、督导员、监考员、考务人员。
- 字段：姓名、证件号、电话、单位、职责、备注。
- 每类人员至少满足配置规则后才能完成。

### 7.6 理论笔试

功能要求：

- 展示报名人数、实考人数、合格人数、通过率。
- 管理理论现场工作检查清单。
- 上传成绩花名册备份。
- 填写合格情况反馈表。

理论现场检查要求：

- 支持 H5/App 端填写和后台查看/修改。
- 清单项按模板初始化。
- 支持检查日期、考场、检查人、备注。
- 全部必检项完成后才允许提交。
- 提交后同步到后台理论考试页面。

### 7.7 实操考试

功能要求：

- 展示报名人数、实考人数、合格人数、通过率。
- 管理实操现场 20 项检查清单。
- 上传考试过程和评分记录。
- 填写考试结果反馈。
- 支持考评员提交材料，组长或管理员复核。

实操检查强规则：

- 20 项检查必须全部处理。
- 第 1-6 项必须上传现场图片附件。
- 未满足附件要求时，保存草稿和提交均需阻断。
- 提交后后台可查看，管理员修改需留痕。

### 7.8 认定归档

归档文件要求：

| 编码 | 文件名称 | 是否必需 |
| --- | --- | --- |
| f1 | 考试试卷 | 是 |
| f2 | 学员理论答题卡 | 是 |
| f3 | 学员实操答题试卷 | 是 |
| f4 | 实操成绩汇总及评分表 | 是 |
| f5 | 考试报名资料与考场组织检查记录 | 是 |
| f6 | 成绩花名册备份记录 | 是 |

功能要求：

- 每项文件支持上传、重传、版本记录。
- 6 项文件未齐，不允许执行归档。
- 执行归档后生成归档批次、归档目录和归档时间。
- 未执行归档，不允许提交归档复核。
- 归档复核通过后任务进入已闭环。

### 7.9 资料档案

档案不是单独录入的数据，而是任务全流程沉淀后的可查询结果。

档案范围：

- 任务档案：任务基本信息、阶段进度、审批记录、所有资料和文件。
- 考生资料档案：考生基础信息、10 项资料、考试结果、归档文件。
- 考场资料档案：考场配置、考场检查、关联任务。
- 考试材料档案：材料清单、试卷、答题卡、成绩文件。
- 考评员资料档案：考评员信息、任务授权、评分/提交材料。
- 考试设备档案：设备清单、检查记录、异常记录。

要求：

- 所有敏感字段按权限脱敏。
- 文件下载需鉴权。
- 档案查询支持按任务、工种、等级、时间、状态筛选。

### 7.10 补贴申领

触发条件：

- 任务已闭环。
- 归档复核已通过。
- 补贴所需材料齐全。

功能要求：

- 发起补贴申领。
- 上传补贴申请材料。
- 记录申领金额、申领人数、提交人、审核状态。
- 支持审批通过、驳回、补充材料。
- 与任务和归档文件关联。

### 7.11 数据面板

指标范围：

- 任务总数、进行中任务、待审核任务、已闭环任务。
- 各阶段完成率和平均停留时长。
- 学员资料完整率。
- 理论/实操检查清单完成率。
- 归档完成率、归档复核通过率。
- 补贴申领数量和金额。
- 风险任务数量、逾期任务数量。

要求：

- 指标以后端聚合为准。
- 支持按时间、工种、等级、负责人、任务状态筛选。
- 空数据展示空态，不使用假数据。

## 8. 文件与资料模型

### 8.1 统一文件关联表

建议新增 `certification_file_ref`，统一承载业务文件关系。

核心字段：

| 字段 | 说明 |
| --- | --- |
| id | 主键 |
| tenant_id | 租户 |
| task_id | 认定任务 |
| owner_type | 归属对象类型，如 task、candidate、checklist、archive、subsidy |
| owner_id | 归属对象 ID |
| file_id | 文件服务 ID |
| file_category | 文件大类，如 candidate_doc、exam_material、archive_file |
| file_item_code | 资料项编码，如 doc01、f1 |
| version_no | 文件版本 |
| required | 是否必需 |
| status | 草稿、已提交、已通过、已驳回、已归档 |
| uploaded_by | 上传人 |
| uploaded_at | 上传时间 |
| review_status | 审核状态 |
| review_comment | 审核意见 |

### 8.2 文件版本规则

- 同一 `owner_type + owner_id + file_item_code` 可以有多个版本。
- 默认读取最新有效版本。
- 审核通过或已归档版本不可覆盖，只能新增版本。
- 删除为逻辑删除，并记录审计日志。

## 9. 审批与流程模型

### 9.1 流程实例表

建议新增 `certification_workflow_instance`。

字段包括：业务类型、业务 ID、任务 ID、流程类型、当前节点、状态、发起人、发起时间、完成时间。

流程类型至少包括：

- task_prepare_review：任务准备审批。
- material_review：资料审核。
- theory_check_review：理论检查复核。
- practical_check_review：实操检查复核。
- archive_review：归档复核。
- subsidy_review：补贴审核。

### 9.2 审批记录表

建议新增 `certification_approval_record`。

字段包括：流程实例 ID、节点编码、节点名称、审批人、审批动作、审批意见、审批前状态、审批后状态、审批时间。

审批动作包括：提交、通过、驳回、撤回、转交、补充材料、复核通过、复核驳回。

### 9.3 审批规则

- 提交动作必须校验业务完整性。
- 驳回必须填写意见。
- 审批通过后业务状态和阶段状态同步更新。
- 审批记录不可物理删除。
- 后端接口必须校验审批权限。

## 13. 非功能需求

### 13.1 安全

- 身份证、手机号、证件号默认脱敏展示。
- 文件下载和预览必须鉴权。
- H5 现场页面必须校验登录或一次性任务授权。
- 所有写接口必须记录操作人。
- 后端必须校验租户隔离和数据归属。

### 13.2 性能

- 任务列表支持分页，默认每页 20 条。
- 考生资料列表需支持 1000 人以内可用，超过后分页和异步导入。
- 看板指标应由后端聚合，避免前端拉取全量明细计算。
- 文件上传需限制大小和类型：图片不超过 10MB，文档不超过 50MB。

### 13.3 可用性

- 所有阻断必须给出中文原因。
- 关键动作需二次确认：删除、提交审批、通过、驳回、执行归档、提交归档。
- 上传、提交、审核按钮需防重复点击。
- 页面刷新后状态应从后端恢复。

### 13.4 可维护性

- 清单项、资料项、归档项使用模板表驱动，避免写死在前端。
- 阶段推进规则集中在后端服务层，避免分散在多个 Controller。
- 文件关联统一走 `certification_file_ref`。
- 审批记录统一走审批服务，不在业务表中只放一个状态字段了事。

## 14. 验收标准

### 14.1 主链路验收

1. 可以新建认定需求并转为认定任务。
2. 可以完成任务准备五表维护并提交审批。
3. 审核人可以通过或驳回任务准备审批，驳回意见可回溯。
4. 审批通过后可以进入认定筹备。
5. 可以导入学员，维护每名学员 10 项资料并统计完整率。
6. 可以生成申报材料并形成文件版本。
7. 可以完成考场、考评员、考试材料、考试设备、考务人员配置。
8. 可以提交理论检查清单、上传成绩备份、填写合格反馈。
9. 可以提交实操 20 项检查清单，且 1-6 项未上传图片时被阻断。
10. 可以上传 6 项归档文件，执行归档并提交复核。
11. 归档复核通过后任务进入已闭环。
12. 已闭环任务可以在资料档案中完整查询。
13. 已闭环任务可以发起补贴申领。
14. 数据面板指标与任务实际数据一致。

### 14.2 文件验收

1. 每个上传文件都能查询到业务归属、上传人、上传时间和文件用途。
2. 重传文件不会覆盖已审核或已归档历史版本。
3. 删除文件只解除或逻辑删除业务关联，不破坏审计追溯。
4. 无权限用户无法下载非本租户或非授权任务文件。

### 14.3 审批验收

1. 每个提交动作产生流程实例或审批记录。
2. 每个通过、驳回、复核动作记录审批人、意见、时间和状态变化。
3. 驳回后业务对象回到可编辑状态。
4. 审批通过后的版本被锁定。

### 14.4 权限验收

1. 认定部管理员可以查看全部认定任务。
2. 任务负责人只能维护被授权任务。
3. 考评员只能查看和提交被分配的任务材料。
4. 企业联系人只能查看本企业相关需求和审核结果。
5. 后端接口权限校验与前端菜单隐藏一致。

## 15. 实施分批建议

虽然需求按完整落地设计，开发可按依赖关系分批：

第一批：数据模型、任务管理、文件关联、审批基础、任务准备五表。  
第二批：认定筹备、学员导入、资料导入、申报材料、考场和考评员配置。  
第三批：认定前、理论考试、实操考试、现场 H5。  
第四批：归档、资料档案、补贴申领、数据面板。  
第五批：流程引擎增强、批量导入优化、移动端体验和报表增强。

分批实施不得改变本文档定义的主对象、状态和文件/审批模型。

## 16. 风险与约束

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 原型使用 localStorage，正式系统需后端持久化 | 状态规则可能散落 | 以后端状态机重建流程 |
| 认定资料类型多且文件多 | 文件追踪混乱 | 统一文件关联表和资料模板 |
| 审批流前期未接 Flowable | 后续迁移成本 | 先建立流程实例和审批记录抽象 |
| 现场 H5 需要移动端体验 | 管理端页面不适合现场填写 | 单独建设现场任务和清单页面 |
| 培训部已有相似数据 | 可能重复建设 | 只在必要处引用培训数据，不混表 |

## 17. 需求结论

认定部模块应建设为围绕“认定任务”的完整业务域，而不是一组孤立页面。最终落地时，系统必须同时具备四条能力：

1. 流程能力：任务从需求到闭环的阶段推进和审批留痕。
2. 文件能力：多类型资料可上传、审核、版本化、归档和追溯。
3. 数据能力：人员、考场、设备、材料、考试结果和补贴结构化存储。
4. 运营能力：任务档案、资料档案、数据看板和风险监控可查询可统计。

按此设计实施后，认定部可以从线下 Excel、纸质材料和人工沟通，升级为可追踪、可审批、可归档、可统计的线上业务闭环。
