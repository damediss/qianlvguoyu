# 企业确认与回传材料「可后补」解耦方案

> 文档版本：v1.0  
> 编写日期：2026-07-15  
> 关联基线：`三年规划企业审核名单回传与排班表上传方案.md`（v1.0，确认时强制齐套）  
> 变更动机：企业希望 **确认方案不依赖回传齐套**；未传名单/排班表时，在 **已确认（status=4）详情可补交**

---

## 一、需求澄清

### 1.1 目标行为

| 场景 | 期望 |
|------|------|
| status=3 待企业审核 | 可上传名单/排班表（可选、可分次）；**随时可点「确认方案」**，不要求两文件齐套 |
| 确认后 status=4 | 若名单或排班表缺失（或尚未齐套），企业在 **已确认详情** 仍可 **补交/覆盖上传** |
| 机构侧 | 持续可见回传齐套状态；缺失时有醒目提示；可下载已有文件 |
| 驳回 | 仍可不依赖回传；规则与基线一致 |

### 1.2 与现行实现差异

| 现行（基线已落地） | 本方案 |
|--------------------|--------|
| `company-confirm` 校验两文件非空，否则 400 | **去掉**确认时齐套强校验 |
| 企业详情：确认按钮 `disabled=!enterpriseReturnReady` | 确认按钮 **始终可点**（status=3） |
| status=4：回传只读、禁止上传 | status=4：**允许补交**（见权限规则） |
| Tag「已齐套」才可确认 | Tag 仅表示材料完备度，与是否已确认解耦 |

### 1.3 明确不做（本期）

- 不新增状态码（仍用 3→4）  
- 不把「补交」拆成机构二次验收态（若以后要机构再验收，另开需求）  
- 不解析 Excel 入库（附件语义不变）  
- 不强制「确认后必须 N 天内补齐」（可选后期加催办）

## 二、推荐流程（状态机）

```
机构提交 ──► status=3 待企业审核
                │
     ┌──────────┼──────────┐
     ▼          ▼          ▼
  下载材料   上传名单   上传排班表   （均可选、可多次）
     │          │          │
     └──────────┼──────────┘
                ▼
        企业确认（无文件门槛）──► status=4
                │
                ▼
     status=4 详情：未齐套则可「补交」名单/排班表
     （建议：齐套后仍允许企业覆盖一次或多次，见决策项）

企业驳回 ──► status=5（不依赖回传）
机构重提 5→3：清空「当前回传指针」，历史保留（沿用基线）
```

### 2.1 业务语义拆分

引入两个正交概念（UI/接口共用字段即可，不必加状态码）：

1. **审核结论**：`status`（3 待审 / 4 已确认 / 5 已驳回）  
2. **回传完备度**：`enterpriseReturnReady = rosterId != null && shiftId != null`

列表与详情用 Tag 表达完备度，例如：

| status | ready | 展示建议 |
|--------|-------|----------|
| 3 | false | 待审核 · 材料未齐 |
| 3 | true | 待审核 · 材料已齐 |
| 4 | false | 已确认 · **待补交**（醒目 warning） |
| 4 | true | 已确认 · 材料已齐 |

## 三、权限与可写窗口

### 3.1 谁可上传 `enterprise-return`

| status | 企业（目标企业账号） | 机构/平台管理员 |
|--------|----------------------|-----------------|
| 3 | ✅ 可传 | ✅ 可代传（与现网 assert 一致时可保留） |
| 4 | ✅ **补交/覆盖**（本方案新增） | ✅ 建议允许代补交（方便运营） |
| 其他 | ❌ | ❌ |

### 3.2 确认后覆盖策略（需产品拍板，推荐默认）

**推荐 A（简单）：** status=4 期间始终允许企业覆盖上传（写 history）。  
- 优点：实现简单，便于改错  
- 风险：机构已按旧文件开班时可能不一致 → UI 提示「覆盖将更新当前回传版本」

**备选 B：** status=4 仅当 `!ready` 时可传；齐套后冻结，改文件需机构驳回重走。  
- 更安全，但你「已确认后补交」一旦传齐就不能再改

**本期建议采用 A**，与「可随时补交」心智一致；下游分班读「当前指针」即可。

### 3.3 下游门禁（关键）

开班/分班读取回传时：若 `!enterpriseReturnReady`，前端拦截并文案：「企业尚未补交筛选名单/排班表，请先补交」。  
**不堵死 status=4 的确认动作**，只堵依赖回传的下游动作。

## 四、后端改造（相对现网 diff）

数据模型、下载接口、history **保持不变**，改行为即可。

### 4.1 `company-confirm`

- **删除**「两文件齐全」校验块  
- 其余：status=3 → 4、写确认人/时间，不变  
- 可选：确认时若未齐套，在日志或 history 记一条 `confirmedWithoutReturn: true`（非必须）

### 4.2 `enterprise-return`

现逻辑：`assertEnterpriseCanConfirm` → 要求 **status==3**。  

改为例如 `assertEnterpriseCanUploadReturn`：

```text
assertAccessible(plan)
if status ∉ {3, 4}:
  throw BAD_REQUEST("仅待企业审核或已确认状态可上传/补交回传材料")
if enterpriseViewer:
  校验 targetOrgId 匹配
else:
  requireOrgOperator / 平台管理员（与现网一致）
文件后缀、分次上传、写指针 + history：不变
```

### 4.3 VO

继续返回 `enterpriseReturnReady`。  
可选新增（便于前端文案，非必须）：

- `enterpriseReturnSupplementAllowed`：`status∈{3,4}`（或再加 `status==4 && !ready` 若选策略 B）

## 五、前端改造

### 5.1 `EnterprisePlanReviewPanel`（企业审核）

**status=3（待审核）**

1. 「企业回传」区块保留：上传、预览、下载  
2. 「确认方案」：**去掉** `disabled=!ready`；可点  
3. 确认前若未齐套：用 `Modal.confirm` 二次确认：  
   > 尚未上传完整的筛选名单/排班表，确认后可在「已确认」详情中补交。是否继续？  
4. 列表「回传」列继续展示完备度（与能否确认无关）

**status=4（已确认详情）**

1. 仍进入详情（「已确认」Tab / 全部记录）  
2. 回传区块：标题改为 **「回传材料（可补交）」**  
3. `!ready` 时顶部 `Alert` warning：请尽快补交名单与排班表  
4. Upload 按钮在 status=4 **显示**（与 3 相同交互）  
5. 无确认/驳回按钮（已确认）

### 5.2 `SolutionPlanningPage`（机构）

- status=4 且 `!ready`：Tag **「已确认待补交」** + 详情 Alert  
- 下载菜单：有文件则可下；缺的显示「未补交」  
- 若允许机构代传：详情也可暴露上传入口（可选，建议做，减少企业不会用系统时的阻塞）

### 5.3 文案统一

- 待审：鼓励先传再确认，但不强制  
- 已确认未齐：强调「请补交，否则无法进入分班/排课」

## 七、验收用例

1. status=3，**不上传任何回传** → 可确认 → status=4，Tag 为「已确认 · 待补交」  
2. status=3，只传名单 → 可确认 → 已确认详情仍缺排班表，可补排班表 → ready=true  
3. status=3，两份都传齐 → 可确认 → status=4，可下载两份  
4. status=4 补交后机构可下载最新文件；history 有追加记录  
5. status=5/2 等：不可补交  
6. 确认接口不再因缺文件返回 400

## 八、决策项（实施前请确认）

1. **确认后齐套还能否覆盖？** 推荐 **可以覆盖（策略 A）**。  
2. **机构能否在已确认代企业补交？** 推荐 **允许**。  
3. **未齐套点确认是否弹二次确认？** 推荐 **是**。  
4. **下游分班是否强依赖 ready？** 推荐 **是（前端门禁）**，与确认解耦。  

---

## 九、结论

- **核心改动**：确认与回传完备度解耦——`3→4` 无文件门槛；`enterprise-return` 在 **3 与 4** 均可写。  
- **体验**：待审可先确认后补；已确认详情承担补交入口；列表用「待补交」提醒。  
- **风险可控**：附件 + history 足够追溯；下游用 `enterpriseReturnReady` 门禁即可。  

确认本节决策项后，可按第六节直接改代码（改动面小，属对基线的行为修正）。
