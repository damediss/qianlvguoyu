## 1. 结论速览

方案批准后发生的方案外改动共 **16 项**，归为四类：

| 类别 | 项数 | 占比 | 性质 |
|---|---|---|---|
| A. 方案设计盲区（应写未写，**可预防**） | 5 | ~31% | 自动补跑、失败原因不可归类、答案分布误入 prompt、X/Y/Z 死字段、UX 验收缺失 |
| B. 实施与验证过程坑（**流程问题**） | 4 | ~25% | 验证管道吞错（假"全绿"）、DTO 命名不对称、测试无持久化语义、时序测试构造反复 |
| C. 真实运行才能暴露（E2E 的价值） | 3 | ~19% | 熔断收尾竞态、错误响应体被丢弃、分布偏差实证 |
| D. 用户使用后提出的合理新需求（**正常迭代**） | 4 | ~25% | 导入进度条、导入时间列+分页、草稿选项展示+难度中文、分页选择失效修复 |

**三条核心洞察**：

1. **最大的单项返工不是 bug，而是"生命周期设计缺失"**——方案只设计了"批次如何生成"，没设计"部分失败的批次算什么状态、后续还能不能继续"。自动补跑整个功能（多轮编排+退避+人工兜底）都是这个缺口的补丁。
2. **第二个大返工是"把确定性规则放进了 prompt"**——"答案字母随机分布"靠 prompt 禁令注定失效（LLM 位置偏差），实测 D 选项仅 3%。设计期就应识别"分布/格式/顺序 = 确定性规则 → 后端保证"，这是 LLM 工程的特有设计检查项。
3. **真实试产放得太晚**——熔断竞态、错误体盲点、分布偏差全部要靠真实运行暴露，但方案把 E2E 放在全部开发完成之后。若在 P0 修正后立即跑一个 10 点小批次，这三个问题会在开发中期暴露，返工成本减半。

## 3. 根因分析

### 3.1 设计盲区（方案应写未写）

**A8 生命周期状态机缺失（影响最大）**。方案定义了 pending/running/paused/done/failed 五态，但没有回答三个关键问题：
- 跑完一轮后仍有失败点，批次该是什么状态？（现实现：done——语义错误，用户理解为"全部完成"）
- 用户面对 144/200 能做什么？（答案曾是：什么都不能做）
- "重试失败块"为什么只限 FAILED 状态？

教训：**为每个实体画全生命周期图，逐个状态问"此状态下用户/系统能执行哪些动作、失败了向哪迁移"**。部分完成是异步批处理系统的常态，不是异常。

**A5 可观测性只做了一半**。方案 P2 把 usage 落库写得很细，但失败原因只在日志——E2E 后 45 个失败无法归类，等意识到要看错误类型时才发现错误响应体早在 HTTP 层被丢弃。教训：**可观测性设计要覆盖"成功指标 + 失败指标 + 上下文透传"三类**；凡是"只在日志里"的信息，都应假设排障时不可用。

**A6 确定性规则误入 prompt**。"答案字母随机分布"是概率分布要求，LLM 无法可靠满足（实测 D 仅 3%），而它恰恰是后端 20 行代码能绝对保证的事。教训见 §4 LLM 工程专项。

**A2 外部依赖核实滞后**。v0.1 凭经验假设了 GLM 缓存行为、字段口径；model_id 大小写错误甚至已经写进了已应用的种子迁移。v0.2 核实后一切都要打补丁。教训：**外部 API 的字段口径/错误码/计费/限制，必须在写方案第一版之前核对官方文档**，核实结论直接写进方案正文。

### 3.2 LLM 工程特有设计缺失

设计 LLM 生成链路时，应对每一句 prompt 要求问一遍：

| 问句 | 若答"否"的对策 |
|---|---|
| 模型能做到吗？（分布均匀、百分比配比、绝对不出现某格式） | 做不到的 → 后端确定性实现/校验兜底 |
| 模型知道吗？（引用的文档、字段含义、编码约定） | 不知道的 → 内容内联进 prompt，或明确告知含义 |
| 校验器能兜住吗？（每条输出要求是否有对应校验规则） | 兜不住的 → 要么补校验器，要么接受概率性产出 |
| 示例给够了吗？（格式一致性靠 few-shot 而非形容词） | 在稳定前缀里给示例，缓存命中后成本极低 |
| 模型答错的代价与检出方式？ | 每个 prompt 约束都要有对应的检出/度量手段（否则写没写一样） |

本次案例：规则 5（分布）→ 模型做不到 → 洗牌；X/Y/Z 字段 → 模型不知道 → 注入含义；规则 6 的 20% 约束 → 6 题粒度数学上不可执行 → 改块内口径；解析质量 → 无度量 → 补 few-shot + 校验留痕。

### 3.3 测试与验证流程缺陷

- **验证管道吞错（最危险）**：`mvn test | grep "Tests run\|FAILURE"` 把编译失败的信号完全滤掉（`[ERROR] COMPILATION ERROR` 不含 FAILURE 字样），且管道后 `$?` 取的是 grep 的退出码——造成"洗牌器测试全绿"的假阳性，实际编译都没过。教训：**验证必须检查真实退出码**（落盘日志 + `echo $?` 直查，或 `set -o pipefail`）；编译失败在 -q 模式下的特征行是 `[ERROR] COMPILATION ERROR`，用 grep 过滤时必须覆盖。
- **mock 无写后读语义**：多轮补跑测试中，mock 的 insert 不影响 selectList 的返回，导致"每轮重查缺口点"在生产正确、在测试里无限重复派发。教训：**测试基建必须模拟持久化语义**（写后读一致），否则任何"根据库内状态决定行为"的代码都无法被有效测试。
- **DTO 命名不对称**：`getOptionList()` / `setOptions()`。凭 getter 惯性写 setter 必错。教训：**写调用前先看目标类的完整成员清单**（当初只 grep 了片段）；此类不对称命名本身就是团队的 API 设计债，新 DTO 应避免。

### 3.4 必须由真实运行暴露的问题（E2E 的正面价值）

熔断收尾竞态（在飞成功把实时计数器清零 → 28 点未派发误标 done）本质是"收尾判定依赖可变实时状态"的设计缺陷，单测 N=1 无法构造时序重叠，只有真实 5 路并发跑 200 块才出现。两点沉淀：
- **设计层面（治本）**：状态收尾判定用事件锁存（flag），不读实时计数——这条已固化为代码注释。
- **测试层面**：并发回归测试要构造"时序重叠"而非"功能等价"路径；构造手段是让信号量释放顺序与计数顺序强耦合（1.6 释放严格晚于其计数自增），而非靠 sleep 时长碰运气（本测试迭代了 3 版才确定化）。

### 3.5 合理的需求演进（不算方案缺陷）

导入进度条、导入时间列、真分页、草稿选项展示、难度中文——这些是用户见到真实界面后提出的体验要求，属于正常迭代。但其中"分页选择失效"（pageSize 写死）属于既有实现缺陷，且"进度条/分页/时间列"这类 UX 基线完全可以在方案的前端验收清单里提前约定，避免二次往返。

## 5. 下次方案制定检查清单（核心交付物）

### 5.1 制定前（信息收集）

- [ ] 涉及外部模型/API/第三方服务：**先核对官方文档**（字段名与大小写、错误码表、计费口径、速率限制、超时建议），核实结论写入方案正文而非"实施时核实"
- [ ] 盘点同类既有页面/服务的 UX 与接口模式（进度反馈、分页方式、时间字段、内容展示密度），新功能与其对齐
- [ ] 确认涉及实体的现状数据（存量值、枚举口径、命名），避免方案与库内事实冲突

### 5.2 设计中

- [ ] **画实体生命周期状态机**：每个状态问"用户能做什么、失败了迁去哪、部分完成算什么、还能不能继续"；异步批处理必须设计"部分失败"终态与对应的人工/自动恢复路径
- [ ] **区分确定性规则与概率性能力**：分布/配比/格式/顺序 → 后端确定性实现 + 校验器；LLM 只负责内容生成（LLM 规范 #6）
- [ ] **prompt 逐句自审五问**（§3.2 表格：做得到吗/知道吗/兜得住吗/有示例吗/错得起吗）
- [ ] **可观测性三件套**：成功指标、失败原因（落库而非仅日志）、上下文透传（错误响应体必须进异常消息）
- [ ] 写路径逐条过原子性：多条写入是否需要块级事务；部分落库的后果是什么
- [ ] 长耗时外部调用的超时预算：按"模型档位 + max_tokens + 思考开关"估算，而非沿用全局默认
- [ ] 并发/异步设计：列出**时序场景清单**（重入、暂停恢复、部分失败、在飞完成与状态判定交叉）——这份清单同时是后续测试设计的输入
- [ ] **事务边界与异步投递**：@Transactional 方法内禁止直接投递依赖本次写库的异步任务——写库经 TransactionTemplate 先提交、任务后投递（2026-09-08 生产事故：Worker 抢跑读不到未提交批次，批次永久卡 pending）
- [ ] **"重做/重新生成"作为一等语义设计**：显式定义清理范围（建议物理删除未审定部分）与插入幂等（软删行占用唯一键，同键重插必撞）；触发入口允许重复调用

### 5.3 评审时

- [ ] 用 §5.2 的时序场景清单逐条对照设计是否有对应处理与测试用例
- [ ] 收尾/状态判定是否存在"依赖可变实时状态"的写法（应改事件锁存）
- [ ] 前端验收清单化：进度反馈、列表分页（真实服务端分页 + 每页条数）、时间字段、内容展示完整性、空态与错误态
- [ ] 测试计划包含：持久化语义模拟、并发时序重叠构造、分布类断言的随机源选择

### 5.4 实施与验证

- [ ] **第一期先打通最小真实链路**（tracer bullet）：修正类改动落地后，立即用小批次（≤10 点）真实调用跑通全链路，把外部依赖的坑暴露在开发中期
- [ ] 验证看真实退出码：`mvn ... > log 2>&1; echo $?` + 确认 `BUILD SUCCESS`；禁止 `| grep | head` 后取 `$?`
- [ ] 调用不熟悉的类之前读完整定义（成员与方法全集），警惕 getter/setter 命名不对称
- [ ] 并发测试构造时序重叠：用"信号量释放严格晚于计数自增"这类结构化顺序保证，不靠 sleep 时长碰运气；构造不出来时优先回头改设计（锁存/事件），而不是加长 sleep
- [ ] 分布类断言用单一 Random 流连续采样，不用顺序小种子
- [ ] 新链路产出的第一批真实数据（分布、失败率、耗时）作为基线记录进方案文档

### 7.2 本段核心洞察

1. **"快照 vs 实时"要作为配置生效时机显式设计**：一次外部调用里的多个参数若口径不一（部分随批次固化、部分跟配置表走），用户心智模型是"改配置即生效"，任何例外都要在设计文档里写明，并让全部参数对齐同一口径。
2. **下拉框是 UX 缺陷重灾区**：数据源接错（复用分页查询）、label 不可辨识（id+英文枚举）两类问题在同一页面两次出现。§5.3 前端验收清单增补：「下拉数据源与列表分页解耦；选项 label 含时间与中文语义」。
3. **《指引》类交付规范要前置对标**：导出文件是交给外部（鉴定中心）的交付物，其列集合、代码格式、枚举中文口径应在方案期拿规范原文逐列确认，而不是交付后返工。
4. **max_tokens 预算与超时预算同类**：§5.2 已入清单的"超时按模型档位 + max_tokens + 思考开关估算"同样适用于 max_tokens 本身——思维链与最终回答共享输出预算，估算必须按"思考开"口径放大。

### 8.2 本段核心洞察

1. **"@Transactional 内投递异步任务"是隐藏最深的竞态**：写库与投递同处一个事务，Worker 在提交前抢跑就读不到数据，且失败是静默的（日志一行 ERROR，批次界面永远"等待中"）。测试环境时序侥幸、生产环境必然暴露。修复范式"写库经 TransactionTemplate 先提交、任务后投递"已入 §5.2 清单。
2. **环境故障会伪装成代码故障**：一天内机器 native OOM 先后伪装成"MockMaker 无法初始化""forked VM 消失""编译产物缺失"三类怪象。沉淀诊断顺序：**先看 hs_err 与机器资源、再对时间线、最后才怀疑代码**；`mvn | grep` 管道会吞掉关键证据，完整输出必须落盘。
3. **"重做/重新生成"必须作为一等语义设计**：二次概括的三个坑（软删占唯一键、编号从零重排、计数对不上）全部源于"重新生成"没有显式定义清理范围与幂等性。范式：物理删除未审定部分（腾唯一键）+ 插入端幂等兜底。
4. **外部模型的结构化输出能力要当成能力清单项核对**：response_format 从"仅 DeepSeek"到"GLM 官方支持"只是一次文档核对的距离——按"仅 DeepSeek"写死导致 45 次失败重试的隐性成本。坑 #13 的完整含义是"支持矩阵逐平台核对"，包括结构化输出这类次要能力。
5. **日志取证要区分"检索命中"与"事实"**：固定 system prompt 里的示例让"按内容词 grep"必然命中每笔请求，造成"大量相同请求"的错觉；请求/响应必须分别计数配对。固定 prompt 的体积（含 few-shot 示例）同时是每次调用的固定成本。
