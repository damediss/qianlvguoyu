# 千铝工投云平台与智能体开发部代码与版本管理制度

制度编号：QLGT-YFGL-2026-104　　版本：V1.1　　发布日期：2026-10-16

## 第一章　总则

**第一条**　为规范 Git 分支策略、提交规范、Code Review 与版本制品管理，保障代码质量与可追溯性，特制定本制度。本制度遵循部门制度“简洁、可测试、可维护、持续迭代”的共同标准。

**第二条**　本制度适用于千铝工投云平台与智能体开发部全部代码仓库，包括 SaaS 平台前后端、仿真训练平台、脚本与文档仓库。AI 辅助生成的代码与人工编写代码适用完全相同的准入标准。

## 第二章　分支策略与提交规范

**第三条**　master 分支受保护，禁止直接推送；开发分支按 feat/<任务号>-<简述>、fix/<任务号>-<简述>、docs/<简述> 命名。

**第四条**　提交信息格式为 type(scope): subject，type 取 feat / fix / refactor / test / docs / chore / perf；提交须可编译、可运行，禁止提交“半成品”阻断主干。

**第五条**　合并 master 一律走合并请求（MR），至少 1 人评审通过，且评审人不得为提交人本人；合并前主代码编译 0 错误、前端类型检查 0 错误。

## 第三章　Code Review 流程与准入标准

**第六条**　评审关注点至少包括：安全（SQL 注入、越权、敏感信息泄漏）、多租户数据隔离、事务边界与并发、异常处理、性能隐患。评审意见须逐条答复或修改。

**第七条**　提交人对代码质量负第一责任，无论代码由人编写还是 AI 生成；使用 AI 辅助开发时，提交前必须触发一次针对该次提交的自动化回归测试集（至少包含冒烟测试）。提交人需在本地或沙箱环境执行一次完整的主流程自测（非单元测试，指真实运行）。提交人需对上线后的功能正确性及故障负责。

**第八条**　评审通过的最低标准：编译通过、自测通过、无红线项（明文密钥、假删写法、绕过权限的直连等）。发现红线项一律打回。

## 第四章　版本号与制品管理

**第九条**　版本号采用语义化版本（主版本.次版本.修订号）；发布版本在仓库打标签，标签与部署制品一一对应。

**第十条**　构建制品（后端 JAR、前端 dist、私有化安装包）按版本归档，保留最近 3 个发布版本，支撑 YW-05 的回退要求。

## 第五章　代码仓库权限与保密要求

**第十一条**　仓库权限按项目最小授权，成员变动随 YW-03 的复核与回收流程同步调整。

**第十二条**　禁止提交：真实密钥与密码、生产数据、客户敏感信息、大型二进制素材与临时文件。发现敏感信息入库的，当日轮换相关凭证并清理历史。

**第十三条**　源码为公司核心数字资产，禁止拷贝至个人设备或外传；外协人员按项目开通限时只读或指定仓库权限。git 提交身份实行白名单管理：部门 8 个署名映射（姓名 + 邮箱）须登记在册，提交须使用白名单内的 name+email 组合；人效统计按 name+email 归集，防止同一人多署名导致统计失真，非白名单身份的提交不予计入人效并须整改。

## 第六章　附则

**第十四条**　本制度由千铝工投云平台与智能体开发部负责解释。

**第十五条**　本制度自发布之日起施行。
