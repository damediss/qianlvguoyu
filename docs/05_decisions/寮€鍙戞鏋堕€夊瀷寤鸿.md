# 开发框架选型建议

版本：V0.1 草稿  
日期：2026 年 5 月 1 日  
用途：配合《云平台技术路线选型建议》，进一步明确项目开工时采用的具体开发框架、工程结构和默认实现方式。

## 一、总体结论

当前项目建议采用“Java 核心业务主服务 + React 管理端 + 可控服务化 + 独立 AI / MCP 适配层 + 流程引擎 + n8n 自动化”的框架组合。

默认框架组合：

**Spring Boot + MyBatis-Plus + Spring Security + React / Vite / TypeScript + Ant Design + ProComponents + TanStack Query + Flowable + n8n + Spring AI / MCP + Docker。**

选型原则：

1. 一期采用可控服务化起步，建立清晰服务边界，但不做全量微服务拆分。
2. 核心业务集中在 `platform-api`，AI、MCP、文件、通知、工作流等边界清晰能力优先独立服务化。
3. 前端采用正式工程，不继续在 HTML 原型上堆功能。
4. AI 和 MCP 不直接操作数据库，只通过受控业务 API 和工具接口访问平台能力。
5. 工作流分层：核心业务流程进入 Flowable，外部自动化交给 n8n。

## 二、框架选型总表

| 层级 | 默认框架 | 说明 |
| --- | --- | --- |
| 后端基础 | Spring Boot 3.x | Java 主业务平台，承载培训、竞赛、认定、课程、题库、证书、补贴、权限、审计 |
| Java 版本 | OpenJDK 21 LTS | 一期默认，后续预留升级空间 |
| 构建工具 | Maven | 国内 Java 团队协作成本低，适合多模块管理 |
| 数据访问 | MyBatis-Plus | 适合后台管理系统、复杂查询、表格筛选和国产 Java 生态 |
| 数据迁移 | Flyway | 管理数据库版本，避免手工改库不可追溯 |
| API 文档 | springdoc-openapi；Knife4j 可选 | OpenAPI 作为接口规范，Knife4j 可用于更友好的中文调试界面 |
| 权限认证 | Spring Security + JWT | 一期自研账号体系；后续需要 SSO 时再评估 Keycloak / Spring Authorization Server |
| 参数校验 | Jakarta Validation / Hibernate Validator | 统一接口入参校验 |
| 对象转换 | MapStruct | DTO、VO、Entity 转换，减少手写样板代码 |
| 工作流 | Flowable | 与 Java / Spring Boot 集成更直接，适合审批、认定、补贴、归档流程 |
| 定时任务 | Quartz | 平台内定时任务；跨系统自动化交给 n8n |
| 缓存 | Redis + Spring Cache，生产优先云托管 Redis | 会话、验证码、热点配置、字典缓存、任务状态、限流 |
| 文件存储 | Cloud OSS Adapter | 统一封装文件接口，生产环境优先接阿里云 OSS 或腾讯云 COS |
| 管理端前端 | React + Vite + TypeScript | 正式 PC 管理后台 |
| UI 组件 | Ant Design + ProComponents | 表单、表格、筛选、详情页、后台布局 |
| 路由 | React Router | 明确、轻量，适合自研后台 |
| 服务端状态 | TanStack Query | 管理接口请求、缓存、刷新和变更 |
| 本地状态 | Zustand | 管理菜单、用户偏好、局部 UI 状态 |
| 图表 | ECharts | 数据面板、驾驶舱、流程健康度 |
| 前端测试 | Vitest + React Testing Library + Playwright | 单元、组件、端到端测试 |
| AI 集成 | Spring AI 或 Node / TypeScript AI Gateway | 独立 AI Gateway 作为 AI 能力入口，负责模型调用、Prompt 编排、草稿生成和材料检查 |
| MCP Server | TypeScript MCP SDK | 一期作为 AI 调用业务系统的轻量适配层，不直连数据库 |
| 自动化 | n8n | 通知、定时、外部接口同步、AI 草稿生成 |
| 部署 | Linux Docker Engine / Docker Compose 起步 | 先保证测试、演示和生产可部署；二期再上 Kubernetes / containerd |

## 三、后端框架落地方式

一期后端采用可控服务化，核心业务主服务放在：

```text
services/platform-api/
```

`platform-api` 是核心业务主服务，内部按业务域拆包，承载统一账号、租户、权限、课程、题库、考试、学习记录、成绩、错题等主流程：

```text
services/platform-api/
  src/main/java/
    com/guoyu/platform/
      PlatformApplication.java
      common/
      config/
      security/
      tenant/
      system/
      file/
      workflow/
      course/
      question/
      exam/
      training/
      competition/
      certification/
      certificate/
      subsidy/
      project/
      report/
      ai/
      integration/
```

一期服务边界：

| 服务 | 目录 | 职责 |
| --- | --- | --- |
| 核心业务主服务 | `services/platform-api/` | 账号权限、租户组织、课程、题库、考试、学习记录、成绩、错题、统一审计和核心业务 API |
| AI Gateway | `services/ai-gateway/` | 模型调用、Prompt 编排、课程大纲草稿生成、材料检查、AI 任务记录 |
| MCP Server | `services/mcp-server/` | 给 AI 暴露受控工具，只调用平台 API，不直连数据库 |
| 文件服务 | `services/file-service/` | 文件元数据、上传、下载、预签名 URL、删除、OSS/COS 适配；一期如进度紧可先作为 `platform-api` 内部模块 |
| 工作流服务 | `services/workflow-service/` | 流程定义、审批任务、流程记录；一期可先集成 Flowable 到 `platform-api`，但接口和数据边界按独立服务设计 |

不一开始拆出 `course-service`、`exam-service`、`tenant-service`、`user-service` 这类细业务服务，避免用户、租户、权限、文件和审计规则在多个服务中重复实现。

默认分层：

| 层 | 命名 | 说明 |
| --- | --- | --- |
| Controller | `*Controller` | REST API，只做参数接收、权限校验入口和结果返回 |
| Application | `*ApplicationService` | 业务用例编排、事务边界、跨领域协调 |
| Domain | `*DomainService` / 领域对象 | 核心业务规则 |
| Repository | `*Repository` / `*Mapper` | 数据访问接口和 MyBatis-Plus 数据访问 |
| Entity | `*Entity` | 数据库表映射 |
| DTO | `*CreateReq`、`*UpdateReq`、`*QueryReq` | 请求对象 |
| VO | `*VO`、`*DetailVO` | 返回对象 |
| Converter | `*Converter` | MapStruct 转换 |

后端默认规则：

1. Controller 不直接写 SQL。
2. Entity 不直接暴露给前端。
3. 所有列表接口统一分页结构。
4. 所有写操作记录操作日志。
5. 涉及企业、项目、用户的数据必须带租户和数据权限过滤。
6. 文件上传只返回文件 ID、文件名、大小、类型和访问策略，不把文件内容存数据库。
7. AI / MCP 工具调用必须走受控业务 API 或 Application 层能力，不允许绕过业务权限直接访问 Mapper。
8. 后台、学员端、手机 H5、AI、工作流可以有不同 Controller 或服务入口，但不能复制业务规则。

### 3.1 性能与资源控制原则

平台性能架构采用“轻核心、异步化、缓存化、对象存储直连、AI 独立隔离、服务可水平扩展”的设计原则。

核心规则：

1. 核心业务服务保持轻量和无状态，不把登录状态、临时任务状态和大对象保存在本机内存。
2. 慢任务全部异步化，包括 AI 生成、文件解析、批量导入、报表生成、通知发送、材料检查和 n8n 自动化。
3. 热点数据通过 Redis 加速，包括 token、菜单权限、字典、验证码、限流计数和任务状态。
4. Redis 只做缓存和基础设施状态，不作为业务主数据库。
5. 大文件不进入核心业务服务内存，优先通过文件服务和 OSS/COS 处理；后续文件变大后改为预签名 URL 直传。
6. AI Gateway 独立运行，AI 调用失败或超时不能拖垮登录、课程、考试、成绩等核心主流程。
7. 后台列表必须分页，禁止无条件全表查询；常用查询字段必须设计索引。
8. 首页、工作台、学员首页使用后端聚合接口，减少前端多次请求。
9. 前端路由和大模块按需加载，大表格分页渲染，避免一次加载全部页面和数据。
10. 一期使用 Docker Compose 管理少量关键服务，不引入全量微服务治理组件，降低资源占用和运维复杂度。

## 四、数据库与数据访问

一期数据库统一使用 MySQL。

默认选择：

1. MyBatis-Plus 负责 CRUD、分页、条件构造。
2. 复杂报表和统计可以写 MySQL SQL / XML SQL，但必须放在对应业务 Mapper 下。
3. Flyway 管理数据库迁移脚本。
4. 多租户字段统一使用 `tenant_id`。
5. 业务主表统一包含 `id`、`tenant_id`、`created_at`、`updated_at`、`created_by`、`updated_by`、`deleted`。
6. 逻辑删除通过统一字段实现，不在业务代码里手动拼接删除条件。
7. 常用过滤字段默认建索引，例如 `tenant_id`、`status`、`created_at`、`course_id`、`exam_session_id`、`user_id`。
8. 后台列表必须有分页参数和最大 `pageSize` 限制，不允许默认返回全量数据。

建议迁移脚本路径：

```text
services/platform-api/src/main/resources/db/migration/
```

命名规则：

```text
V20260501_001__init_system_tables.sql
V20260501_002__init_tenant_tables.sql
V20260501_003__init_course_question_exam.sql
```

## 五、权限、租户与千人千面

一期采用：

**Spring Security + JWT + RBAC + 数据权限 + 动态菜单。**

默认设计：

1. 登录成功后返回 access token 和 refresh token。
2. access token 用于接口认证。
3. refresh token 存 Redis，可撤销。
4. 用户拥有角色，角色绑定菜单和按钮权限。
5. 用户同时绑定组织、部门、岗位、企业或项目关系。
6. 接口层校验功能权限，Service 层校验数据权限。
7. 前端菜单从后端接口加载，不在前端写死。
8. 登录后的首页由后端根据角色和用户画像返回。

一期不默认引入 Keycloak，原因是当前更需要快速跑通自研业务和权限模型。后续如果需要集团 SSO、第三方企业登录或统一身份中心，再单独引入 Keycloak 或 Spring Authorization Server。


## 七、工作流与自动化框架

核心业务流程采用 Flowable：

1. 培训协议审批。
2. 项目准备审核。
3. 认定材料审核。
4. 补贴材料审批。
5. 归档提交流程。
6. 跨部门审批和驳回修改。

Flowable 流程文件放在：

```text
workflows/bpmn/
```

n8n 用于外部自动化：

1. 定时生成项目周报草稿。
2. 项目延期自动提醒。
3. 审批通过后发送企业微信、钉钉、短信或邮件。
4. 文件上传后触发 AI 材料检查。
5. 与第三方系统做低风险数据同步。

n8n workflow 导出文件放在：

```text
workflows/n8n/
```

规则：Flowable 管业务状态，n8n 管自动化动作。n8n 不作为核心业务状态源。

后台可以统一展示为“工作流中心”，但技术上必须区分三类能力：

| 后台能力 | 技术归属 | 边界 |
| --- | --- | --- |
| 业务流程 | Flowable + Java + 数据库 | 管流程模板、流程实例、审批、驳回、状态和留痕 |
| 自动化任务 | n8n | 仅限内部自动化动作，不作为客户可配置能力 |
| AI 节点 | Skill + MCP + AI Gateway | 负责生成、检查、总结、创建草稿，不直接决定核心业务状态 |

n8n 使用边界：

1. n8n 仅供内部员工、内部系统管理员和内部自动化任务使用。
2. 不在客户侧开放 n8n 编辑器、workflow 配置、credentials 管理和执行后台。
3. 不托管客户自己的第三方账号凭证或客户自定义 workflow。
4. 对外产品中的工作流能力由 Java 平台和 Flowable / 自研配置承载。
5. 如果后期需要向客户开放 n8n 能力，必须先完成商业授权、OEM / Embed 授权和法律审查。

### 7.1 对象存储执行规则

文件存储统一通过平台文件服务和 Cloud OSS Adapter 调用，不把业务代码绑定到具体云厂商。

执行规则：

1. 一期不使用 MinIO，不作为默认生产方案、不作为必须部署组件、不写入 Docker Compose 基础环境。
2. 生产环境优先使用阿里云 OSS 或腾讯云 COS。
3. 业务模块只关心上传、下载、预签名 URL、删除、权限校验和归档。
4. 实际供应商通过配置选择，例如 `aliyun-oss` 或 `tencent-cos`。
5. NAS 只作为已有素材、内部大文件或历史资料的索引来源，不作为平台标准上传文件的主存储。
6. 云厂商对象存储需关注账号归属、费用、桶权限、数据合规、生命周期规则和备份策略。

### 7.2 Redis 与 Docker 执行规则

Redis 执行规则：

1. 代码层使用 Redis 协议、Spring Cache 和 Spring Data Redis。
2. 生产部署优先采购阿里云 Tair / 云数据库 Redis 版或腾讯云 Redis。
3. 一期不自建 Redis 集群作为默认方案。
4. Redis 只用于缓存、会话、验证码、任务状态、限流等基础设施，不作为业务主数据库。
5. 不把 Redis 包装成对外数据库服务或客户可购买能力。

Docker 执行规则：

1. 测试、预生产和生产服务器使用 Linux Docker Engine / Docker Compose，后续规模化部署再评估 Kubernetes / containerd。
2. Docker Desktop 只可能用于个人开发机，不进入生产部署要求。
3. 公司开发机使用 Docker Desktop 前，必须由公司统一确认 Docker 商业订阅授权。
4. 如果不采购 Docker Desktop，macOS 开发机优先使用 OrbStack、Rancher Desktop、Colima 或远程 Linux 开发环境。

## 八、AI Gateway、Agent 与 MCP 框架

AI Gateway 放在：

```text
services/ai-gateway/
```

一期建议两种实现方式：

1. 如果只做平台内 AI 调用、知识库问答、材料检查，优先用 Spring Boot + Spring AI。
2. 如果要快速试验多 Agent 编排、工具调用和 MCP，独立 Node / TypeScript 服务更灵活。

一期默认：

1. AI Gateway 独立放在 `services/ai-gateway/`，作为统一 AI 能力入口。
2. MCP Server 独立放在 `services/mcp-server/`。
3. `platform-api` 可以保留 `ai/` 包作为 AI 业务记录、权限校验和草稿落库入口，但不直接承载复杂 Agent 编排。
4. AI Gateway 和 MCP Server 只调用 `platform-api` 暴露的受控接口，不直连业务数据库。

MCP Server 默认采用 TypeScript MCP SDK：

```text
services/mcp-server/
```

MCP 默认规则：

1. MCP Server 不直连业务数据库。
2. MCP Server 只调用 `platform-api` 暴露的受控接口。
3. 每个 MCP Tool 都必须有名称、用途、参数 schema、权限要求和审计日志。
4. 写操作默认只生成草稿或待办，关键动作需要人工确认。
5. AI 生成内容必须标记来源和生成时间。

Agent 工程化规则：

1. 不复制、不依赖、不传播任何疑似泄漏的专有提示词、源码或内部实现，只借鉴公开讨论中的工程化机制。
2. AI Gateway 负责模型调用、Prompt 编排、Agent 状态、草稿生成、使用资料记录和风险提示。
3. MCP Server 只暴露白名单工具，例如 `course.search`、`question.search`、`file.metadata.get`、`course_outline_draft.create`、`material_check_report.create`、`project_weekly_draft.create`。
4. 高风险动作必须使用 Plan / Execute 模式，计划阶段不能自动转为执行授权。
5. 草稿必须记录来源、使用资料、生成时间、触发人、租户、模型标识、草稿状态和人工确认记录。
6. 项目记忆、模块记忆和任务记忆由知识库和业务记录共同承载，不能绕过租户和权限边界。

## 九、测试框架与验收方式

后端测试：

| 类型 | 框架 |
| --- | --- |
| 单元测试 | JUnit 5 + Mockito |
| Web 接口测试 | Spring Boot Test + MockMvc |
| 数据库集成测试 | Testcontainers |
| 权限测试 | Spring Security Test |
| 流程测试 | Flowable Test |

前端测试：

| 类型 | 框架 |
| --- | --- |
| 单元测试 | Vitest |
| 组件测试 | React Testing Library |
| 端到端测试 | Playwright |
| 接口 Mock | MSW |

最低验收要求：

1. 登录、菜单、权限、数据权限必须有测试。
2. 培训、竞赛、认定三个主流程必须有端到端冒烟测试。
3. 文件上传、归档、实操检查清单这类强校验功能必须有失败路径测试。
4. AI 和 MCP 工具调用必须有权限失败、参数错误、人工确认三类测试。
5. 数据库迁移脚本必须能在空库执行成功。

## 十、一期不建议引入的框架

以下框架或方案暂不作为一期默认项：

| 方案 | 原因 |
| --- | --- |
| 全量微服务 | 一期采用可控服务化，不一开始拆出大量细业务服务，避免联调、部署和运维复杂度过高 |
| Kubernetes | 一期 Docker Compose 更快，等更细业务服务拆分和部署复杂度上来后再引入 |
| GraphQL | 当前后台管理、流程和报表以 REST + OpenAPI 更直接 |
| JPA 全量建模 | 后台管理系统复杂查询多，MyBatis-Plus 更适合当前团队和业务形态 |
| Keycloak | 一期自研权限模型更快；SSO 需求明确后再引入 |
| 重型 Agent 框架全量绑定 | AI 需求会快速变化，先用轻量 API + MCP + Prompt 模板更灵活 |
