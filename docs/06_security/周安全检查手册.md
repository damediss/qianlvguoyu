# 周安全检查手册（Security Weekly Playbook）

> 版本：v1.0　创建：2026-08-30　当前检查清单版本：**checklist v1**
> 执行频率：每周一次（定时任务：每周一 09:00 自动触发，也可手动执行）
> 报告产物：`docs/06_security/reports/{ISO周号}-周安全检查报告.md`
> 经验产物：`docs/06_security/experience/agent-experience-log.md`（追加式，禁止改写历史条目）

---

## 1. 目的与范围

以固定检查清单 + 可迭代检查点的方式，对项目代码做纵深安全巡检，覆盖三类核心风险（SQL 注入、XSS、CSRF）及随代码演进新增的检查点，输出分级报告并跟踪处置。

- **检查对象**：`services/platform-api/`（Java 后端）、`apps/admin-web/`（管理端）、`apps/student-web/`（若已创建）、手机端仓库 `gjjd_appnext`（涉及时）
- **不检查**：PHP 老系统（gjjd_phalcon，独立仓库，另行安排）、第三方依赖 CVE 扫描（后续版本可加）
- **原则**：只读检查，不修改任何生产配置与数据；发现按 P0~P3 分级报告，修复需另行授权

## 2. 多 Agent 执行机制

任何模型 Agent（ZCode / Claude Code / MiniMax / Cursor / Qoder / Codex 等）都可以执行本检查，规则如下：

1. **执行前置**：先读本手册与根目录 `AGENTS.md`，再动手。不要求了解历史会话，本手册自包含。
2. **署名制度**：报告中必须写明执行 Agent 名称与底层模型（如 `ZCode / GLM-5.3-Flash`），不同 Agent 的结果独立署名，便于横向比较各模型的能力差异。
3. **独立性与互补性**：
   - 定时触发时，报告标题注明当期执行 Agent；人工指定其他 Agent 复核时，复核报告单独成节（`复核意见`），不覆盖原报告。
   - 鼓励不同 Agent 用不同方法交叉验证同一检查点（如 grep 全扫 vs 按入口 Controller 逆向追踪），方法差异写入经验日志。
4. **经验回流（关键）**：每次执行完，执行 Agent **必须**向 `experience/agent-experience-log.md` 追加条目，格式见 §6。没有经验沉淀的执行视为未完成。
5. **能力差异记录**：若某 Agent 无法执行某检查点（工具受限/能力不足），在报告`未覆盖项`中说明原因，不得跳过不报。

## 3. 检查清单（checklist v1）

> 命令均为 POSIX 通用写法（Git Bash / Linux 均可执行）。后端根路径以下简称 `$BE` = `services/platform-api/src/main/java`，前端管理端 = `apps/admin-web/src`。

### 3.1 SQL 注入（SEC-SQLI）

| ID | 检查点 | 方法（可复制执行） | 判定标准 |
|---|---|---|---|
| SEC-SQLI-01 | Mapper XML `${}` 占位 | `grep -rn -F '\${' $BE/../resources/mapper --include=*.xml` | 0 命中为 PASS；命中逐个人工判定（动态表名/排序列白名单除外） |
| SEC-SQLI-02 | 注解 SQL `${}` | `grep -rn -F '\${' $BE --include=*.java` 并排除 `@Value("\${...}")` 配置占位符后逐条核对 | 注解 SQL（@Select/@Update/@Delete/@Insert）内不得出现 `${}` |
| SEC-SQLI-03 | JdbcTemplate 拼接 | `grep -rn -E 'jdbcTemplate\.(update\|query\|execute)' $BE --include=*.java` 逐处核参数 | SQL 字符串不得含 `+` 拼接的用户输入；一律 `?` 参数化 |
| SEC-SQLI-04 | Wrapper.last()/apply() 动态片段 | `grep -rn -E '\.last\(\|\.apply\(' $BE --include=*.java` | 拼接变量必须为 int/long 等数值类型或常量；字符串入参直拼即 FAIL |
| SEC-SQLI-05 | 排序/分页字段透传 | 查 `PageQuery` 类字段 + `grep -rn 'OrderItem' $BE` | 分页参数带边界校验；不得有前端可控的排序字段/列名透传 |
| SEC-SQLI-06 | 新增点回归 | `git log --since="7 days ago" --name-only` 对上周变更文件中含 SQL/Wrapper 的新代码重点复查 | 新代码遵循上述规则 |

### 3.2 XSS（SEC-XSS）

| ID | 检查点 | 方法 | 判定标准 |
|---|---|---|---|
| SEC-XSS-01 | 后端入参过滤/出参转义层现状 | `grep -rln -iE 'xss\|jsoup\|HtmlUtils\|escapeHtml' $BE` | 记录现状（当前：无全局层）；新增用户输入入口时评估是否需要清洗 |
| SEC-XSS-02 | 前端危险渲染点 | `grep -rn 'dangerouslySetInnerHTML' apps/admin-web/src`；手机端 `grep -rn -E 'rich-text\|uv-parse\|v-html' pages` | 逐处确认数据源：管理端录入的受控内容=低危；**学员/AI/外部来源内容=高危，必须加白名单清洗** |
| SEC-XSS-03 | 文件上传文件名处理 | `grep -rn 'getOriginalFilename' $BE` | 入库/回显前经过 sanitize；`Content-Disposition` 文件名不含原始用户输入 |
| SEC-XSS-04 | 富文本入库来源变化 | 追踪题库/文章/CMS 内容的新写入来源（AI 生成、批量导入、API 写入） | 来源从"管理端录入"扩展时，SEC-XSS-02 相关渲染点升级为 P1 复查 |

### 3.3 CSRF 与访问控制（SEC-CSRF）

| ID | 检查点 | 方法 | 判定标准 |
|---|---|---|---|
| SEC-CSRF-01 | CSRF 配置与鉴权模式匹配 | 读 `SecurityConfig`：csrf 状态 + 各链 sessionCreationPolicy | header-token + STATELESS 下禁用 CSRF=PASS；存在 cookie/session 鉴权的写端点却禁用 CSRF=FAIL |
| SEC-CSRF-02 | CORS 生产配置 | `CorsConfig` 默认值 + **生产 `.env` 实际值**（需服务器核查，本地标注"待核查"） | 生产必须显式白名单；`allowCredentials=true` 不得与通配 origin 并存于生产 |
| SEC-CSRF-03 | 白名单暴露面复查 | `grep -n 'permitAll' SecurityConfig` 逐条核对 | 每条 permitAll 有存在理由；带"测试专用/生成环境移除"注释的条目=FAIL |
| SEC-CSRF-04 | JWT/密钥默认值 | `grep -n 'dev-only-change-me\|:.*default' application.yml` 及生产 `.env` 核查 | 密钥类配置不得有可用默认值；生产必须已覆盖 |
| SEC-CSRF-05 | 有状态链专项 | 对非 STATELESS 的 SecurityFilterChain 逐一检查其端点 | 有状态端点若涉及写操作/敏感跳转，评估 login-CSRF 与 open redirect（跳转 URL 必须来自服务端固定值或白名单） |

### 3.4 本周变更专项（SEC-DIFF）

| ID | 检查点 | 方法 | 判定标准 |
|---|---|---|---|
| SEC-DIFF-01 | 上周新增 Controller/接口 | `git log --since="7 days ago" --name-only --diff-filter=A` 筛 `*Controller.java` 与前端页面 | 新接口必须有明确鉴权路径（受保护路径或白名单理由） |
| SEC-DIFF-02 | 新增配置项 | 上周 `application.yml` / env example 变更 | 密钥无默认值；新开关默认安全态 |

## 4. 报告规范

文件：`reports/{ISO周号}-周安全检查报告.md`（如 `2026-W35`）。必须包含：

1. **元信息**：检查日期、执行 Agent/模型、代码基线（`git rev-parse --short HEAD` + 分支）、范围
2. **检查点执行结果表**：每个 ID 标 PASS / FAIL / SKIP（原因）
3. **发现清单**：编号 F-xxx、级别、位置（`file:line`）、描述、建议、状态（待处置/已修复/接受风险）
4. **未覆盖项**：本次未能执行的检查点及原因（Agent 能力/权限/环境）
5. **复核意见**（如有其他 Agent 复核）
6. **与上期对比**：上期发现的状态流转（新报告需回看上一期报告）

**级别定义**：P0=可直接利用/数据泄露风险，立即处置；P1=生产配置缺陷或暴露面，一周内处置；P2=纵深防御缺失，排期处置；P3=观察项/低危。

## 5. 检查点迭代规则

1. 新检查点来源：经验日志中的高频教训、新架构引入的新风险面（如新增 AI 生成内容流、新增文件类型、新增鉴权方式）、线上事件复盘。
2. 流程：任何 Agent 可在报告`检查点提案`节提出 → 人工或下期执行时评审 → 通过后**升版本号**（v1→v2）并更新 §7 变更记录，不得直接静默改清单。
3. 检查点只增不删；废弃的标记 `DEPRECATED` 并注明原因。

## 6. 经验日志格式（experience/agent-experience-log.md）

追加条目模板：

```
### {日期} | {检查点 ID} | {执行 Agent/模型}
- **发现/误报**：一句话结论
- **方法与坑**：可复用的执行技巧（命令写法、误报甄别、工具差异）
- **建议**：是否值得升级为检查点/自动化脚本
```

规则：只追加不改写；每期执行至少 1 条；重复经验标注 `dup:{日期}` 链接到首条。
