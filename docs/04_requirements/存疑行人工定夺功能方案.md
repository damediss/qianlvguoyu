# 存疑行人工定夺功能方案

> 状态：**已实施**（2026-09-29：后端定夺服务+两接口+权限种子 V20260930_001 + 前端批量定夺 UI；73 用例全绿，npm build 0 错；§9 四项按建议拍板执行）
> 关联：知识归属修正（`exam/knowledgefix`）、方案 `docs/05_decisions/知识归属修正_JEV分层改造方案.md` v0.9
> 术语（统一语言，禁用同义词）：**改挂**（apply）/ **保留**（keep）/ **存疑**（flag）/ **写回** = 把改挂建议写进题库

## 1. 背景与目标

知识修正分类后产生大量存疑行（当前生产 901 条，其中"卫兵拦截 + 置信 ≥0.7"的高置信误伤 231 条）。
存疑行是"自动判定无把握、需人工定夺"的行，但现状**没有任何页面处置入口**——只能看列表、导出 xlsx，人工决策后靠裸 SQL 翻状态，既慢又不可审计。

**目标**：在知识归属修正工作台内提供存疑行的人工定夺能力：

1. 存疑列表列出**原知识点/新知识点的中文名称**（title），不再只有裸 id；
2. 支持**单行与批量定夺**：定夺为**改挂**（采用模型建议的新知识点，待写回落地）或**保留**（维持原知识点）；
3. 定夺动作**可审计**（谁、何时、定了什么），且不能破坏既有"备份 → 写回 → 可回滚"安全链。

## 2. 现状与缺口

### 2.1 数据层（`exam_detail_knowledge_fix`）

| 列 | 说明 |
|---|---|
| `id` | 雪花 id（清单行） |
| `detail_id` | 试题 id（→ `exam_exam_detail.id`） |
| `old_knowledge_id` / `new_knowledge_id` | 原/新知识点 id（→ `exam_knowledge_structure.id`，后者存疑行是模型建议、仅参考） |
| `confidence` / `basis` / `llm_reason` | 置信 / 依据 / 理由 |
| `status` | `flag`=存疑、`apply`=改挂待写回、`keep`=保留、`applied`=已写回、`pending`=待分类 |
| `updated_by` / `updated_at` | 最近操作人/时间 |

### 2.2 现有能力缺口

1. `GET /exam/knowledgefix/fix/list` 返回的 `FixItemVO` 只有 old/new 的**裸 id**，无 title——人工判读必须逐行查库；
2. 无翻状态接口：定夺要裸 SQL `UPDATE ... SET status='apply'/'keep'`；
3. 前端存疑页签只能看，无任何操作列/勾选。

### 2.3 既有安全链（必须保住）

写回（`KnowledgeFixWriteBackService.apply`）= 备份整行 → 逐行 PK 更新 `exam_exam_detail.knowledge_id` → 清单行置 `applied`，全程可回滚。**定夺功能绝不直接写 `exam_exam_detail`**——只改清单行状态，题库落地仍走既有「执行写回」按钮。

## 3. 功能设计

### 3.1 状态机约束（后端强制）

```
存疑(flag) --定夺改挂--> 改挂(apply)   （采纳 new_knowledge_id，等写回落地）
存疑(flag) --定夺保留--> 保留(keep)   （维持 old_knowledge_id，写回不处理）
```

- **仅允许 `flag → apply / keep`**：其余状态（pending/apply/keep/applied）一律拒绝，并发下用 `WHERE id=? AND status='flag'` 条件更新兜底（affected=0 即视为被并发改走，计入 skipped）；
- 定夺为改挂前**后端预校验** `new_knowledge_id` 存在、未删、与行 `course_id` 一致（复用写回同款 course 校验口径，防人工采纳了一个越界建议）；
- 定决不改动 `confidence/basis/llm_reason`（模型原始结论原样保留，审计可查"当初模型怎么判的"）。

### 3.2 列表增强（title 中文名）

`FixItemVO` 增加 `oldKnowledgeTitle` / `newKnowledgeTitle` 两个字段。Controller 在分页查出当页记录后，收集本页 old/new id 集合，一次性按 id 批量查 `exam_knowledge_structure`（BaseMapper `selectBatchIds`）组装 Map 回填——**不改分页 SQL、不引 N+1**。

列表同时带出题干摘要（新增 `stemPreview`，`LEFT(content, 80)`，联 `exam_exam_detail`）——目前看存疑行必须脑内拼 detail_id 再查题干，批量定夺时不可接受。实现：组装阶段按 `detail_id` 批量查 `exam_exam_detail` 取 content 截断（同样是当页一次批量查，不 N+1）。

### 3.3 定决入口与交互

**后端新增两个接口**（controller `KnowledgeFixController`）：

| 接口 | 说明 |
|---|---|
| `POST /exam/knowledgefix/fix/adjudicate` | 单行定夺 `{rowId, action: "apply"\|"keep"}` |
| `POST /exam/knowledgefix/fix/adjudicate/batch` | 批量定夺 `{rowIds: number[], action}`（rowIds ≤ 200，超出 400） |

返回统一：`{succeeded: n, skipped: [{rowId, reason}]}`——被并发改走/状态不符/新节点越界的行跳过并给原因，不整批失败。

**前端（`KnowledgeFixPage` 知识修正页签）**：

- 存疑页签表格改造：
  - 列：勾选框、`detail_id`、**题干摘要**（新增）、**原知识点**（`id + title`）、**新知识点**（`id + title`）、置信、依据、理由、**操作**（单行「定夺」下拉按钮：改挂 / 保留，均弹确认框，确认框里把两个 title 再摆一遍防手滑）；
  - 顶部批量操作条（有勾选时出现）：「已选 N 行」＋「批量定夺为改挂」「批量定夺为保留」（Popconfirm 确认）；
  - 定夺成功后：toast 显示成功/跳过数，勾选清空，当前列表与统计自动刷新（存疑行定决后从列表消失）。
- 写回按钮旁加静态提示语：「定决为改挂的行需点「执行写回」才会写进题库」。

## 4. 权限（三步链，缺一 403）

1. **权限码**：新增 `exam:knowledgefix:adjudicate`（两个定夺接口 `@PreAuthorize` 挂上）；
2. **角色授权**：幂等种子 SQL 给管理员角色授权——实施时按既有 `exam:knowledgefix:classify:export` 的授权行复制模式写（`INSERT ... SELECT ... WHERE NOT EXISTS`），目标角色以生产 `sys_role_permission` 现有知识修正权限的授权对象为准；
3. 菜单不变（知识归属修正菜单已存在）。

## 5. 安全与审计

- 两个写接口均记操作日志（项目统一操作日志机制：操作人/动作/行 id/定夺结果）；
- 定夺行的 `updated_by`/`updated_at` 自然落当前用户与时间；
- 批量上限 200 + 逐行条件更新，杜绝"翻错状态"与"一把梭超时被中断半截"；
- 定决不碰 `exam_exam_detail`，题库变更仍集中在既有写回单一入口（备份/回滚口径不变）。

## 6. 测试计划

**后端单测**（桩模式，不起 Spring）：
1. 单行定夺：flag→apply 成功、flag→keep 成功；非 flag 行拒绝（409/400）；new_knowledge_id 越界（course 不一致）拒绝；
2. 批量定决：混合状态入参（部分已被并发改走）→ 成功的成功、跳过的带原因返回；
3. 列表：title/stemPreview 回填正确，新节点已删时 title 显示「（已删）」而非报错；
4. 权限失败路径（Spring Security Test 或桩断言 `@PreAuthorize` 存在）。

**前端**：`npm run build`（含 tsc）0 错；批量勾选-定决-刷新链路走查。

**验收**：
- [ ] 存疑列表可见原/新知识点中文名与题干摘要
- [ ] 单行定夺两种结果均可生效且列表即时刷新
- [ ] 批量定夺 200 行内成功，混合状态行跳过并提示原因
- [ ] 定决为改挂的行经「执行写回」正确落库且可回滚
- [ ] 无权限账号调定夺接口 403

## 8. 明确不做（本期边界）

- 不做"定决即写回"的一步直达（保住备份-写回-回滚单入口）；
- 不做存疑行**编辑新知识点 id**（模型建议不可改，要改走后续需求）；
- 不做待分类/已写回行的定夺（只覆盖存疑）；
- 不动既有批量「复位并重跑」语义。

## 9. 待确认项（拍板后开工）

| # | 取舍 | 我的建议 | 备选 |
|---|---|---|---|
| 1 | 定决为改挂的行是否**立即写回** | **不立即**（两步走：定夺翻状态 → 页面点写回统一落地，备份审计链不变） | 定决时顺手写回（省一步，但写回入口变两个，备份链分散） |
| 2 | 批量上限 | 200 行/次 | 500（误操作爆炸半径大） |
| 3 | 定决理由 | 不填（updated_by/操作日志已可审计） | 必填短文本（审计更厚，操作更重） |
| 4 | 已删知识点（old=工匠精神培养 deleted=1 那类）定决为保留 | **拒绝保留**（原节点已删，保留=挂死节点），只允许改挂 | 允许保留（行内挂死节点，后续靠别的治理） |
