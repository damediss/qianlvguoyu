# 云平台技术路线选型建议

版本：V0.1 草稿  
日期：2026 年 5 月 1 日  
用途：公司云平台、SaaS、AI Agent、工作流、自研开发与后续技术路线决策备用

## 一、总体判断

当前要建设的平台不是单一的 SaaS 网站，而是一个覆盖培训、竞赛、认定、课程、题库、证书、补贴、项目管理、资料归档、知识库、AI 智能体、工作流和内部自研交付的综合性业务平台。

技术选型的核心不是单纯比较 Java、Go、Rust、Node.js 谁更先进，而是要满足以下目标：

1. 统一账号、组织、角色、权限和数据权限。
2. 统一培训、竞赛、认定、课程、题库、证书等核心业务数据。
3. 支撑 SaaS 多租户和登录后的千人千面。
4. 支撑审批、认定、补贴、归档、项目催办等流程流转。
5. 支撑 AI 助手、Agent 代理、MCP 工具调用和知识库问答。
6. 支撑历史系统接管、旧 PHP 系统重构和现有 Java 平台复用。
7. 支撑后续长期自研、运维、审计、扩展和对外交付。

因此建议采用“Java 核心业务主服务 + 可控服务化 + 工作流引擎 + n8n 自动化 + AI Gateway + MCP 工具层 + 对象存储 + 多租户权限体系”的技术路线。

## 二、推荐主技术栈

| 层级 | 推荐技术 | 用途 |
| --- | --- | --- |
| 后端主栈 | Java / Spring Boot | 培训、竞赛、认定、课程、题库、证书、补贴、审批、权限、审计等核心业务 |
| 前端管理端 | React + TypeScript + Ant Design Pro | PC 管理后台、领导驾驶舱、业务操作台、数据面板 |
| 移动端 / 学员端 | H5 / 小程序优先，后续再评估 UniApp、Flutter 或原生 App | 学习、练习、考试、通知、证书、个人档案 |
| 数据库 | MySQL | 核心业务数据、流程数据、统计数据 |
| 缓存 | Redis 协议缓存，生产优先阿里云 Tair / 云数据库 Redis 版或腾讯云 Redis | 会话、验证码、热点数据、n8n 队列、任务状态、限流 |
| 消息队列 | RabbitMQ 优先；Kafka 二期评估 | 通知、审批事件、导入导出、AI 任务、异步处理 |
| 文件存储 | 阿里云 OSS / 腾讯云 COS + NAS 索引 | 上传材料、课件、证书、归档文件、课程资料、内部技术资料 |
| 工作流 | Flowable | 审批、认定、补贴、归档、项目流程 |
| 自动化 | n8n | 外部通知、定时任务、接口同步、低代码自动化、AI 辅助流程 |
| AI 服务层 | AI Gateway / Agent 服务 | 独立服务，统一接入大模型、知识库、工具调用、Agent 编排 |
| MCP 工具层 | MCP Server | 让 AI 在授权范围内调用业务系统接口和工具 |
| 部署 | Linux Docker Engine / Docker Compose 起步，Kubernetes / containerd 二期 | 一期快速部署，二期规模化运维 |

## 三、后端为什么建议以 Java 为主干

建议后端主平台采用 Java / Spring Boot，而不是把主业务系统押在 Go、Rust 或纯 Node.js 上。

主要原因：

1. 现有资料里已经多次提到原 Java 云平台、PHP 向 Java 重构、竞赛和培训系统统一到 Java。
2. 培训、竞赛、认定、课程、题库、证书、审批、补贴、权限、审计都是典型企业业务系统，Java 生态成熟。
3. Java 更适合长期承载复杂业务规则、权限模型、流程状态、审计日志和后台管理。
4. 后续如果要接 Flowable、Spring Security、Spring Authorization Server、报表、任务调度等企业组件，Java 更顺。
5. 内部团队培养、招聘和长期维护也更容易找到 Java 工程师。

推荐版本：

1. 新项目建议使用 OpenJDK 21 LTS。
2. 后续预留升级到 Java 25 LTS 的空间。
3. Spring Boot 建议使用当前稳定版本线，不使用过旧版本。

## 四、Go 和 Rust 的定位

Go 和 Rust 可以使用，但不建议作为主业务平台的核心技术栈。

Go 适合：

1. 高并发网关。
2. 文件处理服务。
3. 数据同步服务。
4. 消息推送服务。
5. 轻量 MCP Server。
6. 独立工具服务。

Rust 适合：

1. 桌面端 AI 助手。
2. 本地安全工具。
3. 高性能文件处理。
4. 仿真、加密、边缘端或本地代理模块。
5. 对性能和安全要求很高的底层能力。

结论：Java 做主干，Go / Rust 做专项能力。不要为了技术先进，把培训、竞赛、认定、审批、权限这些主业务全部押到 Go 或 Rust 上，否则会增加团队建设、协同开发和长期维护难度。

## 五、工作流与 n8n 的关系

> **状态注记（2026-09-29）**：一期未部署 n8n，内部自动化/通知/定时由平台自实现（定时任务、消息通知等）；
> AGENTS.md 与 README.md 的操作口径已同步移除 n8n。以下论证保留作选型备查——若将来启用 n8n，
> 先撤销本注记并同步恢复两份文档的口径。

核心业务流程不能只靠 n8n。

培训、竞赛、认定、补贴、审批、归档这些流程是平台的核心业务状态，必须进入 Java 后端和业务数据库，具备权限、审计、状态回放、版本、人工确认和验收标准。

建议分层：

| 类型 | 建议方案 | 说明 |
| --- | --- | --- |
| 简单状态流转 | Java 状态机 + 审批表 | 适合项目状态、资料状态、简单审核 |
| 复杂审批和业务流程 | Flowable | 适合认定、补贴、协议审批、归档、跨部门流转 |
| 外部自动化 | n8n | 适合通知、定时任务、接口同步、AI 生成草稿、企微/钉钉/短信/邮件提醒 |

n8n 适合做自动化外挂，不适合做核心业务数据的唯一流程引擎。

典型用法：

1. 每天自动检查延期项目并提醒责任人。
2. 文件上传后触发 AI 检查材料缺失。
3. 项目周报定时生成草稿。
4. 审批通过后自动通知企业或内部人员。
5. 与企业微信、钉钉、短信、邮件、第三方接口做连接。

### 5.1 n8n 授权与商业边界

n8n 在本项目中仅作为企业内部自动化工具使用，开始阶段不作为对外 SaaS 产品能力开放。

允许范围：

1. 内部员工和内部系统管理员使用 n8n。
2. 内部项目周报、材料缺失检查、文件上传后 AI 检查、内部通知、内部数据同步等自动化任务。
3. 使用公司自己的企业微信、钉钉、邮箱、短信、OSS、AI Key 等账号凭证。
4. 客户侧只看到业务结果，例如通知结果、材料检查结果、待办状态，不接触 n8n 后台。

禁止范围：

1. 不向企业客户开放 n8n 编辑器、workflow 配置、credentials 管理和执行后台。
2. 不让客户创建、编辑、运行自己的 n8n workflow。
3. 不托管客户自己的第三方账号凭证。
4. 不将 n8n 白标包装为公司自有 SaaS 功能并对外收费。
5. 不将 n8n 作为客户自定义工作流或客户自动化平台的底层能力直接售卖。

核心原则：

1. 核心业务状态仍由 Java + Flowable / 数据库管理。
2. n8n 只做内部通知、定时、AI 检查触发、低风险数据同步等胶水层。
3. 如果后期要向客户开放自定义工作流能力，优先走自研工作流配置；如直接开放 n8n 能力，必须先采购 n8n 商业授权、OEM 授权或 Embed 授权，并完成授权审查。

### 5.2 对象存储使用边界

本项目一期不使用 MinIO，不建设自托管对象存储服务。生产环境优先使用阿里云 OSS 或腾讯云 COS，后端通过统一的 File Storage Adapter 封装文件能力。

对象存储原则：

1. 业务模块只调用平台文件服务，不直接调用阿里云 OSS、腾讯云 COS 或其他云厂商 SDK。
2. 文件服务统一提供上传、下载、预签名 URL、删除、权限校验和归档能力。
3. 实际供应商通过配置选择，例如 `aliyun-oss` 或 `tencent-cos`。
4. NAS 只作为已有素材、内部大文件或历史资料的索引来源，不作为平台标准上传文件的主存储。
5. 云厂商对象存储需要重点关注账号归属、费用、桶权限、生命周期规则、备份策略和客户数据合规。

### 5.3 Redis 使用边界

代码层使用 Redis 协议和 Spring Cache，生产部署优先采购阿里云 Tair / 云数据库 Redis 版或腾讯云 Redis，不自建 Redis 集群作为一期默认方案。

Redis 使用原则：

1. Redis 只作为缓存、会话、验证码、任务状态、限流等基础设施。
2. 不把 Redis 包装成对外数据库服务或客户可购买能力。
3. 业务数据的主状态仍以 MySQL 业务数据库为准。
4. 云 Redis 需要重点关注费用、实例规格、备份策略、内网访问、账号权限、审计和数据安全。

### 5.4 Docker 使用边界

生产和测试服务器不依赖 Docker Desktop，使用 Linux 服务器上的 Docker Engine / Docker Compose，后续规模化部署再评估 Kubernetes / containerd。

Docker 使用原则：

1. Docker Desktop 只可能用于个人开发机，不进入生产部署要求。
2. 公司开发机使用 Docker Desktop 前，必须由公司统一确认 Docker 商业订阅授权。
3. 如果不采购 Docker Desktop，macOS 开发机优先使用 OrbStack、Rancher Desktop、Colima 或远程 Linux 开发环境。
4. 项目的部署文档、测试环境和生产环境只要求 Docker Engine / Docker Compose 或后续 Kubernetes / containerd，不把 Docker Desktop 写成项目依赖。

## 六、AI、MCP、Skill 和 Agent 的落地方式

AI 不应该直接连接数据库随意查询，也不应该绕过系统权限直接执行操作。

建议增加一层 AI Gateway / Agent 服务，统一管理：

1. 大模型接入。
2. 知识库检索。
3. 用户权限和数据权限。
4. Prompt 模板。
5. Agent 任务状态。
6. MCP 工具调用。
7. 人工确认。
8. 日志审计。

AI Agent 工程化原则：

1. 学习公开 AI 编程工具的工程化思路，但不复制、不依赖、不传播任何疑似泄漏的专有提示词、源码或内部实现。
2. AI 能力按“岗位 Agent 工作台 + 项目记忆系统 + MCP 受控工具 + 草稿优先机制 + 人工确认闭环”建设。
3. 项目记忆分为项目总览记忆、模块记忆和任务记忆，所有长期记忆必须有来源、版本、负责人和更新时间。
4. 每个 AI 能力采用约束优先 Prompt，明确目标、用户角色、可用资料、可用工具、禁止事项、输出格式和人工确认点。
5. 高风险任务采用 Plan / Execute 模式，修改权限、发布课程、审批通过、删除文件、发送通知等动作必须先计划、后确认、再执行。
6. AI 写操作默认只生成草稿，包括课程大纲草稿、材料检查报告、项目周报草稿、通知草稿和审批意见草稿。
7. 复杂任务拆成多个 Agent 阶段，例如资料整理、大纲生成、题库生成、质量检查和人工确认。
8. 每次项目、课程、认定、竞赛或上线结束后，AI 辅助复盘并沉淀经验，但复盘结果必须人工确认后入库。

MCP 的定位：

1. MCP 是 AI 调用外部系统、数据源和工具的协议层。
2. 平台可以为 AI 暴露受控工具，例如查询项目进度、检查材料缺失、生成周报、创建待办、发送通知。
3. 每个 MCP 工具都必须有权限校验、参数校验、操作日志和必要的人工确认。

Skill 的定位：

1. Skill 用于沉淀固定业务能力和固定工作方法。
2. 例如课程生成 Skill、认定材料检查 Skill、竞赛方案生成 Skill、项目周报 Skill、PHP 转 Java 重构 Skill。
3. Skill 更像“岗位经验和流程模板”，MCP 更像“AI 调用系统工具的接口”。

Agent 的定位：

1. Agent 不是普通聊天机器人，而是能围绕目标连续执行多个动作。
2. 第一阶段先做建议型 Agent，由 AI 生成建议、材料和提醒，人来确认。
3. 第二阶段做半自动 Agent，AI 可以创建草稿、生成待办、发起通知，但关键动作仍需人工确认。
4. 第三阶段再做授权执行 Agent，让 AI 执行低风险、规则明确、可追溯的重复操作。

优先建设的 Agent：

| Agent | 作用 |
| --- | --- |
| 项目周报 Agent | 自动读取项目进度，生成周报、风险和需协调事项 |
| 课程生成 Agent | 根据课程资料生成大纲、课件初稿、讲义和题库 |
| 材料检查 Agent | 检查认定、培训、补贴材料缺失和格式错误 |
| 竞赛运营 Agent | 生成竞赛方案、通知、名单、评分分析和总结 |
| 认定审核 Agent | 检查资格、材料、证书和归档状态 |
| 营销跟进 Agent | 生成客户方案、跟进话术、复训续费提醒 |
| 研发治理 Agent | 检查源码、接口、数据库、部署文档、测试用例和交付物完整性 |

一期优先样板：

1. 课程大纲生成 Agent。
2. 材料检查 Agent。
3. 项目周报 Agent。
4. 错题分析 Agent。

## 七、SaaS 与千人千面设计

千人千面不能靠前端写死不同页面，而要靠后端配置和权限体系支撑。

必须具备：

1. 多租户：tenant_id / org_id / company_id。
2. 组织架构：公司、部门、岗位、项目组、企业客户。
3. 角色权限：RBAC，角色决定菜单和操作权限。
4. 数据权限：不同企业、部门、项目、岗位只能看授权数据。
5. 动态菜单：不同角色登录后看到不同模块入口。
6. 动态首页：不同角色登录后进入不同工作台。
7. 用户画像：工种、等级、学习记录、考试记录、项目关系、负责事项。
8. 推荐规则：课程、题库、错题、通知按工种、等级、项目状态推送。

不同用户的首页示例：

| 用户类型 | 登录后首页 |
| --- | --- |
| 老板 / 管理层 | 领导驾驶舱、项目风险、业务数据、待拍板事项 |
| 培训负责人 | 培训项目、开班材料、学员进度、结课和证书 |
| 课程人员 | 课程库、题库、AI 课程初稿、审核任务 |
| 认定专员 | 认定项目、材料检查、考试清单、归档状态 |
| 竞赛运营 | 竞赛报名、题库、赛程、评分、排名、导出 |
| 企业客户 | 下单、审核材料、查看进度、确认名单 |
| 学员 | 学习任务、练习、考试、错题、证书、通知 |

## 八、系统架构建议

一期采用可控服务化架构起步，而不是全量微服务。

标准口径：

**平台一期采用“可控服务化 + 统一平台底座 + 领域分层”的企业级架构。系统从第一天建立清晰的服务边界，但不做全量微服务拆分，优先将 AI、MCP、文件、通知、工作流等边界清晰能力独立服务化，核心业务保持统一权限、统一租户、统一数据模型和统一业务规则，兼顾稳定性、开发速度和长期扩展能力。**

性能口径：

**平台性能架构采用“轻核心、异步化、缓存化、对象存储直连、AI 独立隔离、服务可水平扩展”的设计原则。核心业务服务保持无状态和轻量化，所有耗时任务通过异步任务、消息队列或 n8n 自动化处理；热点数据通过 Redis 加速；大文件通过 OSS/COS 存储；AI、MCP、文件、流程等资源敏感能力与核心业务服务解耦，避免单点压力拖垮主系统。**

原因：

1. 公司希望从第一天具备服务化边界，便于后续扩展、团队协作和技术资产沉淀。
2. AI、MCP、文件、通知、工作流属于技术边界清晰的能力，适合优先独立。
3. 账号、租户、权限、课程、题库、考试、学习记录等核心业务规则必须统一，不能拆散后重复实现。
4. 一期不做全量微服务，避免网关、注册中心、配置中心、链路追踪等服务治理体系过早压垮交付节奏。

核心业务模块仍按领域划分：

1. 账号与权限模块。
2. 多租户与组织模块。
3. 课程库模块。
4. 题库模块。
5. 考试模块。
6. 培训模块。
7. 竞赛模块。
8. 认定模块。
9. 证书模块。
10. 补贴模块。
11. 项目管理模块。
12. 审批与工作流模块。
13. 文件与归档模块。
14. 数据报表模块。
15. AI 与知识库模块。
16. Agent 与 MCP 工具模块。
17. 系统集成模块。

一期建议服务边界：

| 服务 | 职责 |
| --- | --- |
| `platform-api` | 核心业务主服务，承载账号权限、租户组织、课程、题库、考试、学习记录、成绩、错题、统一审计和核心业务 API |
| `ai-gateway` | AI 能力入口，负责模型调用、Prompt 编排、课程大纲草稿生成、材料检查和 AI 任务记录 |
| `mcp-server` | MCP 工具服务，给 AI 暴露受控业务工具，只调用平台 API，不直连数据库 |
| `file-service` | 文件元数据、上传、下载、预签名 URL、删除、OSS/COS 适配；一期可按进度决定独立部署或先并入 `platform-api` |
| `workflow-service` | 流程定义、审批任务、流程记录；一期可先将 Flowable 集成在 `platform-api`，但按独立服务边界设计 |

明确不做：

1. 不一开始拆出 `course-service`、`exam-service`、`tenant-service`、`user-service` 等大量细业务服务。
2. 不让每个服务各自实现一套用户、租户、权限、字典、文件和审计。
3. 不一开始强制引入 Kubernetes、注册中心、配置中心和完整链路追踪。

性能与资源控制重点：

1. MySQL 表结构、索引、分页和查询条件从第一阶段开始规范，禁止无条件全表查询。
2. `platform-api` 保持无状态，登录 token、菜单权限、字典、验证码、限流和任务状态放 Redis。
3. AI 生成、文件解析、批量导入、报表生成、通知发送、材料检查等慢任务走异步，不阻塞用户请求。
4. 文件不穿透核心业务服务，大文件后续通过预签名 URL 直传 OSS/COS，数据库只存元数据和权限。
5. AI Gateway 独立隔离，AI 故障不影响登录、课程、考试、成绩等核心链路。
6. 首页和工作台使用聚合接口，减少前端多接口串行请求。
7. 前端模块按需加载，后台大表格分页，学员端 H5 保持轻量。
8. 一期只运行必要服务，使用 Docker Compose 管理，避免资源被过早引入的治理组件消耗。

## 九、数据与知识库底座

平台后续 AI 化的前提是数据和资料结构化。

必须优先标准化的数据：

1. 企业。
2. 学员。
3. 教师。
4. 考评员。
5. 督导员。
6. 工种。
7. 等级。
8. 课程。
9. 知识点。
10. 题目。
11. 试卷。
12. 考试记录。
13. 学习记录。
14. 证书。
15. 培训项目。
16. 竞赛项目。
17. 认定项目。
18. 材料清单。
19. 归档文件。
20. 审批记录。

知识库建议分为：

| 知识库类型 | 内容 |
| --- | --- |
| 制度流程库 | 公司制度、审批流程、培训流程、竞赛流程、认定流程 |
| 项目资料库 | 项目方案、合同要点、会议纪要、周报、验收材料、复盘报告 |
| 课程题库库 | 课程大纲、课件、讲义、题库、实操标准、评分规则 |
| 客户营销库 | 客户需求、案例、宣传素材、方案模板、报价口径 |
| 系统技术库 | 源码说明、接口文档、部署文档、数据库说明、交付清单 |
| 工业仿真库 | 工艺流程、设备说明、操作规程、模型资产、交互脚本、评分标准 |

知识库不能只是文件上传，要记录来源、版本、负责人、更新时间、适用范围、权限和引用日志。

## 十、部署与运维建议

一期：

1. Linux 服务器使用 Docker Engine / Docker Compose 部署。
2. 测试环境、预生产环境、生产环境分开。
3. 数据库每日备份。
4. 文件对象存储开启版本和生命周期策略。
5. 日志集中采集。
6. 接口错误、任务失败、流程异常必须有告警。
7. 所有自研代码、脚本、部署配置和技术文档进入公司 Git 仓库或统一代码资产库。

二期：

1. Kubernetes。
2. 更细业务服务拆分。
3. 灰度发布。
4. 自动扩缩容。
5. 完整链路追踪。
6. 数据仓库或湖仓。
7. AI 调用成本监控。

## 十一、一期落地建议

第一阶段不要追求一次性做完整大平台，而要先跑通主流程。

建议一期优先：

1. 统一账号、角色、菜单、权限。
2. 统一企业、学员、课程、题库、工种、等级等基础数据。
3. 培训主流程：报名、学员、课程、学习、题库、考试、成绩、证书。
4. 竞赛主流程：报名、签到、题库、比赛、评分、排名、导出。
5. 认定主流程：项目、材料、考试清单、归档、证书台账。
6. 文件上传和归档。
7. 基础数据面板。
8. AI 精准学基础入口：错题、薄弱知识点、推荐练习、学习报告。
9. 知识库最小可用版本。
10. 2-3 个 Agent 试点：项目周报、课程生成、材料检查。
11. n8n 用于通知和自动化，不承载核心业务状态。
12. MCP 工具先只开放查询、生成草稿、创建待办等低风险动作。

## 十二、最终结论

建议公司云平台采用以下路线：

**Java Spring Boot + React / TypeScript / Ant Design Pro + MySQL + 托管 Redis + 阿里云 OSS / 腾讯云 COS + Flowable + n8n + AI Gateway + MCP + Docker Engine / Docker Compose。**

落地原则：

1. Java 做业务主干。
2. n8n 做外部自动化外挂。
3. Flowable 做核心流程引擎。
4. AI Gateway 做统一 AI 能力入口。
5. MCP 做 AI 调用业务系统的工具协议。
6. Skill 沉淀岗位方法和业务模板。
7. Go / Rust 做专项能力，不做主业务平台核心。
8. 一期用可控服务化起步，优先拆 AI、MCP、文件、通知、工作流等清晰边界，不做全量微服务。
9. SaaS 和千人千面必须从多租户、权限、动态菜单、动态首页和用户画像开始设计。
10. AI 化必须建立在公司掌握源码、数据、接口、权限、流程和知识库的基础上。

一句话判断：

**Java 做主干，n8n 做自动化，MCP / Agent 做 AI 工具层，Go / Rust 做专项能力，不要反过来。**
